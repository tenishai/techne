# liveness — subsystem health checks (techne#468/#469)

WHAT: answers "did each rail actually RUN?", as distinct from "is the store internally consistent?" (storage checks) and "is it even WIRED?" (hook-registration drift). Born from 2026-08-02/03, when six built-but-never-wired rails were found cold — `reflect` for four weeks — under a `techne doctor` printing "All checks passed", because doctor only looked at duplicate rows and reclaimable space.
SEAM: a registry (`register_check` / `registered_checks` / `run_checks`) of `CheckFn(config) -> CheckResult | list[CheckResult]`, plus the marker-writing side in `techne/hooks/_liveness.py` (`record_hook_run`, one `hook:<name>:last_run` / `:last_error` row per hook in `extension_state`).
VERDICTS (`Verdict`): live · dormant · stale · unobservable · broken · unknown. DECLARATION ORDER IS NOT SEVERITY ORDER — `worst()` ranks by `_SEVERITY`, where DORMANT TIES WITH LIVE (deliberate dormancy is healthy) and UNKNOWN sits BETWEEN them and STALE, not last: a probe that could not run must outrank a healthy rail, but loses the headline to a rail that ran and reported trouble. `CheckResult.ok` is true for live and dormant ONLY.
`runtime:revision` (techne#473) asks WHICH REVISION is running — a merged fix is not a deployed fix, and on 2026-08-03 a machine ran a known-crashing build for hours after the fix merged because the interpreter pointed at a shared working tree. Compares HEAD against the LOCAL origin/main ref and never fetches: a health check that hits the network fails on a plane. ONLY `main` COUNTS AS A DEPLOYMENT (CI and dev worktrees are working checkouts, and a red they can never clear is noise) — but a working checkout still STATES how far behind it is, because "on a peer's branch, behind the merge" IS the #473 incident and reporting it green without a number reproduced the bug inside its own fix.
CHECKS: per-hook liveness, the self-maintenance rails, outbox lanes, vector coverage, and `mcp:registration` — the last of which asks a different question from the rest. The MCP server is launched by the HOST, so there is no marker to read; what is checkable is whether the RECORDED launch command still resolves (techne#370). Kind.FRESHNESS: a source moved and its mirror did not.
CONSUMERS: `techne doctor` (`cli.py:_render_liveness`) and the SessionStart banner (`core/health.py` — `checks_worst` / `checks_summary` / `checks_error`). NOT `techne status`, which renders hook-registration DRIFT only and no liveness at all.

INVARIANTS — the ones a diff will not show you:

- **UNOBSERVABLE IS A FAILING STATE, NOT A WARNING.** A rail that cannot report is unfinished. "It might be fine" must never render as passing; that ambiguity is the whole reason this subsystem exists. (techne#468, Richard: "i want to know that when i run something it works, or it doesnt.")
- **CHECKS REPORT, THEY NEVER SELF-HEAL.** Print the remedy command; do not run it.
- **NEVER CLAIM MORE THAN WAS OBSERVED.** `failing == 0` is not "everything is live". A store where every check is DORMANT gets "0 of N confirmed live", never "All N confirmed live" — confirming the absence of evidence is the headline bug this subsystem was built to remove, and it has been reintroduced by accident more than once.
- **SESSION-SCOPED HOOKS ARE JUDGED AGAINST THE LAST SESSION, NOT THE CLOCK.** "Days since last fire" measures how recently the OPERATOR WORKED, not whether the hook works. The comparison uses the SECOND-newest settled session (`LIMIT 1 OFFSET 1`), because the newest one is the session currently asking. NOTE THE SET IS NO LONGER JUST SESSION-BOUNDARY HOOKS: techne#479 brought `post_tool_use` and `user_prompt_submit` under this branch, which fire per tool call and per prompt. The rule still holds for them — an idle operator must not look like a dead rail — and it has a consequence worth knowing: because this branch is tested BEFORE `temporal_verdict`, the per-hook interval is only reachable on a store with fewer than two settled sessions. A five-day-old marker on a 3-session store reads LIVE under an 18h window.
- **A MARKER IS STAMPED AT COMPLETION, NOT AT ENTRY.** `last_run` written from the hook's start time can read older than the session it just registered, which renders STALE on a working hook. (One deliberate exception, commented at the site: the session-registration failure path, where a recorded `hook_error` short-circuits to BROKEN before the comparison is reached.)
- **_NEW_STORE_GRACE (7d).** Under it, "nothing has happened yet" is DORMANT. Past it, the same absence IS the finding and escalates to UNOBSERVABLE. Tests that want the failing branch must age the store past the grace; tests that want the dormant branch must stay inside it. NOT UNIVERSAL: the grace is only reached when the rail should otherwise be emitting. An outbox lane with no live consumer (`sync.adapter=noop` / no registered sink) is DORMANT at ANY store age — correctly idle, checked before the age question is asked.
- **LIVENESS AND DRIFT ARE COUNTED SEPARATELY.** `_render_liveness` returns `(liveness_failures, drift_failures)`. Adding them made one run print "Nothing failing, but 0 of 12 subsystems confirmed live" and "5 subsystem(s) not confirmed working" seven lines apart.
- **DRIFT IS CLAUDE-CODE ONLY.** `check_hook_drift` does NOT self-guard — every caller must gate on `config.platform != CLAUDE_CODE` itself. Off that platform there is no settings.json mechanism to drift from.
- **A REMEDY IS BUILT, NEVER SPELLED.** `init_remedy(config)` is the single builder: `None` off claude-code, and `--posture` always interpolated from `config.posture.mode`. A hardcoded `--posture observe` DEMOTES a spool-primary operator who follows it.
- **A CHECK THAT RAISES BECOMES UNKNOWN CARRYING THE EXCEPTION — NEVER AN ABSENT RESULT.** An absent check reads as "nothing wrong", which is the failure mode this module exists to prevent. Same rule on the banner (`checks_error` is rendered, not swallowed) and in doctor's drift block.
- **"CHECKS MUST BE CHEAP" IS ENFORCED BY `@expensive` + `run_checks(cheap_only=True)`, NOT BY THE COMMENT SAYING SO.** `collect_health` runs inside SessionStart under `hooks.timeout_s`, and that path is FAIL-OPEN: one overrun drops the entire banner silently, taking every cheap check with it. #487 shipped a check spawning six git subprocesses whose docstring asserted twice that it stayed out of the banner, while `collect_health` ran the whole registry unfiltered. The marker is the only reason that assertion is now true. `doctor` still runs everything. This is the ONE place the module deliberately omits a check, and the omission is bounded and stated rather than silent.
- **A CHECK MUST COUNT THE POPULATION ITS REMEDY ACTS ON — OR IT CAN NEVER GO GREEN.** `vectors:coverage` took its denominator from ALL knowledge while `backfill_vectors` embeds only `superseded_by IS NULL` (and PURGES superseded embeddings, techne#168). The two counts spanned different populations, so every superseded row reported as permanently "missing" — 16 of 786 on the live store, STALE forever, offering a remedy that provably embedded nothing (measured: a second consecutive backfill returned `knowledge: 0`, warning unchanged). It grew MONOTONICALLY, since superseding is normal operation. A check that can never go green trains the operator to ignore it — the same harm as a false green, reached from the other side, and this check was ADDED to fix a false green (a staleness predicate calling every row fresh while 177 had no vector). Prefer a narrower question you can answer honestly to a broader one you cannot. TELL: a `max(x - y, 0)` clamp on a coverage count is a SMELL — if the two counts were the same population the clamp could never fire, so its presence means they are NOT. (CORRECTED in #497 review: the clamp was not vestigial and was not "hiding the bug". It FIRED, in a reachable state that has nothing to do with supersede — hard-deleting an embedded row leaves the raw vec count EXCEEDING the knowledge count, measured at `total - embedded = -2`, and the clamp rendered those dangling vectors as a clean 0. It was guarding, badly. Read the smell as "these counts are different populations", not as "this guard is dead".)
  COUNT EVERY PART OF THE POPULATION, NOT MOST OF IT. `backfill_vectors` acts on `(NOT in vec OR vec_stale = 1) AND superseded_by IS NULL`. The first cut of the fix scoped the denominator correctly and then counted two of that population's three parts, leaving `vec_stale = 1` — set on ANY in-place content edit — checked by nothing in this module. That produced the MIRROR-IMAGE false green: 100%, remedy None, while a backfill had real work to do. Scoping the population is half the job; enumerating its conditions is the other half.
  COROLLARY: narrowing a count can HIDE what it excludes. A row superseded AFTER being embedded keeps a live ANN vector, and nothing auto-runs backfill in production. Orphans and stale rows are therefore counted SEPARATELY and fail the check — legitimate because the same remedy genuinely fixes each.
  **BUT REPORT-WITHOUT-FAILING IS THE RIGHT ANSWER WHEN NO REMEDY EXISTS, and the distinction is not a nicety.** A vec rowid whose knowledge row was HARD-DELETED is a real defect, but the purge selects `FROM knowledge`, so a rowid with no row behind it is never matched — verified: purge removed 0 of 2. Failing on it would attach `techne vectors backfill` to a finding that command cannot clear, i.e. rebuild the never-green defect inside its own fix. It is surfaced in the detail and evidence and left out of the verdict. THE RULE: a condition you can detect but not remedy belongs in the DETAIL, never in the VERDICT — visible without being unclearable. (Owning issue for the fix itself: techne#408.)
  KNOW WHICH SURFACE "THE DETAIL" MEANS: `techne doctor`, NOT the SessionStart banner. `format_banner` is warnings-only and emits nothing for a LIVE check, so a detail-only finding is invisible to an operator who never runs doctor — verified, not assumed (#497 review, nit 2). That is uniform treatment of every LIVE check rather than concealment of this one, but the rule above is only as strong as the surface it names, and this is the surface. A finding that must reach someone who only sees the banner cannot use this pattern.
  ALL FOUR ALTERNATIVES WERE CONSIDERED AND ARE WORSE, recorded so the question is not re-litigated: STALE with `remedy=None` is a permanent red with nothing to try (#496's harm, minus the false comfort); UNKNOWN/UNOBSERVABLE both claim we could NOT observe when we counted it exactly, breaking the honesty invariant in the other direction AND still failing; DORMANT falsely claims the channel is idle and would suppress the real coverage report on the same row; and a separate `vectors:dangling` check relocates the dilemma without resolving it — whatever verdict it carries is either an unclearable red or exactly this, with more surface area.
- **THE SAME SILHOUETTE, THREE TIMES: A STATE THE CHECK CANNOT VOUCH FOR, RENDERED AS ONE IT CAN.** #473 (a runtime nobody could name reading as deployed), #370/#486 (an un-self-healed MCP entry rendering identically to a healed one), and #487's own first cut (a working checkout behind main reporting green with no distance; a failed `rev-list` returning LIVE). The taxonomy already carries the right answer each time — `UNKNOWN` for a failed probe, an ENRICHED DORMANT DETAIL for a state that is healthy-but-not-what-you-asked-about. Reach for those before reaching for a new verdict.

FAIL-MODES:
- A marker rail is only as live as its DEPLOYED code: markers stop being written entirely if the runtime is pinned to a revision without the `record_hook_run` calls. Merged is not deployed.
- Tests that invoke `doctor`/`collect_health` without pinning `Config.load` read `TECHNE_HOME` first and grade the DEVELOPER'S REAL STORE, not their fixture — assert the fixture's db path appears in the output.
- Registration drift and liveness are blind to each other by design: drift compares by `(event, matcher)` presence only, so a hook registered under the WRONG INTERPRETER is caught by neither. Known, open gap.
