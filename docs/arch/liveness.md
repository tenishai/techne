# liveness — subsystem health checks (techne#468/#469)

WHAT: answers "did each rail actually RUN?", as distinct from "is the store internally consistent?" (storage checks) and "is it even WIRED?" (hook-registration drift). Born from 2026-08-02/03, when six built-but-never-wired rails were found cold — `reflect` for four weeks — under a `techne doctor` printing "All checks passed", because doctor only looked at duplicate rows and reclaimable space.
SEAM: a registry (`register_check` / `registered_checks` / `run_checks`) of `CheckFn(config) -> CheckResult | list[CheckResult]`, plus the marker-writing side in `techne/hooks/_liveness.py` (`record_hook_run`, one `hook:<name>:last_run` / `:last_error` row per hook in `extension_state`).
VERDICTS (`Verdict`): live · dormant · stale · unobservable · broken · unknown. DECLARATION ORDER IS NOT SEVERITY ORDER — `worst()` ranks by `_SEVERITY`, where DORMANT TIES WITH LIVE (deliberate dormancy is healthy) and UNKNOWN sits BETWEEN them and STALE, not last: a probe that could not run must outrank a healthy rail, but loses the headline to a rail that ran and reported trouble. `CheckResult.ok` is true for live and dormant ONLY.
`runtime:revision` (techne#473) asks WHICH REVISION is running — a merged fix is not a deployed fix, and on 2026-08-03 a machine ran a known-crashing build for hours after the fix merged because the interpreter pointed at a shared working tree. Compares HEAD against the LOCAL origin/main ref and never fetches: a health check that hits the network fails on a plane. ONLY `main` COUNTS AS A DEPLOYMENT (CI and dev worktrees are working checkouts, and a red they can never clear is noise) — but a working checkout still STATES how far behind it is, because "on a peer's branch, behind the merge" IS the #473 incident and reporting it green without a number reproduced the bug inside its own fix.
CHECKS: per-hook liveness, the self-maintenance rails, outbox lanes, vector coverage, `schema:<store>` (techne#676 — see the invariant below), `runtime:loaded` (techne#491 — see the invariant below), `config:trust` (subsystem `security` — is the file that SELECTS egress writable by the agent it constrains? techne#393 → docs/arch/config-trust.md), `custodian` (techne#555 — `rail:<name>:bound`, one per emit→ingest rail plus `reflect`), `cards:pending` (techne#824 — a librarian card carrying a stand-in gist RIDES RECALL, so a backlog is a recall-quality defect, not housekeeping; the verdict keys on AGE not COUNT because a card is pending for the whole normal gap between indexing and the fill pass, and it comes from `temporal_verdict` rather than a local comparison so that an UNREADABLE timestamp reports UNOBSERVABLE instead of the healthy verdict — a backlog whose age cannot be read is not a green store), and `mcp:registration` — the last of which asks a different question from the rest. The MCP server is launched by the HOST, so there is no marker to read; what is checkable is whether the RECORDED launch command still resolves (techne#370). Kind.FRESHNESS: a source moved and its mirror did not.
CONSUMERS: `techne doctor` (`cli.py:_render_liveness`) and the SessionStart banner (`core/health.py` — `checks_worst` / `checks_summary` / `checks_error`). NOT `techne status`, which renders hook-registration DRIFT only and no liveness at all.

INVARIANTS — the ones a diff will not show you:

- **A VERSION CHECK MUST KNOW WHICH MECHANISM EACH STORE USES, OR IT CRIES WOLF ON THREE HEALTHY STORES (techne#676).** `check_schema_versions` compares each store's schema stamp to the constant that migrates it. There is no single way to read that stamp: `VersionIO` was made pluggable by techne#136 so core keeps its audited `schema_version` TABLE while domain stores use the zero-ceremony `PRAGMA user_version`. Reading the pragma on `techne.db` / `archivist.db` returns **0 — the field is UNUSED, not stale** — while their real stamps read 24 and match; `librarian.db` is migrated by `SqliteStore.migrate` (executescript, additive, no ladder) and has no stamp to compare at all. A check that asked the pragma uniformly would report three false problems on a healthy machine and be trained into noise within a week. `_VERSION_REGISTRY` is the one place that mapping is written down, and `test_registry_constants_all_resolve` fails if a renamed constant would silently read as 0 — which would turn every store into a false "ahead". **BEHIND IS LIVE, NOT A FAULT**: a store below its code is the ladder waiting to run. Only AHEAD is a finding, because no step above the code's version has ever existed, so the stamp cannot describe the store's real shape. THE INCIDENT: `guarded_migrate` folded `current > target` into `current >= target` and returned silently; `architect.db` sat at v4 against a code constant of 3 for at least six days, skipping every migration, and surfaced only when a migration written against it passed 3,001 tests and did nothing.
- **UNOBSERVABLE IS A FAILING STATE, NOT A WARNING.** A rail that cannot report is unfinished. "It might be fine" must never render as passing; that ambiguity is the whole reason this subsystem exists. (techne#468, Richard: "i want to know that when i run something it works, or it doesnt.")
- **CHECKS REPORT, THEY NEVER SELF-HEAL.** Print the remedy command; do not run it.
- **A DORMANT THAT CARRIES A REMEDY IS "OFF, BUT NOT BY CHOICE".** DORMANT is documented as off-by-configuration and must name the key that disabled it — so a channel the operator deliberately turned ON, which is simply broken, does not fit and must not be reported as healthy silence. `vectors:coverage` is the case: after techne#708 `search_vec` degrades to FTS rather than hanging, and `backfill_vectors` is the only call left that may download, so an install with the extra present and the weights absent is permanently FTS-only while the doctor says "not initialised" and names no key. The verdict STAYS DORMANT (it still ties with LIVE, and a broken-verdict here would fail every fresh install before its first backfill) but the detail names the state and `remedy` gives the operator the command. THE PROBE MUST NOT BUILD THE BACKEND: techne#361 pins that this path never constructs the model, so `embeddings.model_cached()` answers from the filesystem and returns None — not False — when it cannot tell. (Prudence, #728 review.)
- **NEVER CLAIM MORE THAN WAS OBSERVED.** `failing == 0` is not "everything is live". A store where every check is DORMANT gets "0 of N confirmed live", never "All N confirmed live" — confirming the absence of evidence is the headline bug this subsystem was built to remove, and it has been reintroduced by accident more than once.
- **SESSION-SCOPED HOOKS ARE JUDGED AGAINST THE LAST SESSION, NOT THE CLOCK.** "Days since last fire" measures how recently the OPERATOR WORKED, not whether the hook works. The comparison uses the SECOND-newest settled session (`LIMIT 1 OFFSET 1`), because the newest one is the session currently asking. NOTE THE SET IS NO LONGER JUST SESSION-BOUNDARY HOOKS: techne#479 brought `post_tool_use` and `user_prompt_submit` under this branch, which fire per tool call and per prompt. The rule still holds for them — an idle operator must not look like a dead rail — and it has a consequence worth knowing: because this branch is tested BEFORE `temporal_verdict`, the per-hook interval is only reachable on a store with fewer than two settled sessions. A five-day-old marker on a 3-session store reads LIVE under an 18h window.
- **A MARKER IS STAMPED AT COMPLETION, NOT AT ENTRY.** `last_run` written from the hook's start time can read older than the session it just registered, which renders STALE on a working hook. (One deliberate exception, commented at the site: the session-registration failure path, where a recorded `hook_error` short-circuits to BROKEN before the comparison is reached.)
- **_NEW_STORE_GRACE (7d).** Under it, "nothing has happened yet" is DORMANT. Past it, the same absence IS the finding and escalates to UNOBSERVABLE. Tests that want the failing branch must age the store past the grace; tests that want the dormant branch must stay inside it. NOT UNIVERSAL: the grace is only reached when the rail should otherwise be emitting. An outbox lane with no live consumer (`sync.adapter=noop` / no registered sink) is DORMANT at ANY store age — correctly idle, checked before the age question is asked.
- **LIVENESS AND DRIFT ARE COUNTED SEPARATELY.** `_render_liveness` returns `(liveness_failures, drift_failures)`. Adding them made one run print "Nothing failing, but 0 of 12 subsystems confirmed live" and "5 subsystem(s) not confirmed working" seven lines apart.
- **A CHECK KEYED ON OUTPUT-EXISTS CANNOT SEE WHICH PRODUCER WROTE IT (techne#555).** `check_maintenance_rails` keys on `knowledge_candidates.origin` — the rail's OUTPUT — which is right for what it asks. But TWO producers write that column: the resident emit→ingest route (`model_used='agent-assisted'`) and the model-bound automatic route (`model_used=<model id>`). MEASURED 2026-08-21: `rail:reflect` read LIVE off 420 all-time candidates while the automatic rail had produced **zero, ever**, since 2026-06-20 — every one of those 420 came from the resident route, and the automatic pass had been raising `AuthenticationError` on every session for two months. The subsystem built to stop "an absent result is indistinguishable from a working one" contained that exact hole, because the check measured the right table for the wrong question. `check_model_bound_rails` FAILS CLOSED on an outcome it does not recognise (techne#555/#709 — the first cut mapped everything that was not literally `error`/`partial` to LIVE, including a missing or garbled one, which is fail-OPEN in the check whose whole job is catching silent nothing), and closes the original gap by reading the RUN MARKER (`rail:<name>:last_run`) rather than the output. THAT FAIL-CLOSED GUARANTEE IS SCOPED TO A BOUND RAIL (techne#735): `_rail_binding` is asked first, and an unbound rail reads DORMANT for every outcome including an unrecognised one. #709's guarantee is unchanged where it applies — it just no longer applies to a rail that cannot run. THE GENERAL STATEMENT (poe2, 2026-08-21, sharpening this card's first draft): `origin` records THAT a row exists, `model_used` records WHO WROTE IT, and a check keyed on existence cannot distinguish two producers writing one table. Same defect class as techne#704 (a claim true of the repo, false of the deployment) and techne#706 (a suite green on fixtures that never touch the real thing) — IN ALL THREE, THE SIGNAL WAS MEASURED ON A PROXY THAT A SECOND PRODUCER OR A SECOND ENVIRONMENT COULD SATISFY WITHOUT THE THING BEING TRUE. AUDITED 2026-08-21: consolidate (9) and dream (15) are single-producer TODAY and so do not have the bug — but only because they had no automatic runner at all, which is the gap techne#555 closes. Binding a model to them CREATES the second producer, which is why the marker check ships WITH the feature rather than after it.
- **A MARKER IS A RECORD OF A PAST CONFIGURATION, NOT A STATEMENT ABOUT NOW (techne#735).** `check_model_bound_rails` reads `rail:<name>:last_run` and derived its verdict from the OUTCOME alone. But a marker describes a run that happened under a binding that may no longer exist, so a rail switched off kept reporting its last healthy run **forever**. #732 fixed one half at WRITE time — the unbound reflect path retracts its marker — and a write-time retraction is structurally unable to cover the rest: `lifecycle.py` gates the reflect call site on `reflect.enabled`, so when the feature is OFF `reflect_on_session` is never invoked and no code path can clear the marker; `clear_rail_marker` exists but reflect is its ONLY caller, so all five custodian rails keep theirs permanently; and even the fixed path lies in the window between an operator editing the config and the next session end. MEASURED before the fix, one `outcome="ok"` marker: reflect enabled+bound → LIVE (correct), reflect `enabled=false` → **LIVE**, reflect enabled but unbound → **LIVE**, dream with an unbound custodian → **LIVE**. THE DIRECTION IS WHY IT IS IMPORTANT RATHER THAN A NIT: unbound + stale `error` reads BROKEN — noisy, wrong, self-announcing, so someone fixes it; disabled + stale `ok` reads LIVE — silent, wrong, comfortable. Green-while-dead, in the subsystem that exists to stop a diagnostic lying in exactly that direction. THE FIX IS ONE RULE RATHER THAN THREE PATCHES (Prudence's generalisation, #732 retro): **no verdict is derived from a marker without first asking whether the rail is currently bound** (`_rail_binding`). An unbound rail reads DORMANT and its payload is KEPT AND SHOWN in the detail, which is what #732 was protecting. THE DOWNGRADE APPLIES TO `error`/`partial` TOO, DELIBERATELY: reading BROKEN off a stale payload is wrong the same way as reading LIVE — both derive a claim about now from a configuration that is gone. BROKEN is merely wrong in the SAFE direction, which is exactly what would let it survive unexamined. Pinned by `test_an_unbound_rail_with_an_error_marker_reads_dormant_not_broken`. AND IT IS A CHECK WHOSE ANSWER DEPENDS ON `config`, WHICH THIS CARD WARNS ABOUT — accepted, for a reason worth recording rather than re-deriving. The invariant below says a check whose answer depends on how its input was CONSTRUCTED is measuring its caller. The distinction: "is this rail bound" is a question ABOUT the config, where `config:trust`'s question was about the filesystem. All four production callers pass a loaded `Config`, and `check_maintenance_rails` already reads `config.reflect.enabled`, so this is precedent rather than new surface. (Prudence, #743 r1 suggestion.) AND `_rail_binding` ASKS *WHETHER* A RAIL IS BOUND, NOT *BOUND TO WHAT* — the marker cannot answer the second question because `record_rail_marker` does not record a model (payload keys are `detail`, `outcome`, `ts`). So a rail re-pointed at a different model, with no run since, reports LIVE off the PREVIOUS model's run. MEASURED: ran under `ollama/model-A` with `outcome='ok'`, switch `custodian.model` to model-B, still LIVE with `ok=True`. That is this very invariant surviving on the model axis, and the irony is worth the sentence — `custodian.md` makes `model_used` a REQUIRED kwarg with no default precisely because it is the only column recording which producer judged a candidate. The candidate row names its producer; the marker that vouches for the rail does not. NOT A REGRESSION (it reads LIVE identically before techne#735) and the fix is a marker-format change, so it is filed rather than done here. Named so this paragraph is not read as closing the class. (Prudence, #743 r2.) The shape has a precedent on this card: see the ENRICHED DORMANT DETAIL note below, for a state that is healthy-but-not-what-you-asked-about.

DELIBERATE BOUNDARY: `custodian.rails` is not consulted — it selects what the SCHEDULED runner drives and an excluded rail can still be run with `--rail`, so exclusion is a scheduling choice, not an absent binding.
- **DRIFT IS CLAUDE-CODE ONLY.** `check_hook_drift` does NOT self-guard — every caller must gate on `config.platform != CLAUDE_CODE` itself. Off that platform there is no settings.json mechanism to drift from.
- **A REMEDY MUST NAME A COMMAND THAT EXISTS, AND A NAME-DERIVED REMEDY CANNOT PROMISE THAT (techne#936).** `check_maintenance_rails` built every stale rail's remedy as `f"techne {rail} --help"`, and only ONE of the three rail names in `_RAIL_EXPECTATIONS` is a CLI verb: `techne consolidate --help` and `techne dream --help` both answer `Error: No such command`. Measured 2026-09-15 on 30984e0, with `rail:consolidate` reading stale and printing that remedy. This is the sibling of the invariant above — the same spelled-vs-built distinction, failing from the other direction: the string was DERIVED rather than hardcoded, and derivation is what made it wrong, because the rail NAME and the COMMAND THAT DRAINS IT are different facts. `consolidate` and `dream` have no verb of their own; they run through `custodian run --rail <name>` (bound model) or the MCP emit/ingest pair, neither guessable from `No such command`. `_RAIL_EXPECTATIONS` now carries a third field and the remedy is read from it.
  WHY THIS IS WORSE THAN A MISSING REMEDY: the remedy line is the one part of a check an operator acts on WITHOUT reading the code, and it fires at the exact moment the check went stale — so a dead end there spends the operator's attention precisely when the subsystem needed it. `remedy=None` would have sent them to the docs; a wrong command sends them nowhere and looks authoritative doing it.
  TEST-ENFORCED, AND THE SCOPE OF THAT ENFORCEMENT IS NARROWER THAN AN EARLIER DRAFT OF THIS LINE CLAIMED. `test_rail_remedy_resolves_to_a_real_command` parses the leading `techne a b c` out of every remedy in `_RAIL_EXPECTATIONS` and resolves it against the real Click tree -- 3 of roughly 10 remedy literals in this module. `test_every_remedy_a_real_run_emits_resolves` widens it to whatever a real `run_checks` pass emits on the running machine. A remedy on a branch that environment never takes is STILL UNGUARDED; that is a known gap, not a covered one, and saying so is the difference between a guard and a reassurance.
- **A BANNER CHECK MUST BE CHEAP, BUT "CHEAP" IS A PROPERTY OF THE IMPLEMENTATION, NOT OF THE QUESTION (techne#937).** `codex:freshness` and `cards:freshness` both answer questions whose OBVIOUS implementation is `@expensive` — re-hash every file, or shell out to git — and `@expensive` means `collect_health(cheap_only=True)` skips them, so the obvious version lands in `doctor` only and the banner stays silent, which is the thing being asked for rather than delivered. Both were made cheap instead of being deferred.
  `cards:freshness` IS AUTHORITATIVE AND COSTS 0.006s. A git blob sha is a formula, not a git feature — `sha1(b"blob %d\0" % len(data) + data)` — 19 anchors hashed with ZERO subprocesses, against 21 subprocesses and 0.50s for the shell-out. techne#937 proposed comparing STAT TIMES on the assumption the real comparison was unaffordable. It is not.
  THE EQUIVALENCE IS CONDITIONAL AND AN EARLIER DRAFT STATED IT FLAT. `git hash-object <path>` runs CLEAN FILTERS; the formula hashes raw bytes, so they agree only where no eol filter applies. Measured: with `core.autocrlf=true` (the Windows default) or `* text=auto` in `.gitattributes`, a CRLF working file hashes differently and EVERY anchor reads STALE. This repo sets neither, so it holds here — a property of the checkout, not of the formula. The exact claim is: identical to `git hash-object --no-filters` always, and to plain `git hash-object` wherever no eol filter applies.
  IT RESOLVES THE CHECKOUT, NOT THE PRIMARY, and that was a real bug. `primary_repo_root` maps a linked worktree to its parent — correct for CODEX, which is indexed against the primary by design, and WRONG for cards, which live in the checkout being edited. Worktree-per-session is the standing dev topology, so with the primary resolver a session that edited a seam without bumping its card read LIVE, because the primary's cards were compared against the primary's seams. `find_repo_root` is the right resolver here; the two are not interchangeable just because both answer "which repo".
  IT GLOBS WHAT THE GATE GLOBS, AND THAT WAS A THIRD INSTANCE OF THE SAME CLASS. The check read only `docs/arch/*.md` while `scripts/check_arch_cards.py` reads `("ARCHITECTURE.md", "docs/arch/*.md")`, so ARCHITECTURE.md's one anchor -- `pyproject.toml` -- was unguarded here. Drifting it put the GATE RED and the BANNER LIVE at the same instant on the same drift, and the banner reported a confident "19 anchor(s)" no operator could read as 19 of the 20 the gate guards. The globs are MIRRORED rather than imported (scripts/ is not a package and is absent from an installed build), and `test_banner_and_gate_cover_the_same_anchors` compares the two counts on the real repo -- so a third card location fails a test instead of going silently unguarded.
  A MISSING SEAM IS A FINDING, NOT A SKIP. The pre-push gate calls it a hard failure; the check silently `continue`d past it, so a card vouching for a renamed or deleted file read LIVE in the banner while the gate was red.
  THE MTIME VERSION WAS BUILT FIRST AND MEASURED, WHICH IS WHY THE FORMULA IS WORTH THE LINE. It reported 12 of 19 anchors stale while the sha gate said all 19 were fresh, because `git checkout` rewrites mtimes and every branch switch manufactures a full set of false positives. The issue argued mtime "over-warns, never under-warns" and called that the right trade for a banner hint. OVER-WARNING IS THE RIGHT DIRECTION ONLY WHILE THE RATE STAYS READABLE: 12 of 19 is the "trains you to ignore it" failure this card names elsewhere, and a check nobody reads is worth less than no check.
  `codex:freshness` KEYS ON indexed_head, NOT AGE, AND THAT IS AN HONESTY POINT AS WELL AS A COST ONE. A fixed age threshold is crude — a repo nobody touched for a month is not stale, one touched twice this morning may be. "Indexed before the current HEAD" is the honest predicate, and recording `indexed_head` at index time makes asking it one ref read. The age is reported beside it because that is what an operator reads; it does not decide the verdict. It reports UNOBSERVABLE, never LIVE, when `indexed_head` is absent (an index written before #937) or HEAD is unreadable — a comparison that cannot be made is not a pass, the same rule `cards:pending` follows for an unreadable timestamp.
  THE PRE-PUSH SCRIPT KEEPS A STRICTER CONTRACT THAN THE CHECK. `scripts/check_arch_cards.py` treats a MALFORMED anchor as a hard failure, deliberately, so a typo'd sha cannot leave a seam unguarded. The banner check SKIPS what it cannot parse, because a banner that fails to render is worse than a banner missing one line. Two surfaces, two right answers.
- **A REMEDY IS BUILT, NEVER SPELLED.** `init_remedy(config)` is the single builder: `None` off claude-code, and `--posture` interpolated from `config.posture.mode`. A hardcoded `--posture observe` DEMOTES a spool-primary operator who follows it.
  **THIS CLAIM WAS FALSE FOR AS LONG AS IT HAS BEEN WRITTEN HERE, AND IS NOW TEST-ENFORCED (techne#480).** `techne status` (`cli.py`) and the session-start drift banner each interpolated `config.posture.mode` by hand, inheriting neither guard — so on a machine with a store but no `config.yaml` (an MCP server wired up without ever running `techne init`; `init_session` creates the DB) `doctor` said `--posture auto` and `status` said `--posture observe`, on the same machine, in opposite directions. All four sites now route through the builder, and `test_init_remedy_is_the_only_place_the_init_hint_is_spelled` scans every module under `techne/` except `core/checks.py` for a hand-spelled hint — BOTH the interpolated `--posture {` and the literal `techne init --posture` — and fails if one reappears. Two tells, not one, because they come apart exactly at the hardcoded form this bullet names as the hazard: a guard that only catches interpolation tests the mechanism, not the invariant. A card assertion that only a reader can check is a claim; one a test can fail is an invariant.
  **BUT A GUARD APPLIED WHERE THERE IS NOTHING TO GUARD DOES THE HARM IT PREVENTS (techne#480).** Interpolating the current mode protects a choice the operator already MADE. On a machine that has used Claude Code but never run `techne init` there is no `config.yaml`, so `config.posture.mode` is the dataclass default `observe` — and pinning it suppresses the auto-detection that would have found `spool-primary` from the CC memory on disk, freezing a first install into the weakest posture. With no file, `--posture auto` IS the honest value. THE DISCRIMINATOR IS `config.loaded_from`, set only by `Config.load()` and never serialized: it answers "did these values come from a file?", which is a different question from "what is this value?". Deliberately NOT a fresh `stat()` inside the builder — `Config.load(path=...)` can read a config that is not `techne_home()/config.yaml`, and a second, independent filesystem question is free to disagree with the one that actually produced the values in hand.
  THE SHAPE, worth recognising elsewhere: this was not a wrong guard, it was a RIGHT guard with an unstated precondition. "Never pin a literal" silently assumed a value worth preserving existed. A guard whose justification names a state ("the operator's choice") should test for that state, not for the attribute that usually carries it.
- **A CHECK THAT RAISES BECOMES UNKNOWN CARRYING THE EXCEPTION — NEVER AN ABSENT RESULT.** An absent check reads as "nothing wrong", which is the failure mode this module exists to prevent. Same rule on the banner (`checks_error` is rendered, not swallowed) and in doctor's drift block.
THE WAY PAST `@expensive` IS TO MAKE THE SIGNAL CHEAP, NOT TO REACH AROUND THE MARKER (techne#696). PR #697 wanted the runtime-staleness signal in the banner and called `check_runtime_loaded` — `@expensive` — directly from the SessionStart hook, leaving the marker set. The result was incoherent as well as costly: `deferred_check_names()` still listed the check, so the banner announced it as deferred and printed its output four lines later. It was withdrawn, and the correct reading of the marker is that it is the design telling you where the signal must come from. `check_runtime_loaded` is expensive because it interrogates OTHER processes (`ps`, plus git on the non-reflog branch); the fix was to have the process that already knows answer for itself. An MCP server compares its own `sys.modules` against a baseline taken at startup and PUBLISHES the verdict to `<techne_home>/runtime-state/<pid>.json`; `check_runtime_torn` then reads it with a directory listing, one `open()` each, and `os.kill(pid, 0)` to reap the dead — no subprocess, so it registers as an ordinary check and reaches the banner through `collect_health`'s existing `run_checks(cheap_only=True)` call with no bespoke banner code at all. WHEN A CHECK MUST BE `@expensive`, ASK WHETHER SOMETHING ELSE ALREADY HAS THE ANSWER FOR FREE. Note also `runtime:torn` is strictly sharper than the `runtime:loaded` it sits beside: that one compares process start against deploy time and says of itself it is "ordering only… not a tear detector", while this one names the modules.

A DECORATOR-STACK HAZARD, PAID FOR ONCE (techne#696): `check_runtime_loaded` carries `@register_check` ABOVE `@expensive`. Inserting a new check by anchoring on `@expensive\ndef check_runtime_loaded(` lands BETWEEN them — double-registering the newcomer and stripping `check_runtime_loaded`'s registration, so it stops running entirely. Anchor on the OUTERMOST decorator, and assert a registration COUNT (`names.count(...) == 1`) rather than only membership, because a superset assertion cannot notice a double-registration.

AND THE PART WORTH MORE THAN THE HAZARD: **the suite caught it, by name, and the author reported that it had not.** `tests/test_runtime_loaded.py::TestRegistration::test_the_check_is_registered` fails on exactly this — it is one line, `assert check_runtime_loaded in checks_mod.registered_checks()`, and its docstring already says why ("a check that exists but is not registered reports nothing, and an absent check reads as 'nothing wrong'"). `test_cheap_only_omits_it_and_a_full_run_includes_it` fails too. The author had run ONE test file during a mutation loop, saw green, and generalised that into "the suite stayed green" — a claim about 3,000 tests made from having run ten. Re-measured against the full suite: **4 failed**, two of them pre-existing and untouched. (The first re-measurement said THREE, because it reproduced only the *stripping* half of the accident and not the *double-registration* half. The missing fourth is `test_the_check_is_cheap_and_registered_like_any_other` — the `count(...) == 1` assertion this very paragraph argues for. A correction of an undercount that itself undercounted, in the sentence prescribing the assertion that would have caught it.) THE LESSON IS NOT ABOUT DECORATORS. Before writing "no test caught this", run the tests. A false claim that the guards are missing is worse than the bug it describes, because it survives into the next person's design decisions — this paragraph originally prescribed "assert counts rather than membership", which INVERTS the evidence: the assertion that caught it is a membership check, and both belong.

A CHECK MAY REPORT A CONFIG THAT MAKES A FEATURE MEANINGLESS, NOT ONLY ONE THAT BREAKS IT (techne#553). `check_instance_identity` fires when a non-standalone instance writes federated knowledge under an unqualified `instance_name`. The write succeeds and the row lands — what degrades is the ATTRIBUTION, to something that cannot discriminate, which is why its kind is `FAIL_OPEN` rather than a fifth kind invented to fit it (an earlier draft added `Kind.CONFIG`; the four kinds came out of the 2026-08-03 audit and adding one per check is how a taxonomy stops meaning anything). The collision it prevents is GUARANTEED rather than likely: cabal's `identity.toml.example`, which every new cabal starts from, ships `archivist`, `architect`, `librarian`, `mason` and `wright`, so three operators federating into one store contribute three different agents all named `archivist` — and `archivist` is the persona that writes there. It stays DORMANT unless the archivist is bound to a STORE (techne#552 — it keyed on `config.standalone`, which DEFAULTS TO TRUE, so an operator adopting `archivist: store` got DORMANT "attributes nothing" while writing into a shared store under an empty instance_name: a false GREEN on precisely the config the guard exists for). A local-bound instance attributes nothing and has nothing to collide with; a check that fires where there is no problem is how a true signal is trained into noise (#562).
