# liveness — subsystem health checks (techne#468/#469)

WHAT: answers "did each rail actually RUN?", as distinct from "is the store internally consistent?" (storage checks) and "is it even WIRED?" (hook-registration drift). Born from 2026-08-02/03, when six built-but-never-wired rails were found cold — `reflect` for four weeks — under a `techne doctor` printing "All checks passed", because doctor only looked at duplicate rows and reclaimable space.
SEAM: a registry (`register_check` / `registered_checks` / `run_checks`) of `CheckFn(config) -> CheckResult | list[CheckResult]`, plus the marker-writing side in `techne/hooks/_liveness.py` (`record_hook_run`, one `hook:<name>:last_run` / `:last_error` row per hook in `extension_state`).
VERDICTS (`Verdict`): live · dormant · stale · unobservable · broken · unknown. DECLARATION ORDER IS NOT SEVERITY ORDER — `worst()` ranks by `_SEVERITY`, where DORMANT TIES WITH LIVE (deliberate dormancy is healthy) and UNKNOWN sits BETWEEN them and STALE, not last: a probe that could not run must outrank a healthy rail, but loses the headline to a rail that ran and reported trouble. `CheckResult.ok` is true for live and dormant ONLY.
`runtime:revision` (techne#473) asks WHICH REVISION is running — a merged fix is not a deployed fix, and on 2026-08-03 a machine ran a known-crashing build for hours after the fix merged because the interpreter pointed at a shared working tree. Compares HEAD against the LOCAL origin/main ref and never fetches: a health check that hits the network fails on a plane. ONLY `main` COUNTS AS A DEPLOYMENT (CI and dev worktrees are working checkouts, and a red they can never clear is noise) — but a working checkout still STATES how far behind it is, because "on a peer's branch, behind the merge" IS the #473 incident and reporting it green without a number reproduced the bug inside its own fix.
CHECKS: per-hook liveness, the self-maintenance rails, outbox lanes, vector coverage, `schema:<store>` (techne#676 — see the invariant below), `runtime:loaded` (techne#491 — see the invariant below), `config:trust` (subsystem `security` — is the file that SELECTS egress writable by the agent it constrains? techne#393 → docs/arch/config-trust.md), and `mcp:registration` — the last of which asks a different question from the rest. The MCP server is launched by the HOST, so there is no marker to read; what is checkable is whether the RECORDED launch command still resolves (techne#370). Kind.FRESHNESS: a source moved and its mirror did not.
CONSUMERS: `techne doctor` (`cli.py:_render_liveness`) and the SessionStart banner (`core/health.py` — `checks_worst` / `checks_summary` / `checks_error`). NOT `techne status`, which renders hook-registration DRIFT only and no liveness at all.

INVARIANTS — the ones a diff will not show you:

- **A VERSION CHECK MUST KNOW WHICH MECHANISM EACH STORE USES, OR IT CRIES WOLF ON THREE HEALTHY STORES (techne#676).** `check_schema_versions` compares each store's schema stamp to the constant that migrates it. There is no single way to read that stamp: `VersionIO` was made pluggable by techne#136 so core keeps its audited `schema_version` TABLE while domain stores use the zero-ceremony `PRAGMA user_version`. Reading the pragma on `techne.db` / `archivist.db` returns **0 — the field is UNUSED, not stale** — while their real stamps read 24 and match; `librarian.db` is migrated by `SqliteStore.migrate` (executescript, additive, no ladder) and has no stamp to compare at all. A check that asked the pragma uniformly would report three false problems on a healthy machine and be trained into noise within a week. `_VERSION_REGISTRY` is the one place that mapping is written down, and `test_registry_constants_all_resolve` fails if a renamed constant would silently read as 0 — which would turn every store into a false "ahead". **BEHIND IS LIVE, NOT A FAULT**: a store below its code is the ladder waiting to run. Only AHEAD is a finding, because no step above the code's version has ever existed, so the stamp cannot describe the store's real shape. THE INCIDENT: `guarded_migrate` folded `current > target` into `current >= target` and returned silently; `architect.db` sat at v4 against a code constant of 3 for at least six days, skipping every migration, and surfaced only when a migration written against it passed 3,001 tests and did nothing.
- **UNOBSERVABLE IS A FAILING STATE, NOT A WARNING.** A rail that cannot report is unfinished. "It might be fine" must never render as passing; that ambiguity is the whole reason this subsystem exists. (techne#468, Richard: "i want to know that when i run something it works, or it doesnt.")
- **CHECKS REPORT, THEY NEVER SELF-HEAL.** Print the remedy command; do not run it.
- **NEVER CLAIM MORE THAN WAS OBSERVED.** `failing == 0` is not "everything is live". A store where every check is DORMANT gets "0 of N confirmed live", never "All N confirmed live" — confirming the absence of evidence is the headline bug this subsystem was built to remove, and it has been reintroduced by accident more than once.
- **SESSION-SCOPED HOOKS ARE JUDGED AGAINST THE LAST SESSION, NOT THE CLOCK.** "Days since last fire" measures how recently the OPERATOR WORKED, not whether the hook works. The comparison uses the SECOND-newest settled session (`LIMIT 1 OFFSET 1`), because the newest one is the session currently asking. NOTE THE SET IS NO LONGER JUST SESSION-BOUNDARY HOOKS: techne#479 brought `post_tool_use` and `user_prompt_submit` under this branch, which fire per tool call and per prompt. The rule still holds for them — an idle operator must not look like a dead rail — and it has a consequence worth knowing: because this branch is tested BEFORE `temporal_verdict`, the per-hook interval is only reachable on a store with fewer than two settled sessions. A five-day-old marker on a 3-session store reads LIVE under an 18h window.
- **A MARKER IS STAMPED AT COMPLETION, NOT AT ENTRY.** `last_run` written from the hook's start time can read older than the session it just registered, which renders STALE on a working hook. (One deliberate exception, commented at the site: the session-registration failure path, where a recorded `hook_error` short-circuits to BROKEN before the comparison is reached.)
- **_NEW_STORE_GRACE (7d).** Under it, "nothing has happened yet" is DORMANT. Past it, the same absence IS the finding and escalates to UNOBSERVABLE. Tests that want the failing branch must age the store past the grace; tests that want the dormant branch must stay inside it. NOT UNIVERSAL: the grace is only reached when the rail should otherwise be emitting. An outbox lane with no live consumer (`sync.adapter=noop` / no registered sink) is DORMANT at ANY store age — correctly idle, checked before the age question is asked.
- **LIVENESS AND DRIFT ARE COUNTED SEPARATELY.** `_render_liveness` returns `(liveness_failures, drift_failures)`. Adding them made one run print "Nothing failing, but 0 of 12 subsystems confirmed live" and "5 subsystem(s) not confirmed working" seven lines apart.
- **DRIFT IS CLAUDE-CODE ONLY.** `check_hook_drift` does NOT self-guard — every caller must gate on `config.platform != CLAUDE_CODE` itself. Off that platform there is no settings.json mechanism to drift from.
- **A REMEDY IS BUILT, NEVER SPELLED.** `init_remedy(config)` is the single builder: `None` off claude-code, and `--posture` interpolated from `config.posture.mode`. A hardcoded `--posture observe` DEMOTES a spool-primary operator who follows it.
  **THIS CLAIM WAS FALSE FOR AS LONG AS IT HAS BEEN WRITTEN HERE, AND IS NOW TEST-ENFORCED (techne#480).** `techne status` (`cli.py`) and the session-start drift banner each interpolated `config.posture.mode` by hand, inheriting neither guard — so on a machine with a store but no `config.yaml` (an MCP server wired up without ever running `techne init`; `init_session` creates the DB) `doctor` said `--posture auto` and `status` said `--posture observe`, on the same machine, in opposite directions. All four sites now route through the builder, and `test_init_remedy_is_the_only_place_the_init_hint_is_spelled` scans every module under `techne/` except `core/checks.py` for a hand-spelled hint — BOTH the interpolated `--posture {` and the literal `techne init --posture` — and fails if one reappears. Two tells, not one, because they come apart exactly at the hardcoded form this bullet names as the hazard: a guard that only catches interpolation tests the mechanism, not the invariant. A card assertion that only a reader can check is a claim; one a test can fail is an invariant.
  **BUT A GUARD APPLIED WHERE THERE IS NOTHING TO GUARD DOES THE HARM IT PREVENTS (techne#480).** Interpolating the current mode protects a choice the operator already MADE. On a machine that has used Claude Code but never run `techne init` there is no `config.yaml`, so `config.posture.mode` is the dataclass default `observe` — and pinning it suppresses the auto-detection that would have found `spool-primary` from the CC memory on disk, freezing a first install into the weakest posture. With no file, `--posture auto` IS the honest value. THE DISCRIMINATOR IS `config.loaded_from`, set only by `Config.load()` and never serialized: it answers "did these values come from a file?", which is a different question from "what is this value?". Deliberately NOT a fresh `stat()` inside the builder — `Config.load(path=...)` can read a config that is not `techne_home()/config.yaml`, and a second, independent filesystem question is free to disagree with the one that actually produced the values in hand.
  THE SHAPE, worth recognising elsewhere: this was not a wrong guard, it was a RIGHT guard with an unstated precondition. "Never pin a literal" silently assumed a value worth preserving existed. A guard whose justification names a state ("the operator's choice") should test for that state, not for the attribute that usually carries it.
- **A CHECK THAT RAISES BECOMES UNKNOWN CARRYING THE EXCEPTION — NEVER AN ABSENT RESULT.** An absent check reads as "nothing wrong", which is the failure mode this module exists to prevent. Same rule on the banner (`checks_error` is rendered, not swallowed) and in doctor's drift block.
THE WAY PAST `@expensive` IS TO MAKE THE SIGNAL CHEAP, NOT TO REACH AROUND THE MARKER (techne#696). PR #697 wanted the runtime-staleness signal in the banner and called `check_runtime_loaded` — `@expensive` — directly from the SessionStart hook, leaving the marker set. The result was incoherent as well as costly: `deferred_check_names()` still listed the check, so the banner announced it as deferred and printed its output four lines later. It was withdrawn, and the correct reading of the marker is that it is the design telling you where the signal must come from. `check_runtime_loaded` is expensive because it interrogates OTHER processes (`ps`, plus git on the non-reflog branch); the fix was to have the process that already knows answer for itself. An MCP server compares its own `sys.modules` against a baseline taken at startup and PUBLISHES the verdict to `<techne_home>/runtime-state/<pid>.json`; `check_runtime_torn` then reads it with a directory listing, one `open()` each, and `os.kill(pid, 0)` to reap the dead — no subprocess, so it registers as an ordinary check and reaches the banner through `collect_health`'s existing `run_checks(cheap_only=True)` call with no bespoke banner code at all. WHEN A CHECK MUST BE `@expensive`, ASK WHETHER SOMETHING ELSE ALREADY HAS THE ANSWER FOR FREE. Note also `runtime:torn` is strictly sharper than the `runtime:loaded` it sits beside: that one compares process start against deploy time and says of itself it is "ordering only… not a tear detector", while this one names the modules.

A DECORATOR-STACK HAZARD, PAID FOR ONCE (techne#696): `check_runtime_loaded` carries `@register_check` ABOVE `@expensive`. Inserting a new check by anchoring on `@expensive\ndef check_runtime_loaded(` lands BETWEEN them — double-registering the newcomer and stripping `check_runtime_loaded`'s registration, so it stops running entirely. Anchor on the OUTERMOST decorator, and assert a registration COUNT (`names.count(...) == 1`) rather than only membership, because a superset assertion cannot notice a double-registration.

AND THE PART WORTH MORE THAN THE HAZARD: **the suite caught it, by name, and the author reported that it had not.** `tests/test_runtime_loaded.py::TestRegistration::test_the_check_is_registered` fails on exactly this — it is one line, `assert check_runtime_loaded in checks_mod.registered_checks()`, and its docstring already says why ("a check that exists but is not registered reports nothing, and an absent check reads as 'nothing wrong'"). `test_cheap_only_omits_it_and_a_full_run_includes_it` fails too. The author had run ONE test file during a mutation loop, saw green, and generalised that into "the suite stayed green" — a claim about 3,000 tests made from having run ten. Re-measured against the full suite: **4 failed**, two of them pre-existing and untouched. (The first re-measurement said THREE, because it reproduced only the *stripping* half of the accident and not the *double-registration* half. The missing fourth is `test_the_check_is_cheap_and_registered_like_any_other` — the `count(...) == 1` assertion this very paragraph argues for. A correction of an undercount that itself undercounted, in the sentence prescribing the assertion that would have caught it.) THE LESSON IS NOT ABOUT DECORATORS. Before writing "no test caught this", run the tests. A false claim that the guards are missing is worse than the bug it describes, because it survives into the next person's design decisions — this paragraph originally prescribed "assert counts rather than membership", which INVERTS the evidence: the assertion that caught it is a membership check, and both belong.

A CHECK MAY REPORT A CONFIG THAT MAKES A FEATURE MEANINGLESS, NOT ONLY ONE THAT BREAKS IT (techne#553). `check_instance_identity` fires when a non-standalone instance writes federated knowledge under an unqualified `instance_name`. The write succeeds and the row lands — what degrades is the ATTRIBUTION, to something that cannot discriminate, which is why its kind is `FAIL_OPEN` rather than a fifth kind invented to fit it (an earlier draft added `Kind.CONFIG`; the four kinds came out of the 2026-08-03 audit and adding one per check is how a taxonomy stops meaning anything). The collision it prevents is GUARANTEED rather than likely: cabal's `identity.toml.example`, which every new cabal starts from, ships `archivist`, `architect`, `librarian`, `mason` and `wright`, so three operators federating into one store contribute three different agents all named `archivist` — and `archivist` is the persona that writes there. It stays DORMANT on a standalone install, which attributes nothing and has nothing to collide with; a check that fires where there is no problem is how a true signal is trained into noise (#562). The general rule: WHEN A FEATURE'S CORRECTNESS DEPENDS ON AN OPERATOR-SUPPLIED NAME BEING UNIQUE, A CHECK ENFORCES THAT AND A DOCSTRING DOES NOT.

- **"CHECKS MUST BE CHEAP" IS ENFORCED BY `@expensive` + `run_checks(cheap_only=True)`, NOT BY THE COMMENT SAYING SO.** `collect_health` runs inside SessionStart under `hooks.timeout_s`, and that path is FAIL-OPEN: one overrun drops the entire banner silently, taking every cheap check with it. #487 shipped a check spawning six git subprocesses whose docstring asserted twice that it stayed out of the banner, while `collect_health` ran the whole registry unfiltered. The marker is the only reason that assertion is now true. `doctor` still runs everything. This is the ONE place the module deliberately omits a check, and the omission is bounded and stated rather than silent.
  **STATED WHERE THE READER IS, NOT ONLY IN A DOCSTRING (techne#488).** "Bounded and known" was true of the SEAM and false of the SURFACE: `{'dormant': 12}` gives a reader no way to tell there was ever a thirteenth, which is this module's founding bug wearing the module's own uniform. `deferred_check_names()` reads the registry's markers — no probe, no subprocess — and `collect_health` records `checks_deferred` on EVERY path, in its own guarded block outside the main try, so the key survives both a failing `run_checks` AND a failing import of the checks module itself. `None` means "could not be determined" and is distinct from `[]` ("nothing was deferred") — an absent key would make a consumer's `.get("checks_deferred", [])` read "nothing deferred" at the exact moment every check was skipped.
  A SYNTHETIC `UNKNOWN` PLACEHOLDER IS THE WRONG FIX and is recorded here so it is not re-proposed: `health.py:checks_bad` treats anything outside (live, dormant) as bad, so a placeholder would rank through `worst()` and pin a PERMANENT ⚠️ for checks that were never run — the never-green harm this card already names under `vectors:coverage`, reached from a third direction. DEFERRED-NESS IS NOT A VERDICT. It is reported beside the verdicts, never among them.
  THE BANNER GETS A SUFFIX, NOT A ROW. No liveness row is printed when everything is healthy, deliberately — a permanent "all good" line trains the eye to skip it — so the note rides an existing warning line and the UNCONDITIONAL record is the structured key that `techne_status` and the MCP surface read. ACCEPTED LIMIT, stated precisely because the first version of this sentence understated it: the suffix rides a LIVENESS warning line, so it is absent whenever liveness itself is healthy — INCLUDING on a banner already warning about something else (a capture gap, a hook error). A reader of the earlier wording would have concluded "if I see a ⚠️ banner the note is on it", which is false. Deliberate: hanging a liveness-deferral note off an unrelated warning would be worse than omitting it. The unconditional record is the structured `checks_deferred` key. NOTE `techne doctor` does NOT read it and does not need to: doctor calls `_render_liveness` -> `run_checks(config)` UNFILTERED, so nothing is deferred on that path at all. `health.py` is the only writer and the verbatim `techne_status` MCP passthrough the only other consumer.
  NAMES ARE FUNCTION NAMES (`check_runtime_loaded`), not doctor's `subsystem:name` labels (`runtime:loaded`). The label lives on a `CheckResult`, and a deferred check has produced none — that is what deferred means. Deriving one from the other guesses at a convention nothing enforces; declaring it on the decorator creates a second copy free to drift from the check's own return value.
- **A CHECK MUST COUNT THE POPULATION ITS REMEDY ACTS ON — OR IT CAN NEVER GO GREEN.** `vectors:coverage` took its denominator from ALL knowledge while `backfill_vectors` embeds only `superseded_by IS NULL` (and PURGES superseded embeddings, techne#168). The two counts spanned different populations, so every superseded row reported as permanently "missing" — 16 of 786 on the live store, STALE forever, offering a remedy that provably embedded nothing (measured: a second consecutive backfill returned `knowledge: 0`, warning unchanged). It grew MONOTONICALLY, since superseding is normal operation. A check that can never go green trains the operator to ignore it — the same harm as a false green, reached from the other side, and this check was ADDED to fix a false green (a staleness predicate calling every row fresh while 177 had no vector). Prefer a narrower question you can answer honestly to a broader one you cannot. TELL: a `max(x - y, 0)` clamp on a coverage count is a SMELL — if the two counts were the same population the clamp could never fire, so its presence means they are NOT. (CORRECTED in #497 review: the clamp was not vestigial and was not "hiding the bug". It FIRED, in a reachable state that has nothing to do with supersede — hard-deleting an embedded row leaves the raw vec count EXCEEDING the knowledge count, measured at `total - embedded = -2`, and the clamp rendered those dangling vectors as a clean 0. It was guarding, badly. Read the smell as "these counts are different populations", not as "this guard is dead".)
  COUNT EVERY PART OF THE POPULATION, NOT MOST OF IT. `backfill_vectors` acts on `(NOT in vec OR vec_stale = 1) AND superseded_by IS NULL`. The first cut of the fix scoped the denominator correctly and then counted two of that population's three parts, leaving `vec_stale = 1` — set on ANY in-place content edit — checked by nothing in this module. That produced the MIRROR-IMAGE false green: 100%, remedy None, while a backfill had real work to do. Scoping the population is half the job; enumerating its conditions is the other half.

AND THE CHECK THAT STATES THAT RULE BROKE IT (techne#635, fixed 2026-08-18): `check_vector_coverage` counted `knowledge` alone while `backfill_vectors` embeds knowledge, OBSERVATIONS and THREADS. Measured when filed: 450 observations and 14 threads unembedded, invisible to the check that exists to catch exactly that. THE SILENT-GREEN PATH IS SPECIFIC: work heavily without promoting knowledge, knowledge coverage stays high, doctor stays green, and OBSERVATION coverage rots — and observations are the population `per_turn_recall` reads, so recall degrades to FTS-only for all recent work with no signal anywhere. That is the 2026-07-16 incident (0 of 11,000 observations embedded) waiting to recur. The sibling counts are deliberately simpler than knowledge's: observations are append-only and threads rotate their rowid, so neither carries `vec_stale` or supersession and "present or not" IS the whole question — a richer predicate would be a second definition of coverage.

EMISSION IS NOT CONSUMPTION (techne#636). `check_maintenance_rails` keys on `MAX(knowledge_candidates.created_at)`, so a rail goes green the moment it produces a candidate and stays green no matter what becomes of it — measured: `rail:reflect` green with 206 candidates PENDING and the last review decision 2026-07-27. `_rail_consumption` now reports the pending count and the last promote/discard date in the detail. THE VERDICT STAYS EMISSION-KEYED DELIBERATELY: an unreviewed backlog is a fact about the OPERATOR's review cadence, not about whether the rail ran, and turning it red is a policy decision that belongs in its own change rather than smuggled into the fix that made it visible — the same report-don't-enforce split #497 landed for dangling vectors.
  COROLLARY: narrowing a count can HIDE what it excludes. A row superseded AFTER being embedded keeps a live ANN vector, and nothing auto-runs backfill in production. Orphans and stale rows are therefore counted SEPARATELY and fail the check — legitimate because the same remedy genuinely fixes each.
  **REPORT-WITHOUT-FAILING IS THE RIGHT ANSWER WHEN NO REMEDY EXISTS — and the reason it applied HERE has since expired. The rule outlived its own example; the entry is kept for the rule, not as a live claim about this check.** AS ORIGINALLY DERIVED: a vec rowid whose knowledge row was HARD-DELETED is a real defect, but `_purge_superseded_knowledge_vec` selects `WHERE rowid IN (SELECT id FROM knowledge WHERE superseded_by IS NOT NULL)` — FROM knowledge — so a rowid with no row behind it was never matched (verified: purge removed 0 of 2). Failing on it would have attached `techne vectors backfill` to a finding that command could not clear, rebuilding the never-green defect inside its own fix. THE RULE, still general and still load-bearing: a condition you can detect but not remedy belongs in the DETAIL, never in the VERDICT — visible without being unclearable. **BUT IT NO LONGER DESCRIBES `dangling`.** #408 shipped `_purge_orphaned_vec`, which deletes `WHERE rowid NOT IN (SELECT id FROM knowledge)` — the SAME predicate the `dangling` count uses, same population — so the remedy now clears the finding exactly (EXECUTED through the real functions: `dangling=1` → `backfill_vectors` → `{'orphans_swept': 1}` → `dangling=0`, detail line gone). `dangling` is still excluded from the verdict, for a smaller and entirely different reason: folding it in changes `techne doctor` output on live stores and belongs in its own change. Do NOT cite this entry as evidence the condition is unremediable — it is not, and has not been since #408. (Owning issue: techne#408.)
  A HOOK'S `detail` STRING IS OPERATOR-FACING AND ROTS LIKE ANY OTHER PROSE. `_HOOK_EXPECTATIONS` pairs each hook with a one-line description that `techne doctor` prints verbatim, so it is documentation living inside a data structure — and it drifted: `codex_grep_assist` still read "fires on Grep, when enabled" after techne#596 taught the rail to fire on Bash searches too, on the very commit that centralised the matcher into one constant to stop that fact living in two places. If a change alters WHEN a hook fires, this string is part of the change (techne#596 r3).
  KNOW WHICH SURFACE "THE DETAIL" MEANS: `techne doctor`, NOT the SessionStart banner. `format_banner` is warnings-only and emits nothing for a LIVE check, so a detail-only finding is invisible to an operator who never runs doctor — verified, not assumed (#497 review, nit 2). That is uniform treatment of every LIVE check rather than concealment of this one, but the rule above is only as strong as the surface it names, and this is the surface. A finding that must reach someone who only sees the banner cannot use this pattern.
  ALL FOUR ALTERNATIVES WERE CONSIDERED AND ARE WORSE, recorded so the question is not re-litigated — BUT THEY WERE WEIGHED UNDER THE NOW-EXPIRED "no remedy exists" PREMISE ABOVE, so read them as the reasoning behind the general rule, not as a live constraint on `vectors:coverage`: STALE with `remedy=None` is a permanent red with nothing to try (#496's harm, minus the false comfort); UNKNOWN/UNOBSERVABLE both claim we could NOT observe when we counted it exactly, breaking the honesty invariant in the other direction AND still failing; DORMANT falsely claims the channel is idle and would suppress the real coverage report on the same row; and a separate `vectors:dangling` check relocates the dilemma without resolving it — whatever verdict it carries is either an unclearable red or exactly this, with more surface area.
- **A CHECK WHOSE ANSWER DEPENDS ON HOW ITS INPUT WAS CONSTRUCTED IS MEASURING ITS CALLER, NOT THE SUBSYSTEM.** `config:trust`'s first cut read `config.egress_trust`, a field only `Config.load()` populates, so a directly-constructed `Config` produced UNKNOWN — and since `collect_health` is handed whatever config its caller built, the health banner went amber across five unrelated tests. The question ("is a boundary in place?") was a property of the FILESYSTEM and answerable directly, on one code path that always runs. Ask what the check is actually about before reaching for state someone else recorded. The recorded state kept exactly one job — DISAGREEING with the live probe, which means a layer was deployed after this process loaded and the running process still honors the old resolution. That is STALE, because reporting the live LOCKED alone would be a false green of precisely the kind in the invariant below.
- **DEPLOYED IS NOT LOADED — `runtime:revision` READS DISK AND CANNOT SEE WHAT A LIVE PROCESS HOLDS (techne#491).** Its sibling `runtime:loaded` compares each long-lived techne process's start time against the deployed HEAD's committer time. The incident: `techne_reflect_emit` died with `ImportError: cannot import name 'extract_json_array_or_none'` while the symbol sat on disk in BOTH the repo and the runtime, because the MCP server held `_resident` in `sys.modules` from before a pull and later imported the post-pull `reflect.py` against it. `runtime:revision` reported LIVE throughout — the fourth instance of the silhouette below — and it also produced a WRONG DIAGNOSIS: `rail:reflect` read as STALE-because-unreflected when it was BROKEN in the only process that could run it.
  **IT IS A CONSERVATIVE STALENESS WARNING, NOT A TEAR DETECTOR, AND THE WORDING IS LOAD-BEARING.** Measured 2026-08-06: pulling the runtime under a live server — the same operation that tore it originally — did NOT tear it; `reflect_emit` then ran clean on that process (5 threads, 15 candidates, 0 parse failures). Tearing depends on WHICH modules the process has yet to import and whether the deploy touched them. So the check reports the ORDERING it observed and explicitly disclaims the inference. Overstate it and it cries wolf on every routine deploy, and a warning that cries wolf stops being read — which is how this subsystem fails.
  A SEPARATE CHECK, NOT AN EXTENSION, because the remedies differ: `runtime:revision` says pull the runtime, `runtime:loaded` says restart the process. One result cannot carry two remedies.
  A SHARPER SIGNAL IS DELIBERATELY UNBUILT: comparing mtimes of the files a process actually loaded (`sys.modules[...].__file__`) measures what the failure really depends on, but needs the process to introspect ITSELF, which a check in another process cannot do without a reporting rail on every long-lived consumer. Recorded on #491 as the follow-up if the conservative version proves noisy.
  **IT MEASURES THE DEPLOYMENT, NOT THE CHECKOUT IT WAS IMPORTED FROM, AND THE LANDING TIME, NOT THE COMMIT TIME.** Both were false greens, both reproduced. (a) `runtime:revision` may reasonably ask about its own checkout — it only talks about itself — but this check compares a timestamp against OTHER processes: running `doctor` from a review worktree made the reference HEAD a commit existing nowhere else on the machine, and a server that started after it was vouched for against a revision it could not have loaded. That is the #473 configuration turning the new check green. It now prefers `<techne_home>/runtime` and NAMES the path it measured in every verdict. (b) Committer time is not deploy time — commit lands upstream 22:02, operator pulls 23:00, server starts 22:30: pre-pull code, reported LIVE. It now reads `.git/logs/HEAD`'s mtime (when the ref moved HERE; one stat, no subprocess) and falls back to the committer date, saying which. NOT `.git/HEAD`'s mtime, which read three days stale on the live runtime because a fast-forward rewrites `refs/heads/main` and the reflog, never the symref. Landing time also shrinks the duty cycle, since pulls are rarer than commits — the difference between a useful warning and a permanently-amber one.
