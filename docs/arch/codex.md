# codex — code-graph store (EXPERIMENTAL)

STATUS: experimental, P1 only; tree-sitter+graphqlite deferred until the Codex persona is scoped (docs/roadmap.md).
SEAM: persona-agnostic code-graph substrate, db-per-repo (codex/<slug>-<hash>.db, PRAGMA user_version, CODEX_VERSION=3). files→symbols→call/import/def-use edges stored RELATIONALLY on SQLite — NOT a graph DB (keeps the single-file/portable substrate). Reachability/blast-radius = hand-rolled recursive CTEs, not a graph engine. graphqlite (Cypher + PageRank/Louvain UDF) = possible future techne[codex] upgrade, NOT built.
PARSING: tree-sitter SourceAdapter (Python+TypeScript) lives SEPARATELY in techne/codex/source.py, behind the `techne[codex]` extra (tree-sitter, -python, -typescript, watchdog). LSP-assist: techne/codex/lsp_resolve.py + core/lsp_client.py.
WHY source.py IS ANCHORED, since its churn will make this gate fire on edits that do not concern the card: this card makes load-bearing claims about code that lives THERE, not in core/codex.py — `_SKIP_DIRS`' exact/case-sensitive/repo-relative rule, `_walk_repo`, and the `sweep_excluded_rows` half of the purge story below. Anchoring only core/codex.py left those claims free to rot silently, which is the exact failure the cards exist to prevent. THE FRICTION IS THE PRICE AND IT IS DELIBERATE (techne#613 follow-up): a grammar or extraction change will trip the gate without touching anything this card says. WHEN THAT HAPPENS, RE-READ THE THREE CLAIMS ABOVE AND BUMP THE SHA — do not delete the anchor to make the gate quiet.
WHAT GETS WALKED — `_SKIP_DIRS` MATCHES EXACT, CASE-SENSITIVE SEGMENTS **OF THE REPO-RELATIVE PATH**, AND IT SKIPS VENV *CONTENTS*, NOT JUST DIRECTORIES CALLED `venv` (techne#604). Those three words are load-bearing: testing the whole path would make a repo living UNDER a directory named `build`/`site-packages` index nothing at all, which is why `source.py:530-534` relativises first and says so. Exact names only, no patterns, so a virtualenv named anything else (`.venv-ci-3.12`) walks straight in unless its `site-packages` / `dist-packages` segment is caught. Measured before that entry existed: 114,412 vendored symbols against 5,137 real ones — 96% of this repo's graph — and `codex_blast_radius` returning `aiohttp/web.py` as a dependent of a techne hook. The failure is SILENT: a plausible symbol from site-packages reads exactly like one of ours. Residual, accepted: each venv's `bin/activate_this.py` (2 symbols) still indexes.
MIGRATION v2→v3 PURGES, IT DOES NOT MERELY GATE. Indexing is INCREMENTAL and the only DELETE is scoped to the file being re-indexed, so rows for files the walker no longer visits are never revisited — a polluted index survives a fix to the skip list forever. Worse, `index_freshness` (techne#595) then reports `stale: 0, coverage: complete` over them, because every one of those files IS present and unchanged on disk: they are not stale, they should not be there. `_codex_v2_to_v3` deletes exactly the excluded rows and their OUTBOUND edges; INBOUND edges are unresolved rather than deleted, since a repo symbol really does call into that vendored code and dropping the edge erases a true fact — and `resolution_status` is reset with the NULL to restore the v1 invariant that a NULL `to_symbol` is never 'lsp' — NOT because it changes a query result FOR THE ROWS THIS STEP TOUCHES, which it does not: every row it resets becomes 'unresolved', which is not 'external', so it arms the name fallback either way. THE UNQUALIFIED FORM OF THAT CLAIM — "codegraph reads the column only in `add_edge`, all four fallback sites gate on `to_symbol IS NULL` alone" — WAS TRUE UNTIL techne#679 AND IS NOW FALSE: the four fallbacks read `resolution_status` to refuse an `external` edge (see the v4 paragraph below). The anchor gate cannot catch a drift of this shape, and did not: the falsifying edit is in `codegraph.py`, which no card anchors, while the falsified sentence lived here, so `check_arch_cards.py` reported every card fresh over a card that disagreed with itself. THE RESULTING STATE IS NOT SAFE, AND SAYING SO IS PART OF THE CARD: a NULL `to_symbol` arms the name fallback, so `callers`/`callees`/`reachable` assert a repo-local call that never happened whenever some local symbol shares the bare name (#606). The migration neither causes nor cures that — a FRESH v3 walk stores the identical row. Byte-identity with a re-indexed db holds FOR THE ROWS THIS STEP TOUCHES, not unconditionally (#604 r5): a drifted v2 db also keeps rows for files the walker no longer visits at all — the very defect named at the top of this paragraph — and `source.py:466`'s absolute-path fallback is a second such row. Purging vendored symbols does not, and is not meant to, reconcile those. Convergence on fresh-index state is the deliberate target; deleting these edges would make migration and re-index disagree. Its deletes are CHUNKED at 500 and that bound is load-bearing: `doomed` is unbounded (indexing this repo's venv produced 114,410), one bind per symbol exceeds SQLITE_LIMIT_VARIABLE_NUMBER, and the raise lands BEFORE the version write — so `user_version` stays at 2 and every later `codex_store()` re-raises, taking codex down permanently. Its match runs in PYTHON over repo-relative path parts, not as SQL `LIKE`: LIKE is case-insensitive and matches substrings of the whole stored path, so it purged `vendor/SITE-PACKAGES/…` the walker would keep, and would have emptied a repo stored with absolute paths under a `site-packages` ancestor. Its patterns are held in codex.py as SQL rather than imported from `source._SKIP_DIRS` — the migration must run without the optional extra, and must encode what the skip list meant AT v3.
BUT A MIGRATION RUNS ONCE, SO ENFORCEMENT LIVES IN THE INDEXER (techne#613) — the paragraph above describes a fix that could not stay fixed. `_codex_v2_to_v3` fires exactly when `user_version` moves 2→3, so a db STAMPED v3 and then re-indexed from a tree predating the skip-list change is re-polluted with no path back. OBSERVED ON A REAL DB, not constructed: `user_version: 3` holding 114,410 vendored symbols, which `index_freshness` then certifies as `stale: 0, coverage: complete` — #604's self-certifying state reached by a second route. `initial_walk` therefore calls `source.sweep_excluded_rows` on EVERY full index, so a skip-list change heals itself; `_SKIP_DIRS` has already changed twice and each change would otherwise have needed its own migration. TWO PREDICATES, DELIBERATELY NOT ONE, and this is the thing not to "DRY": the migration's `_V3_PURGE_SEGMENTS` stays FROZEN at what v3 meant (a migration whose meaning changes when someone edits a constant is not a migration), while the sweep reads the LIVE `_SKIP_DIRS` — that is precisely what makes it self-healing. The MECHANICS are shared, via public `purge_symbol_ids` (chunk 500, outbound edges deleted, inbound unresolved), so a db healed by the migration and one healed by the sweep are indistinguishable. The sweep mirrors the WALKER's rule — relativise, then exact case-sensitive segments — so `my-site-packages-tool/`, `site_packages_util.py` and `vendor/SITE-PACKAGES/` survive, absolute rows inside the repo are relativised, and rows outside it are declined rather than guessed at. DELIBERATELY NOT FAIL-SAFE, unlike the neighbouring `repo_root` persist: a sweep that failed quietly would return the caller to the silent pollution it exists to end. Its count is REPORTED — `RepoSource.last_swept`, echoed by `techne codex index` — because a silent purge and a silent no-op look identical from outside, which is how #604 stayed invisible. No `techne codex purge` command exists and none is wanted: re-indexing IS the heal.
v4 GIVES AN IMPORT EDGE ITS BINDING, WHICH IS WHAT MADE RESOLUTION POSSIBLE WITHOUT A TOOLCHAIN (techne#679). Before it, `from a.b import c` and `import a.b` produced the same row shape — a bare `to_name` and nothing else — so 890 distinct names on the live index mixed modules (`os`, `techne`) with imported names (`Config`, `Enum`) indistinguishably, and a call to `Config` could not be tied to the module that supplied it. `edges.to_module` records the source module of a from-import and is NULL for a plain `import x`; that NULL is the discriminator, not a gap. It is also NULL for a relative import (`from . import x`), deliberately: resolving one needs the importing file's own package position, which the parser does not have, and a guessed module resolves to the wrong file — worse than no binding, because `external` and `import_resolved` are both asserted as facts downstream. THE MIGRATION DOES NOT BACKFILL, and cannot: an index written before v4 recorded no module and there is nowhere to recover one from short of re-parsing, so `import_resolve` simply finds no binding and leaves those edges 'unresolved' — its pre-v4 behaviour exactly. `techne/codex/import_resolve.py` consumes the column and is the dep-free complement to `lsp_resolve`, not a competitor: it never overwrites an `lsp` row, and the ordering is a claim about evidence quality — a language server that understands the code outranks a line-reading of an import. Its third outcome is the one worth having. `external` means the callee is bound to a module this index does not contain, so no symbol here can be it — a FACT, where `unresolved` is an absence of one. BECAUSE IT IS A FACT IT REQUIRES POSITIVE EVIDENCE, and failing to find a path is not evidence: the module-path-to-file-path mapping fails for reasons of LAYOUT, so `external` is written only when the module's root names NOTHING ANYWHERE in the index — no directory segment at any depth, no file stem — and anything in-repo-shaped that could not be placed stays `unresolved`. THE DEPTH MATTERS AND WAS WRONG TWICE: an earlier rule tested only the index's TOP-level names, which under `src/` are `{src, tests}` and never a package, so every unplaceable in-repo module fell through to a false `external` — the flat-layout blind spot that techne's own flat tree cannot surface, in a repo whose measurements come from it. Three layouts made earlier rules assert falsehoods about files sitting in the index: a `src/` Python tree, where the dotted path is not the repo-relative path (now matched by unambiguous path suffix, never by guessing between two candidates); a TypeScript relative specifier such as `./util`, which is a path relative to the importing file rather than a module and is therefore left unbound at the parser, exactly as `from . import x` is; and a pnpm-style monorepo, where `packages/foo/src/index.ts` imported as `'foo'` still cannot be PLACED but is no longer asserted absent. THE LOOKUP CANNOT INVENT A SYMBOL, and getting that wrong put four false facts on this repo. It searches the source module by the BOUND name, so an alias asked the wrong question — `documents.py` does `from techne.core.stores import plain_connect as connect`, `stores.py` has no module-level `connect` but does have `DomainStore.connect`, and four calls were bound to a method none of them makes, reported by `include_inferred=False` as `exact`. A RENAMING alias therefore records NO module in either language: the name and the module are each right and wrong together, the original name is stored nowhere, so there is no true fact to lose. `X as X` IS NOT A RENAME and keeps its module — the re-export idiom binds the same name it imported, so the lookup asks the right question; refusing it indiscriminately cost 62 such imports and 4 resolutions on this repo, measured after an earlier version of this fix did exactly that. And the lookup takes an ALLOW-LIST of kinds (`function`, `class`) rather than excluding `module` — `interface` is absent because the indexer never emits it (tenishai/techne#859): a module-level from-import binds a module-level object, never a method, which is also the re-export case the resolver already promised to leave `unresolved`. NO REPO FILE SHADOWS A BUILTIN, and the two languages need different depths of that rule. `myapp/app.py` importing `logging` means the stdlib, since `myapp` is a package and not a `sys.path` entry — so for PYTHON only the suffix branch is refused, and an exact TOP-LEVEL match is left to resolve, because a repo-root `logging.py` IS what Python resolves when the root is on `sys.path`. THAT CARVE-OUT IS PYTHON'S AND ONLY PYTHON'S: there is no `sys.path` in node, a bare specifier resolves through `node_modules`, and builtins outrank it — so for TypeScript the exact branch is the impossible answer rather than the plausible one, and the builtin test runs BEFORE it. An earlier version guarded only the suffix branch, which left `import { promisify } from 'util'` binding to a top-level `util/index.ts` — the likeliest form of the very collision the guard exists to stop. The test is on the module ROOT, spelled once in `_module_root` for both languages after three consecutive rounds each fixed a root in one place and left it wrong in another; and a builtin SHORT-CIRCUITS the in-repo name test, since a repo that happens to hold a `util/` directory does not make the node `util` module unknowable. A BARE NON-BUILTIN SPECIFIER IS STILL A GUESS, recorded rather than fixed: `{stem}/index.ts` is a candidate shape matched at any depth, so a bare `'ui'` resolves to `packages/ui/index.ts` — correct under a pnpm workspace symlink, wrong for an ordinary nested `apps/web/ui/`, and the resolver reads no `package.json` and cannot tell them apart. Refusing bare specifiers would delete the monorepo case, so the cost is pinned by a test instead of removed. CANDIDATE SHAPES ARE LANGUAGE-SCOPED and that is the single gate against a cross-language binding — a Python call must not bind to a TypeScript symbol and be asserted `import_resolved`, which is the status that survives `include_inferred=False`; an unknown language returns no candidates rather than widening, because a second redundant gate on the symbol lookup would mean neither could be shown to be load-bearing. `external` IS ALSO READ, not merely written: `codegraph`'s four name-inference fallbacks refuse to arm on an external edge, since matching `to_name` against a local symbol would invent the very hop the status proves impossible. The resolver runs UNCONDITIONALLY at the end of `techne codex index` and `index-all`, before the optional `--lsp` step which still upgrades what it resolved; it is not behind a flag, because `--lsp` was and the corpus stayed at 1 resolved edge for months. That is what lets `include_inferred=False` return a non-empty graph, which it never could before, since nothing had ever set `to_symbol`. A RESOLVED TARGET MUST ALSO BE MODULE-LEVEL, and `kind` only half expresses that: a function nested inside another function is `kind='function'` too, so `from pkg.util import helper` for a closure — an ImportError in Python — resolved. Nesting is the discriminator and `span` already carries it, so a candidate enclosed by another symbol in its file is refused with no schema change. MEASURED on this repo 2026-08-31: 24,443 call edges, 5,965 resolved and 593 ruled out external in 0.3s with no language server, every bound target a `function` (5,396) or a `class` (569) and none a `method`, against 1 resolved in 33,081 across the whole live corpus beforehand.

THE PER-FILE RE-INDEX HAD THE SAME ASYMMETRY THE MIGRATION FIXED, AND IT FAILED SILENTLY (techne#610). `_index_file` deleted this file's OUTBOUND edges before deleting its symbols — correct, "an edge's owning file is its from_symbol's file" — but `edges.to_symbol` is also `REFERENCES symbols(id)`, and INBOUND edges from OTHER files were never cleared, so the `DELETE FROM symbols` violated the FK. It now unresolves them (`to_symbol=NULL, resolution_status='unresolved'`) exactly as `_codex_v2_to_v3` does, for the same reason: the call is still a true fact, only its resolved target is being replaced. A PLAIN WALK NEVER REACHES THIS — fresh edges leave `to_symbol` NULL and NULL does not constrain — it needs a resolver pass to have populated the column, which is why it hid until #605's population existed. THE SELECTION EFFECT IS THE WORST PART: a file failed to re-index PRECISELY BECAUSE something calls into it, so the better-connected a module is, the more certainly it went stale. And it was invisible: the exception was caught best-effort, the transaction rolled back so the file KEPT ITS PREVIOUS ROWS, and the walk returned normally — 461 `codex_index_failed` tracebacks in one run of this repo while `techne codex index` exited 0. `_index_file` now raises `IndexFailure` and `_index_file_safe` returns `(count, failed)`, because the old `int` contract could not tell "unchanged, nothing to do" from "blew up and rolled back"; `RepoSource.last_failed` carries it out and the CLI EXITS NON-ZERO, mirroring `last_swept`'s rule that a silent purge and a silent no-op look identical from outside.

THE WALKER CAN NOW FAIL OUT LOUD, AND `_unindexed_count` LISTENS (techne#599). `_walk_repo` was `root.rglob("*")`, and rglob SWALLOWS per-directory errors internally: an unreadable directory just drops out of the walk with no exception. `_unindexed_count` guarded it with `except OSError` and DOCUMENTED a degraded result — that handler was dead code, so a `chmod 000` directory holding the sought symbol vanished from enumeration while `coverage` reported `complete` and the caller emitted "This is genuine absence", the exact sentence #595 exists to make trustworthy. It is `os.walk(onerror=..., followlinks=False)` now, with `_SKIP_DIRS` PRUNED IN PLACE rather than walked-then-discarded, plus an `on_symlink_dir` callback for the second undocumented route (a symlinked directory is still not descended into — unchanged — but no longer an unrecorded hole). Indexing ignores both callbacks by default and stays best-effort; only a caller making a POSITIVE claim about completeness needs them. BOTH GUARDS ARE KEPT, deliberately: the `except OSError` catches the WALKER ITSELF failing outright, the callbacks catch a walk that succeeds while quietly dropping a directory — two failure modes, two mechanisms, and collapsing them is what left the second unhandled. All four routes to a wrong "genuine absence" are now NAMED in the docstring; routes 3 and 4 (a genuinely new top-level component; a root-only index plus any subdirectory) remain the design's accepted cost, stated rather than implied.

A READ FROM INSIDE A `git worktree` RESOLVES TO THE PRIMARY CHECKOUT (tenishai/agents#53). db-per-repo means db-per-PRIMARY-repo: a linked worktree has its own `.git`, so `find_repo_root` stops there — a path that has never been indexed — and every query from a review worktree or a worktree-per-session checkout (techne#376/#740) answered "no codex index for the active repo". MEASURED before the fix: across 340 posted reviews by the review agent, the impact pass ran in 6% of them, because her persona correctly says to fall back to grep when codex returns nothing. Nobody was ignoring instructions; the tool was pointed at a path with no db. Resolving to the primary is also the SEMANTICALLY right answer — the impact pass asks what calls a symbol TODAY on the base branch, and the worktree is checked out at the PR head. READ PATH ONLY, and the asymmetry is the point: `reindex_edited_file` still uses `find_repo_root`, or an edit inside a PR worktree would write that branch's symbols into the base graph other sessions are querying. `primary_repo_root` follows git's own `commondir` file rather than splitting the git-dir on `/worktrees/` — `coord.py` records why that heuristic is unsafe. IT ALSO CHECKS THE COMMON DIR IS NAMED `.git`, and the first draft did not, which was wrong in BOTH directions (Prudence, #719): `commondir` -> `parent` is the repo root ONLY for the `<root>/.git` layout, so in the common `.bare + worktrees` layout `parent` is not a checkout at all and an indexed worktree STOPPED resolving — a working install broken — while a BARE REPO NESTED INSIDE ANOTHER REPO resolved to the OUTER repo's index, i.e. confident answers about entirely different code. Both reproduced before fixing. The `.exists()` arm behind it is reached only by an absolute `commondir` naming a `.git` that is gone. THE CLAIM THAT THE FALLBACK MEANT THIS 'CAN ONLY IMPROVE RESOLUTION, NEVER BREAK A WORKING INSTALL' WAS FALSE and is recorded as such, because it is the kind of totalising claim that stops the next reader checking.

THE EDIT RAIL DECLINES INSIDE A LINKED WORKTREE, as a direct consequence. `_inject_edit_blast_radius` pairs the resolved graph with a LINE NUMBER from the file on disk, so once the query resolves to the primary, a PR-branch line looked up against the base-branch graph names a DIFFERENT symbol and the rail would annotate an edit with some other function's dependents. It returns None there instead. Latent when found (`codex_edit_rail` defaults False), which is why it is pinned by a test rather than a note: the next person to enable the flag would not know.
