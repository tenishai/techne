# codex — code-graph store (EXPERIMENTAL)

> Citations like "Prudence, #872 r2" below are automated code-review findings,
> not a person — see [Who's who](../../README.md#whos-who).

**INDEX PROVENANCE IS RECORDED, NEVER INFERRED FROM FILE MTIME (techne#937).** `initial_walk` writes `indexed_at` and `indexed_head` into `codex_meta` beside `repo_root`. The db's own mtime cannot answer "does this index still describe the checkout": mtime moves on ANY write including a WAL checkpoint, so it drifts YOUNGER than the actual index and reads fresh when it is not. `indexed_head` is the load-bearing one — comparing it to the current HEAD is one small ref read and a string compare, which is what lets `codex:freshness` live in the SessionStart banner instead of being marked `@expensive` and vanishing from it. THE FAILURE IT EXISTS FOR: a 5-day-old cabal index with 60 files changed answered `codex search` with ZERO hits for three symbols that exist in source (`_delegation_budget_note`, `_budget_at_least_one`, `_doom_loop_guard`), and a stale index does not degrade gracefully — it says "we don't have that" with exactly the confidence of a correct miss.

STATUS: experimental, P1 only; the tree-sitter parser ships (`techne[codex]`), graphqlite deferred until the Codex persona is scoped.
SEAM: persona-agnostic code-graph substrate, db-per-repo (codex/<slug>-<hash>.db, PRAGMA user_version, CODEX_VERSION=6). files→symbols→call/import/def-use edges stored RELATIONALLY on SQLite — NOT a graph DB (keeps the single-file/portable substrate). Reachability/blast-radius = hand-rolled recursive CTEs, not a graph engine. graphqlite (Cypher + PageRank/Louvain UDF) = possible future techne[codex] upgrade, NOT built.
PARSING: tree-sitter SourceAdapter (Python+TypeScript) lives SEPARATELY in techne/codex/source.py, behind the `techne[codex]` extra (tree-sitter, -python, -typescript, watchdog). LSP-assist: techne/codex/lsp_resolve.py + core/lsp_client.py.
WHY source.py IS ANCHORED, since its churn will make this gate fire on edits that do not concern the card: this card makes load-bearing claims about code that lives THERE, not in core/codex.py — `_SKIP_DIRS`' exact/case-sensitive/repo-relative rule, `_walk_repo`, and the `sweep_excluded_rows` half of the purge story below. Anchoring only core/codex.py left those claims free to rot silently, which is the exact failure the cards exist to prevent. THE FRICTION IS THE PRICE AND IT IS DELIBERATE (techne#613 follow-up): a grammar or extraction change will trip the gate without touching anything this card says. WHEN THAT HAPPENS, RE-READ THE THREE CLAIMS ABOVE AND BUMP THE SHA — do not delete the anchor to make the gate quiet.
WHAT GETS WALKED — `_SKIP_DIRS` MATCHES EXACT, CASE-SENSITIVE SEGMENTS **OF THE REPO-RELATIVE PATH**, AND IT SKIPS VENV *CONTENTS*, NOT JUST DIRECTORIES CALLED `venv` (techne#604). Those three words are load-bearing: testing the whole path would make a repo living UNDER a directory named `build`/`site-packages` index nothing at all, which is why `source.py:530-534` relativises first and says so. Exact names only, no patterns, so a virtualenv named anything else (`.venv-ci-3.12`) walks straight in unless its `site-packages` / `dist-packages` segment is caught. Measured before that entry existed: 114,412 vendored symbols against 5,137 real ones — 96% of this repo's graph — and `codex_blast_radius` returning `aiohttp/web.py` as a dependent of a techne hook. The failure is SILENT: a plausible symbol from site-packages reads exactly like one of ours. Residual, accepted: each venv's `bin/activate_this.py` (2 symbols) still indexes.
MIGRATION v2→v3 PURGES, IT DOES NOT MERELY GATE. Indexing is INCREMENTAL and the only DELETE is scoped to the file being re-indexed, so rows for files the walker no longer visits are never revisited — a polluted index survives a fix to the skip list forever. Worse, `index_freshness` (techne#595) then reports `stale: 0, coverage: complete` over them, because every one of those files IS present and unchanged on disk: they are not stale, they should not be there. `_codex_v2_to_v3` deletes exactly the excluded rows and their OUTBOUND edges; INBOUND edges are unresolved rather than deleted, since a repo symbol really does call into that vendored code and dropping the edge erases a true fact — and `resolution_status` is reset with the NULL to restore the v1 invariant that a NULL `to_symbol` is never 'lsp' — NOT because it changes a query result FOR THE ROWS THIS STEP TOUCHES, which it does not: every row it resets becomes 'unresolved', which is not 'external', so it arms the name fallback either way. THE UNQUALIFIED FORM OF THAT CLAIM — "codegraph reads the column only in `add_edge`, all four fallback sites gate on `to_symbol IS NULL` alone" — WAS TRUE UNTIL techne#679 AND IS NOW FALSE: the four fallbacks read `resolution_status` to refuse an `external` edge (see the v4 paragraph below). The anchor gate cannot catch a drift of this shape, and did not: the falsifying edit is in `codegraph.py`, which no card anchors, while the falsified sentence lived here, so `check_arch_cards.py` reported every card fresh over a card that disagreed with itself. THE RESULTING STATE IS NOT SAFE, AND SAYING SO IS PART OF THE CARD: a NULL `to_symbol` arms the name fallback, so `callers`/`callees`/`reachable` assert a repo-local call that never happened whenever some local symbol shares the bare name (#606). The migration neither causes nor cures that — a FRESH v3 walk stores the identical row. Byte-identity with a re-indexed db holds FOR THE ROWS THIS STEP TOUCHES, not unconditionally (#604 r5): a drifted v2 db also keeps rows for files the walker no longer visits at all — the very defect named at the top of this paragraph — and `source.py:466`'s absolute-path fallback is a second such row. Purging vendored symbols does not, and is not meant to, reconcile those. Convergence on fresh-index state is the deliberate target; deleting these edges would make migration and re-index disagree. Its deletes are CHUNKED at 500 and that bound is load-bearing: `doomed` is unbounded (indexing this repo's venv produced 114,410), one bind per symbol exceeds SQLITE_LIMIT_VARIABLE_NUMBER, and the raise lands BEFORE the version write — so `user_version` stays at 2 and every later `codex_store()` re-raises, taking codex down permanently. Its match runs in PYTHON over repo-relative path parts, not as SQL `LIKE`: LIKE is case-insensitive and matches substrings of the whole stored path, so it purged `vendor/SITE-PACKAGES/…` the walker would keep, and would have emptied a repo stored with absolute paths under a `site-packages` ancestor. Its patterns are held in codex.py as SQL rather than imported from `source._SKIP_DIRS` — the migration must run without the optional extra, and must encode what the skip list meant AT v3.
BUT A MIGRATION RUNS ONCE, SO ENFORCEMENT LIVES IN THE INDEXER (techne#613) — the paragraph above describes a fix that could not stay fixed. `_codex_v2_to_v3` fires exactly when `user_version` moves 2→3, so a db STAMPED v3 and then re-indexed from a tree predating the skip-list change is re-polluted with no path back. OBSERVED ON A REAL DB, not constructed: `user_version: 3` holding 114,410 vendored symbols, which `index_freshness` then certifies as `stale: 0, coverage: complete` — #604's self-certifying state reached by a second route. `initial_walk` therefore calls `source.sweep_excluded_rows` on EVERY full index, so a skip-list change heals itself; `_SKIP_DIRS` has already changed twice and each change would otherwise have needed its own migration. TWO PREDICATES, DELIBERATELY NOT ONE, and this is the thing not to "DRY": the migration's `_V3_PURGE_SEGMENTS` stays FROZEN at what v3 meant (a migration whose meaning changes when someone edits a constant is not a migration), while the sweep reads the LIVE `_SKIP_DIRS` — that is precisely what makes it self-healing. The MECHANICS are shared, via public `purge_symbol_ids` (chunk 500, outbound edges deleted, inbound unresolved), so a db healed by the migration and one healed by the sweep are indistinguishable. The sweep mirrors the WALKER's rule — relativise, then exact case-sensitive segments — so `my-site-packages-tool/`, `site_packages_util.py` and `vendor/SITE-PACKAGES/` survive, absolute rows inside the repo are relativised, and rows outside it are declined rather than guessed at. DELIBERATELY NOT FAIL-SAFE, unlike the neighbouring `repo_root` persist: a sweep that failed quietly would return the caller to the silent pollution it exists to end. Its count is REPORTED — `RepoSource.last_swept`, echoed by `techne codex index` — because a silent purge and a silent no-op look identical from outside, which is how #604 stayed invisible. No `techne codex purge` command exists and none is wanted: re-indexing IS the heal.
v4 GIVES AN IMPORT EDGE ITS BINDING, WHICH IS WHAT MADE RESOLUTION POSSIBLE WITHOUT A TOOLCHAIN (techne#679). Before it, `from a.b import c` and `import a.b` produced the same row shape — a bare `to_name` and nothing else — so 890 distinct names on the live index mixed modules (`os`, `techne`) with imported names (`Config`, `Enum`) indistinguishably, and a call to `Config` could not be tied to the module that supplied it. `edges.to_module` records the source module of a from-import and is NULL for a plain `import x`; that NULL is the discriminator, not a gap. It is also NULL for a relative import (`from . import x`), deliberately: resolving one needs the importing file's own package position, which the parser does not have, and a guessed module resolves to the wrong file — worse than no binding, because `external` and `import_resolved` are both asserted as facts downstream. THE MIGRATION DOES NOT BACKFILL, and cannot: an index written before v4 recorded no module and there is nowhere to recover one from short of re-parsing, so `import_resolve` simply finds no binding and leaves those edges 'unresolved' — its pre-v4 behaviour exactly. "A RE-INDEX POPULATES IT" WAS TRUE OF THE RESOLVER AND FALSE OF THE INDEXER, WHICH MADE THE MIGRATION INERT ON EVERY REPO NOBODY EDITED (techne#864). `_index_file` skips a file whose SHA-256 matches the stored one, and adding a column changes no file's bytes — so the re-index this sentence promised skipped every file, `to_module` stayed NULL forever, and `index-all` printed `0 symbols; resolved 0 calls, 0 external` and exited 0, which reads as "already current". Measured on the live v3→v4 rollout: four of nine repos got ZERO benefit and reported success, ladon and liminal at 0 of 455 and 0 of 635 import edges. THE FIX IS THE #613 SHAPE ONE LEVEL FURTHER OUT and generalises past this column: the migration now writes `codex_meta.reparse_owed_since`, and `initial_walk` forces a full re-parse when it is set, then clears it. The skip is keyed on the FILE; what changed is the QUESTION asked of it, and no file-level hash can express that. A KEY RATHER THAN A BOOLEAN so the reason reaches the log and the CLI line ("REPARSED for schema v4"), and so a future v5 adding another parse-derived column overwrites it rather than colliding with a stale flag. THE DEBT IS DISCHARGED ONLY WHEN EVERY STORED FILE WAS ACTUALLY RE-PARSED, and "nothing raised" was tried first and is too weak (Prudence, #872 r2). `failed` counts only `IndexFailure`, while `_index_file` returns 0 WITHOUT raising on three paths — unknown extension, `OSError` on read, and a missing grammar whose empty parse rolls the delete back so the file KEEPS its pre-migration rows — and `_walk_repo` never visits a file whose language is outside the run's `--language`. All four leave `failed == 0`. Reproduced two ways on the real ladon index: grammar absent gave `symbols 0, forced_by 4, failed 0` with the debt discharged and the column still empty; and `--language typescript` discharged it while 57 Python files were never visited, after which the next full run reported `forced_by None` — #864 again, through the mechanism that fixed it. So the run tracks which files it re-parsed and keeps the debt unless every stored file is among them. TWO EXCLUSIONS, or the strict form never clears: a file GONE FROM DISK keeps stale rows nothing deletes and can never be re-parsed, and a file whose extension the indexer does not handle cannot carry the column. Language SELECTION is deliberately NOT an exclusion — that is the case that made the weak predicate wrong. AND "GONE FROM DISK" MUST BE TESTED BY ERRNO, NOT BY `is_file()` (Prudence, #872 r3), which returns False for THREE different states and only one of them can never be re-parsed: genuinely absent (ENOENT), inside a directory we cannot read (EACCES — and `_walk_repo` takes no `onerror`, so that directory drops out of the walk silently per techne#599), and a BROKEN SYMLINK, which needs no permissions at all since a `git checkout` leaving a dangling link is enough. The latter two still hold pre-migration rows, so excluding them discharged the debt with the data stale — #864 restored through the exclusion written to prevent it, measured as `locked rows still present: 2, edges still NULL: 2, debt: None`. It is `lstat`, not `stat`: stat follows the link and reports ENOENT for a broken one, which is the same collapse by another name. A ROW OUTSIDE THE ROOT IS ALSO EXCLUDED, and that is a scope claim rather than a convenience: `_walk_repo` only descends from the root, so such a row can never be re-parsed by this run and demanding it would pin the debt exactly as a deleted file would. THE COST OF A PINNED DEBT IS WHY THESE EXCLUSIONS ARE NOT OPTIONAL: `force = force or owed is not None`, and `index-all` runs at SessionStart, so a debt that can never be discharged re-parses every repo at every session start forever. The IN-REPO absolute case Prudence also raised is real in principle and unreachable in practice — `sweep_excluded_rows` relativises those rows during the walk, measured — so the predicate normalises for it without a test that could distinguish, and the test drives `_files_still_owed` directly instead. AND IT IS RECORDED ONLY FOR A DB THAT ALREADY HOLDS ROWS: a fresh store is stamped straight to the current version, and a debt there would force the walk it was already going to do and then clear a flag that never meant anything. `--rebuild` on `index` and `index-all` is the manual door for the cases nothing recorded — a grammar or query fix changes extraction with no schema version to hang a debt on. `techne/codex/import_resolve.py` consumes the column and is the dep-free complement to `lsp_resolve`, not a competitor: it never overwrites an `lsp` row, and the ordering is a claim about evidence quality — a language server that understands the code outranks a line-reading of an import. Its third outcome is the one worth having. `external` means the callee is bound to a module this index does not contain, so no symbol here can be it — a FACT, where `unresolved` is an absence of one. BECAUSE IT IS A FACT IT REQUIRES POSITIVE EVIDENCE, and failing to find a path is not evidence: the module-path-to-file-path mapping fails for reasons of LAYOUT, so `external` is written only when the module's root names NOTHING ANYWHERE in the index — no directory segment at any depth, no file stem — and anything in-repo-shaped that could not be placed stays `unresolved`. THE DEPTH MATTERS AND WAS WRONG TWICE: an earlier rule tested only the index's TOP-level names, which under `src/` are `{src, tests}` and never a package, so every unplaceable in-repo module fell through to a false `external` — the flat-layout blind spot that techne's own flat tree cannot surface, in a repo whose measurements come from it. Three layouts made earlier rules assert falsehoods about files sitting in the index: a `src/` Python tree, where the dotted path is not the repo-relative path (now matched by unambiguous path suffix, never by guessing between two candidates); a TypeScript relative specifier such as `./util`, which is a path relative to the importing file rather than a module and is therefore left unbound at the parser, exactly as `from . import x` is; and a pnpm-style monorepo, where `packages/foo/src/index.ts` imported as `'foo'` still cannot be PLACED but is no longer asserted absent. THE LOOKUP CANNOT INVENT A SYMBOL, and getting that wrong put four false facts on this repo. It searches the source module by the BOUND name, so an alias asked the wrong question — `documents.py` does `from techne.core.stores import plain_connect as connect`, `stores.py` has no module-level `connect` but does have `DomainStore.connect`, and four calls were bound to a method none of them makes, reported by `include_inferred=False` as `exact`. A specifier prefixed `.`, `@` or `$` is left unbound at the parser — each is a path this resolver cannot follow, `$lib/queries` being a Vite/SvelteKit alias for `./src/lib/queries` declared in tsconfig `paths` and vite `resolve.alias`, neither of which is read. `$` WAS MISSING UNTIL REAL TYPESCRIPT EXPOSED IT: indexing tenishai/ladon — the first repo with real TypeScript this resolver had run on — asserted `external` over `ui/src/lib/queries.ts:23`, a false fact of exactly the r1 shape, which seven rounds of hand-built fixtures had not produced because none used `$`. A RENAMING alias therefore recorded NO module in either language until v6: the name and the module were each right and wrong together, and the original name was stored nowhere, so refusing was the only safe answer. v6 stores it (see below). `X as X` IS NOT A RENAME and keeps its module — the re-export idiom binds the same name it imported, so the lookup asks the right question; refusing it indiscriminately cost 62 such imports and 4 resolutions on this repo, measured after an earlier version of this fix did exactly that. And the lookup takes an ALLOW-LIST of kinds (`function`, `class`) rather than excluding `module` — `interface` is absent because the indexer never emits it (tenishai/techne#859): a module-level from-import binds a module-level object, never a method, which is also the re-export case the resolver already promised to leave `unresolved`. NO REPO FILE SHADOWS A BUILTIN, and the two languages need different depths of that rule. `myapp/app.py` importing `logging` means the stdlib, since `myapp` is a package and not a `sys.path` entry — so for PYTHON only the suffix branch is refused, and an exact TOP-LEVEL match is left to resolve, because a repo-root `logging.py` IS what Python resolves when the root is on `sys.path`. THAT CARVE-OUT IS PYTHON'S AND ONLY PYTHON'S: there is no `sys.path` in node, a bare specifier resolves through `node_modules`, and builtins outrank it — so for TypeScript the exact branch is the impossible answer rather than the plausible one, and the builtin test runs BEFORE it. An earlier version guarded only the suffix branch, which left `import { promisify } from 'util'` binding to a top-level `util/index.ts` — the likeliest form of the very collision the guard exists to stop. The test is on the module ROOT, spelled once in `_module_root` for both languages after three consecutive rounds each fixed a root in one place and left it wrong in another; and a builtin SHORT-CIRCUITS the in-repo name test, since a repo that happens to hold a `util/` directory does not make the node `util` module unknowable. A BARE NON-BUILTIN SPECIFIER IS STILL A GUESS, recorded rather than fixed: `{stem}/index.ts` is a candidate shape matched at any depth, so a bare `'ui'` resolves to `packages/ui/index.ts` — correct under a pnpm workspace symlink, wrong for an ordinary nested `apps/web/ui/`, and the resolver reads no `package.json` and cannot tell them apart. Refusing bare specifiers would delete the monorepo case, so the cost is pinned by a test instead of removed. CANDIDATE SHAPES ARE LANGUAGE-SCOPED and that is the single gate against a cross-language binding — a Python call must not bind to a TypeScript symbol and be asserted `import_resolved`, which is the status that survives `include_inferred=False`; an unknown language returns no candidates rather than widening, because a second redundant gate on the symbol lookup would mean neither could be shown to be load-bearing. `external` IS ALSO READ, not merely written: `codegraph`'s four name-inference fallbacks refuse to arm on an external edge, since matching `to_name` against a local symbol would invent the very hop the status proves impossible. The resolver runs UNCONDITIONALLY at the end of `techne codex index` and `index-all`, before the optional `--lsp` step which still upgrades what it resolved; it is not behind a flag, because `--lsp` was and the corpus stayed at 1 resolved edge for months. That is what lets `include_inferred=False` return a non-empty graph, which it never could before, since nothing had ever set `to_symbol`. A RESOLVED TARGET MUST ALSO BE MODULE-LEVEL, and `kind` only half expresses that: a function nested inside another function is `kind='function'` too, so `from pkg.util import helper` for a closure — an ImportError in Python — resolved. Nesting is the discriminator and `span` already carries it, so a candidate enclosed by another symbol in its file is refused with no schema change. MEASURED on this repo 2026-08-31: 24,454 call edges, 5,967 resolved and 593 ruled out external in 0.3s with no language server, every bound target a `function` (5,396) or a `class` (569) and none a `method`, against 1 resolved in 33,081 across the whole live corpus beforehand.

v5 PROVES SAME-FILE CALLS, AND NEEDED A PARSE-TIME BIT TO DO IT SAFELY (techne#940). The import pass binds a call through the import that supplied the name, so a call to a function defined in the caller's own file stayed `unresolved`, and `blast-radius --only-proven` printed "(nothing reachable)" for a function whose only callers sat beside it — the empty answer that reads as "safe to change". Reproduced on this repo with `_cursor_key` (four callers, all in core/reflect.py). `resolve_edges_by_scope` runs after the import pass and writes `scope_resolved`: bare call, no import binding the name in the file, exactly one non-nested function/class of that name, no nested function/class of that name (methods do not block). THE BIT IS `edges.bare_call`: `f()` and `x.f()` from one caller collapse onto ONE edge row (PK from_symbol,to_name,kind), so without it `requests.get()` would prove a dependency on a local `get`. The indexer sets it from the callee node's parent (the call node itself = bare). Pre-v5 rows are NULL and untouched; the migration records `reparse_owed_since=5` so the next index re-parses. MEASURED on this repo: proven call edges 6,120 → 9,482 (+3,362 scope_resolved); every one re-checked against source text (same file, a bare `name(` in the caller span, no parameter/assignment/for/as rebinding): 0 violations. NOT PROVEN: a local or module-level ASSIGNMENT of the same name, `global`, and `import a.b` binding `a`. The `--only-proven` CLI and the MCP tool now state how many name-matched nodes they hid, so an empty proven radius is never bare.

v6 RESOLVES A CALL THROUGH A RENAMING IMPORT, BY STORING THE NAME IT RENAMED (techne#1164). `from techne.core.search import search as do_search` bound `do_search` with no module, so `techne search` was missing from `codex callers search`, and every call through a renamed import stayed `unresolved`. `edges.to_orig` now records the original name of a renaming from-import (Python `from a import x as y`, TypeScript `import { x as y }`), the import edge keeps its `to_module`, and `resolve_edges_by_import` asks the source module for `to_orig or to_name`. The decoy case that made v4 refuse renames still cannot bind: `from pkg.util import real as helper` beside a `def helper` in `pkg/util.py` now resolves to `real`, and the resolver never binds it to `helper` (`test_x_as_y_resolves_to_the_original_not_the_decoy`). A rename whose original is ABSENT from an IN-REPO source module (`from pkg.util import nothere as helper`) stays `unresolved`, as before v6; the resolver never retries the bound name, and a test pins that. Default name inference (`include_inferred=True`) can still reach a same-named `helper` from such an edge: `callers()`/`callees()` label that row `name-inferred`, while `reachable()`, which backs blast-radius, carries no per-row label by design, and `--only-proven` excludes it. A rename from a module OUTSIDE the repo now takes the `external` branch (`from requests import nothere as g`) unless its root names something in this repo, the same veto every import gets (then it stays `unresolved`); before v6 it had no binding at all; the six `external` edges in the measurement below are this case. A relative renaming import (`from . import x as y`) records no `to_orig`, since it has no module to look it up in (Temperance and Prudence, PR #1165). `X as X` stores no `to_orig` and resolves as before. The pair form of `_extract_import_names` is unchanged; the indexer asks for triples with `with_orig=True`. Function-local imports needed nothing new: every import edge is already attributed to the module symbol, so `def cmd(): from m import f as g; g()` binds like a module-level import. Pre-v6 rows stay unresolved until a re-parse, and the migration records `reparse_owed_since=6` as v4 and v5 do. MEASURED on this repo (same tree, main's code against this change): 87 call edges changed, all from `unresolved`: 81 to `import_resolved`, each checked to name its alias's original in the imported module, and 6 to `external` (renamed stdlib imports such as `from pathlib import Path as _Path`). No already-resolved edge changed.

THE PER-FILE RE-INDEX HAD THE SAME ASYMMETRY THE MIGRATION FIXED, AND IT FAILED SILENTLY (techne#610). `_index_file` deleted this file's OUTBOUND edges before deleting its symbols — correct, "an edge's owning file is its from_symbol's file" — but `edges.to_symbol` is also `REFERENCES symbols(id)`, and INBOUND edges from OTHER files were never cleared, so the `DELETE FROM symbols` violated the FK. It now unresolves them (`to_symbol=NULL, resolution_status='unresolved'`) exactly as `_codex_v2_to_v3` does, for the same reason: the call is still a true fact, only its resolved target is being replaced. A PLAIN WALK NEVER REACHES THIS — fresh edges leave `to_symbol` NULL and NULL does not constrain — it needs a resolver pass to have populated the column, which is why it hid until #605's population existed. THE SELECTION EFFECT IS THE WORST PART: a file failed to re-index PRECISELY BECAUSE something calls into it, so the better-connected a module is, the more certainly it went stale. And it was invisible: the exception was caught best-effort, the transaction rolled back so the file KEPT ITS PREVIOUS ROWS, and the walk returned normally — 461 `codex_index_failed` tracebacks in one run of this repo while `techne codex index` exited 0. `_index_file` now raises `IndexFailure` and `_index_file_safe` returns `(count, failed)`, because the old `int` contract could not tell "unchanged, nothing to do" from "blew up and rolled back"; `RepoSource.last_failed` carries it out and the CLI EXITS NON-ZERO, mirroring `last_swept`'s rule that a silent purge and a silent no-op look identical from outside.

THE WALKER CAN NOW FAIL OUT LOUD, AND `_unindexed_count` LISTENS (techne#599). `_walk_repo` was `root.rglob("*")`, and rglob SWALLOWS per-directory errors internally: an unreadable directory just drops out of the walk with no exception. `_unindexed_count` guarded it with `except OSError` and DOCUMENTED a degraded result — that handler was dead code, so a `chmod 000` directory holding the sought symbol vanished from enumeration while `coverage` reported `complete` and the caller emitted "This is genuine absence", the exact sentence #595 exists to make trustworthy. It is `os.walk(onerror=..., followlinks=False)` now, with `_SKIP_DIRS` PRUNED IN PLACE rather than walked-then-discarded, plus an `on_symlink_dir` callback for the second undocumented route (a symlinked directory is still not descended into — unchanged — but no longer an unrecorded hole). Indexing ignores both callbacks by default and stays best-effort; only a caller making a POSITIVE claim about completeness needs them. BOTH GUARDS ARE KEPT, deliberately: the `except OSError` catches the WALKER ITSELF failing outright, the callbacks catch a walk that succeeds while quietly dropping a directory — two failure modes, two mechanisms, and collapsing them is what left the second unhandled. All four routes to a wrong "genuine absence" are now NAMED in the docstring; routes 3 and 4 (a genuinely new top-level component; a root-only index plus any subdirectory) remain the design's accepted cost, stated rather than implied.

A READ FROM INSIDE A `git worktree` RESOLVES TO THE PRIMARY CHECKOUT. db-per-repo means db-per-PRIMARY-repo: a linked worktree has its own `.git`, so `find_repo_root` stops there — a path that has never been indexed — and every query from a review worktree or a worktree-per-session checkout (techne#376/#740) answered "no codex index for the active repo". MEASURED before the fix: across 340 posted reviews by the review agent, the impact pass ran in 6% of them, because her persona correctly says to fall back to grep when codex returns nothing. Nobody was ignoring instructions; the tool was pointed at a path with no db. THE CLAIM THAT THE FALLBACK MEANT THIS 'CAN ONLY IMPROVE RESOLUTION, NEVER BREAK A WORKING INSTALL' WAS FALSE and is recorded as such, because it is the kind of totalising claim that stops the next reader checking.
