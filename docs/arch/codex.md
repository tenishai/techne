# codex — code-graph store (EXPERIMENTAL)

STATUS: experimental, P1 only; tree-sitter+graphqlite deferred until the Codex persona is scoped (docs/roadmap.md).
SEAM: persona-agnostic code-graph substrate, db-per-repo (codex/<slug>-<hash>.db, PRAGMA user_version, CODEX_VERSION=3). files→symbols→call/import/def-use edges stored RELATIONALLY on SQLite — NOT a graph DB (keeps the single-file/portable substrate). Reachability/blast-radius = hand-rolled recursive CTEs, not a graph engine. graphqlite (Cypher + PageRank/Louvain UDF) = possible future techne[codex] upgrade, NOT built.
PARSING: tree-sitter SourceAdapter (Python+TypeScript) lives SEPARATELY in techne/codex/source.py, behind the `techne[codex]` extra (tree-sitter, -python, -typescript, watchdog). LSP-assist: techne/codex/lsp_resolve.py + core/lsp_client.py.
WHY source.py IS ANCHORED, since its churn will make this gate fire on edits that do not concern the card: this card makes load-bearing claims about code that lives THERE, not in core/codex.py — `_SKIP_DIRS`' exact/case-sensitive/repo-relative rule, `_walk_repo`, and the `sweep_excluded_rows` half of the purge story below. Anchoring only core/codex.py left those claims free to rot silently, which is the exact failure the cards exist to prevent. THE FRICTION IS THE PRICE AND IT IS DELIBERATE (techne#613 follow-up): a grammar or extraction change will trip the gate without touching anything this card says. WHEN THAT HAPPENS, RE-READ THE THREE CLAIMS ABOVE AND BUMP THE SHA — do not delete the anchor to make the gate quiet.
WHAT GETS WALKED — `_SKIP_DIRS` MATCHES EXACT, CASE-SENSITIVE SEGMENTS **OF THE REPO-RELATIVE PATH**, AND IT SKIPS VENV *CONTENTS*, NOT JUST DIRECTORIES CALLED `venv` (techne#604). Those three words are load-bearing: testing the whole path would make a repo living UNDER a directory named `build`/`site-packages` index nothing at all, which is why `source.py:530-534` relativises first and says so. Exact names only, no patterns, so a virtualenv named anything else (`.venv-ci-3.12`) walks straight in unless its `site-packages` / `dist-packages` segment is caught. Measured before that entry existed: 114,412 vendored symbols against 5,137 real ones — 96% of this repo's graph — and `codex_blast_radius` returning `aiohttp/web.py` as a dependent of a techne hook. The failure is SILENT: a plausible symbol from site-packages reads exactly like one of ours. Residual, accepted: each venv's `bin/activate_this.py` (2 symbols) still indexes.
MIGRATION v2→v3 PURGES, IT DOES NOT MERELY GATE. Indexing is INCREMENTAL and the only DELETE is scoped to the file being re-indexed, so rows for files the walker no longer visits are never revisited — a polluted index survives a fix to the skip list forever. Worse, `index_freshness` (techne#595) then reports `stale: 0, coverage: complete` over them, because every one of those files IS present and unchanged on disk: they are not stale, they should not be there. `_codex_v2_to_v3` deletes exactly the excluded rows and their OUTBOUND edges; INBOUND edges are unresolved rather than deleted, since a repo symbol really does call into that vendored code and dropping the edge erases a true fact — and `resolution_status` is reset with the NULL to restore the v1 invariant that a NULL `to_symbol` is never 'lsp' — NOT because it changes a query result, which it does not: codegraph reads that column only in `add_edge`, and all four fallback sites gate on `to_symbol IS NULL` alone. THE RESULTING STATE IS NOT SAFE, AND SAYING SO IS PART OF THE CARD: a NULL `to_symbol` arms the name fallback, so `callers`/`callees`/`reachable` assert a repo-local call that never happened whenever some local symbol shares the bare name (#606). The migration neither causes nor cures that — a FRESH v3 walk stores the identical row. Byte-identity with a re-indexed db holds FOR THE ROWS THIS STEP TOUCHES, not unconditionally (#604 r5): a drifted v2 db also keeps rows for files the walker no longer visits at all — the very defect named at the top of this paragraph — and `source.py:466`'s absolute-path fallback is a second such row. Purging vendored symbols does not, and is not meant to, reconcile those. Convergence on fresh-index state is the deliberate target; deleting these edges would make migration and re-index disagree. Its deletes are CHUNKED at 500 and that bound is load-bearing: `doomed` is unbounded (indexing this repo's venv produced 114,410), one bind per symbol exceeds SQLITE_LIMIT_VARIABLE_NUMBER, and the raise lands BEFORE the version write — so `user_version` stays at 2 and every later `codex_store()` re-raises, taking codex down permanently. Its match runs in PYTHON over repo-relative path parts, not as SQL `LIKE`: LIKE is case-insensitive and matches substrings of the whole stored path, so it purged `vendor/SITE-PACKAGES/…` the walker would keep, and would have emptied a repo stored with absolute paths under a `site-packages` ancestor. Its patterns are held in codex.py as SQL rather than imported from `source._SKIP_DIRS` — the migration must run without the optional extra, and must encode what the skip list meant AT v3.
BUT A MIGRATION RUNS ONCE, SO ENFORCEMENT LIVES IN THE INDEXER (techne#613) — the paragraph above describes a fix that could not stay fixed. `_codex_v2_to_v3` fires exactly when `user_version` moves 2→3, so a db STAMPED v3 and then re-indexed from a tree predating the skip-list change is re-polluted with no path back. OBSERVED ON A REAL DB, not constructed: `user_version: 3` holding 114,410 vendored symbols, which `index_freshness` then certifies as `stale: 0, coverage: complete` — #604's self-certifying state reached by a second route. `initial_walk` therefore calls `source.sweep_excluded_rows` on EVERY full index, so a skip-list change heals itself; `_SKIP_DIRS` has already changed twice and each change would otherwise have needed its own migration. TWO PREDICATES, DELIBERATELY NOT ONE, and this is the thing not to "DRY": the migration's `_V3_PURGE_SEGMENTS` stays FROZEN at what v3 meant (a migration whose meaning changes when someone edits a constant is not a migration), while the sweep reads the LIVE `_SKIP_DIRS` — that is precisely what makes it self-healing. The MECHANICS are shared, via public `purge_symbol_ids` (chunk 500, outbound edges deleted, inbound unresolved), so a db healed by the migration and one healed by the sweep are indistinguishable. The sweep mirrors the WALKER's rule — relativise, then exact case-sensitive segments — so `my-site-packages-tool/`, `site_packages_util.py` and `vendor/SITE-PACKAGES/` survive, absolute rows inside the repo are relativised, and rows outside it are declined rather than guessed at. DELIBERATELY NOT FAIL-SAFE, unlike the neighbouring `repo_root` persist: a sweep that failed quietly would return the caller to the silent pollution it exists to end. Its count is REPORTED — `RepoSource.last_swept`, echoed by `techne codex index` — because a silent purge and a silent no-op look identical from outside, which is how #604 stayed invisible. No `techne codex purge` command exists and none is wanted: re-indexing IS the heal.
OPS: schema symbols(id,file,name,kind,…)+edges; codex_meta KV (v2) persists repo_root; migrations via _apply_codex_migration() before store.migrate().
API: `techne codex index <repo>`; MCP codex_search, codex_blast_radius.
CONSUMERS: none cross-repo yet (experimental). CI installs the `codex` extra so extraction tests run, not skip.
