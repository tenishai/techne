# coord — inter-session mailbox (techne#376)

WHAT: concurrent Claude Code sessions talk without a human router.
IDENTITY: self-asserted session_id (CLAUDE_CODE_SESSION_ID); NO token — trust boundary = local machine (anything that writes techne.db can already do anything). ONE NARROW EXCEPTION since techne#393: the keys that select where memory EGRESSES to can be moved out of the agent's reach into an operator-owned layer → docs/arch/config-trust.md. That does not soften the statement above — it carves out the config surface only, and only when the deployment actually gives the agent a different uid.
ADDRESSING: channel (default 'coord', broadcast) | session_id (direct, delivers even if offline).
PRESENCE: live_sessions() reads ~/.claude/sessions/<pid>.json; keeps a row only if fresh within a 90-min window (_PRESENCE_FRESH_SECONDS) AND its pid is a live process — reap-on-read via os.kill(pid,0) (techne#380; heartbeat freshness alone advertised dead PIDs as routable, missing/foreign pid fails open). Read-only: never writes/deregisters the roster, so a hard SIGKILL still relies on TTL+reap.
DELIVERY: push — post_tool_use hook injects unread into next tool call; session-start banner shows unread + who's live.

INVARIANTS:
- resolve_recipient(to): 'coord' passthrough | live display-name alias→session_id | v4-UUID passthrough; unmatched name → raise ValueError (dead-letter, NEVER silent-store).
- name tie → newest-active session wins.
- **IDENTITY IS TWO DIFFERENT THINGS AND THEY ARE NOT INTERCHANGEABLE (techne#446).** A message's AUTHOR and a reader's RECEIPT both used to key on the session UUID, which Claude Code mints fresh per launch — so a relaunched session had no receipts and did not recognise its own past sends. It re-read the entire backlog every launch and the unread count only ever grew (measured: 97 messages, the bus's whole life, reported unread; 56 of them the reader's own). Both now key on the DURABLE identity — the `-n` display name — via `reader_key()`, falling back to the UUID when unnamed. `coord_reads.reader_session` is namespaced (`name:` / `uuid:`) because the column holds two KINDS of identity and a bare value cannot say which.
- PER-READER FANOUT IS NOT THE BUG AND MUST STAY. `coord` is a broadcast: if one peer marking a message read cleared it for everyone, a slower peer would silently never see it.
- **A NAME IS DURABLE ACROSS TIME, NOT ACROSS CONCURRENCY — and merging identity IS merging cardinality.** #446's first cut claimed it changed the receipt's identity and never its cardinality; that was FALSE for two LIVE sessions sharing a `-n` name (duplicate names are reachable — see `resolve_recipient`). Both keyed on `name:poe_1`, so one marking a message read emptied the other's inbox silently, and since the authorship filter matched the name too, same-named peers were invisible to each other — a regression, since distinct UUIDs used to work. Caught in review (#490), not by the change's own tests, which used two DIFFERENT names. `_durable_name()` now returns None when another LIVE session holds the same name, so both fall back to the UUID: two concurrent twins each re-read the backlog (the old, NOISY behaviour) rather than silently swallowing each other's messages. Prefer noise to silence WHERE THE RIVAL IS VISIBLE — and it is not always visible, see the next invariant. Dead sidecars do NOT count as rivals — presence is TTL+reap and never deregisters, so counting corpses would permanently demote a name that is unique right now.
- **A DORMANT TWIN IS A RIVAL — FIXED IN #492, and the fix is `procStart`, not a stricter TTL.** `live_sessions()` drops a record on `updatedAt` BEFORE consulting `_pid_alive`, so a twin that was running but idle past the 90-min TTL was invisible to `_durable_name`'s rival check. BOTH halves leaked: the authorship filter `from_name != 'poe_1'` dropped the dormant twin's sends outright, and — because the key is recomputed per call while `coord_reads` rows are PERMANENT — twins whose active windows are more than the TTL apart took TURNS being the unique name-holder, shared one receipt row, and consumed each other's messages. That second half is the #446 fanout collapse itself, in a configuration this card previously called impossible.
  THE FIX: a rival is heartbeat-fresh OR (pid-alive AND `_is_same_process`). The sidecar records `procStart`, the kernel's process start time, so a dormant twin (alive, matching) is distinguishable from a corpse whose pid was RECYCLED (alive, not matching). That guard is what makes a TTL-free rival check safe — a pid-only check would demote a name permanently off a lingering sidecar, i.e. #446 restored, which is why the issue warned against the obvious fix.
  **COMPARE AS EPOCHS.** `procStart` is UTC; `ps -o lstart=` prints local. The two renderings of one instant differ by the UTC offset (measured 4h here) and are EQUAL to the second once parsed. `startedAt` is the app's own clock and drifts ~2s from the kernel's — the wrong field.
  PRODUCTION STILL CANNOT TELL A DEAD PREDECESSOR FROM A DORMANT TWIN BY NAME ALONE, and `test_a_relaunched_session_does_not_re_read_the_backlog` is the boundary: same arrangement, opposite intent. `procStart` separates them without moving that test — an implementer who "fixes" it instead trades this bug for #446.
  THE SUITE COULD NOT SEE THIS UNTIL THE FIXTURE WAS HONEST: `_live` pinned `live_sessions` to return every record as live, defining the concept the assertions turn on. It now stamps a fresh `updatedAt`, a real pid and a real `procStart`, and lets liveness be computed.
- **THE SIDECAR DIRECTORY IS SCANNED EXACTLY ONCE PER UNREAD-PATH CALL — AND THAT MUST BE MEASURED ON THE UNPINNED PATH.** (Scoped deliberately: `send(to=<name>)` still scans TWICE — `session_name()` then `resolve_recipient()` → `live_sessions()` — which is unchanged from main, off the post_tool_use path, and tracked on #494. An unscoped heading here would be this card's own failure mode, since headings are what a hurried reader retains.) `_identity` resolves identity once per `inbox()`/`unread_count()`/`mark_read()`, not per use. The first cut scanned `~/.claude/sessions` 2-3x with no cache — ~6ms per tool call on the post_tool_use hot path, landing immediately after techne#470 took hooks from 100ms to 50ms. The SECOND cut still scanned 2x on the NAMED path, because `_durable_name` calls `live_sessions()`, which re-globs and re-parses the whole directory itself; `live_sessions(records=...)` now accepts the records already read. Measured with 61 sidecars: 2 scans / ~7ms → 1 scan / ~4ms.
  THE TEST THAT GUARDED THIS WAS HOLLOW IN THE EXACT DIMENSION IT MEASURED — it pinned `live_sessions`, i.e. the second scanner, so it counted 1 while production did 2. It now pins the reaper (`_pid_alive`) and NEITHER reader.
  **THE RULE, in Prudence's formulation (#490 round 2), which is better than the one I first wrote here: A STUB MUST NOT REDEFINE THE CONCEPT THE ASSERTION TURNS ON.** My version — "a test that counts work done by a collaboration may pin neither collaborator" — was both too narrow and too absolute. Too narrow: the `_live` fixture in tests/test_coord.py pins `live_sessions` while counting nothing, redefining what *live* MEANS (every record, no TTL), which is exactly why the whole suite was blind to the dormant-twin leak above. Too absolute: the `named` fixture pins `live_sessions` to `[]` honestly, to ARRANGE a precondition the assertions do not turn on. The usable test: name the concept the assertion turns on, then check that no stub owns its definition.
- THE DURABLE KEY COSTS TWO THINGS, both deliberate: a recycled name inherits the previous holder's receipts (the name denotes a persistent ROLE, which is what makes it stable enough to key on), and an unnamed session keeps the old re-read-everything behaviour (no `-n`, no durable identity to offer).

API: MCP techne_send / techne_inbox / techne_mark_read / techne_coord_threads; CLI `techne coord`.
CONSUMERS: every live session sharing techne.db; MCP SERVER_INSTRUCTIONS tell agents to announce branch/commit intent on 'coord' (reflex).
