# coord — inter-session mailbox (techne#376)

WHAT: concurrent Claude Code sessions talk without a human router.
IDENTITY: self-asserted session_id (CLAUDE_CODE_SESSION_ID); NO token — trust boundary = local machine (anything that writes techne.db can already do anything). ONE NARROW EXCEPTION since techne#393: the keys that select where memory EGRESSES to can be moved out of the agent's reach into an operator-owned layer → docs/arch/config-trust.md. That does not soften the statement above — it carves out the config surface only, and only when the deployment actually gives the agent a different uid.
ADDRESSING: channel (default 'coord', broadcast) | session_id (direct, delivers even if offline).
PRESENCE: live_sessions() reads ~/.claude/sessions/<pid>.json; keeps a row only if fresh within a 90-min window (_PRESENCE_FRESH_SECONDS) AND its pid is a live process — reap-on-read via os.kill(pid,0) (techne#380; heartbeat freshness alone advertised dead PIDs as routable, missing/foreign pid fails open). Read-only: never writes/deregisters the roster, so a hard SIGKILL still relies on TTL+reap.
PRESENCE HAS TWO PREDICATES, AND USING THE WRONG ONE MAKES A GUARD INERT (techne#581). `live_sessions()` answers "who can I ROUTE to?" and therefore requires a fresh `updatedAt`. `present_session_ids()` answers "does this id name a session that EXISTS right now?" and requires only a sidecar plus a live pid. The distinction is forced by Claude Code, not invented here: it writes the `updatedAt` heartbeat ONLY for `entrypoint: "cli"` sessions, while every headless `claude -p` run (`entrypoint: "sdk-cli"` — every agent persona) writes a live pid and `updatedAt: null`. Measured 2026-08-16 in an agent's own config dir: `_session_records()` returned 3 while `live_sessions()` returned [] — permanently, not transiently. So an EXISTENCE test built on `live_sessions` is blind to every agent on the box, which is exactly how #573's first cut shipped a guard that could never fire there. `present_session_ids` is the WEAKER claim of the two by design — right for a guard that REFUSES on absence (a false present costs only the old silent behaviour; a false absent would refuse a session that is genuinely working), wrong for routing. IT IS TTL-FREE **AND** PID-ONLY, which is the combination the `_durable_name` invariant below explicitly warns against ("do NOT simplify to a pid-only check") — that path pays for `_same_process_pids`/`procStart` precisely because a recycled pid on a lingering sidecar reads as alive. A wound-down session can therefore still be reported present, and THE ENUMERATION IS PHRASED BY WHAT THE PROBE DOES, not by what the pid looks like — every shape-based version was wrong ("the one way", then four ways, the last miss introduced by the very commit fixing the previous one): (1) THE PROBE CANNOT RUN — missing pid, non-integer pid, or a pid >= 2**31 that does not fit a C int, all fail open because unverifiable is not dead; (2) THE PROBE IS SKIPPED — `pid: 0` or negative take the `pid <= 0` short-circuit, and these ARE integers, which a "non-integer" framing kept missing; (3) THE PROBE RUNS AND IS WRONG — a recycled pid, live and owned by an unrelated process, with nothing about the value to give it away; (4) NOTHING BOUNDS ANY OF THEM, there being no TTL here. Measured 2026-08-16: zero false-presents in practice — current state, not a guarantee. CASE 3 IS NOW CLOSED (techne#587, 2026-08-17) — cases 1, 2 and 4 stand, and the enumeration above still describes what `_pid_alive` alone can tell you rather than what `present_session_ids` returns. DEMOTION REQUIRES POSITIVE EVIDENCE: `_recycled_pids` reports only pids where `ps` gave a start time, the sidecar claimed one, and they DISAGREE. The complement of `_same_process_pids` is deliberately NOT used, because that set lumps a real mismatch together with every unknown (no `procStart`, `ps` silent about the pid, an unparseable `lstart`, DST ambiguity) and demoting on the union manufactures FALSE ABSENTS — the worse error here, since a false present costs only the older weaker behaviour while a false absent refuses a session that is genuinely working. `_classify_pids` is therefore THREE-VALUED (same / recycled / unknown) and both callers read the value they need. THE COST OBJECTION THAT DEFERRED THIS IN #581 WAS REAL AND IS NOW PAID FOR RATHER THAN DISMISSED: measured on this host, `present_session_ids()` was 0.005 ms against 31.9 ms for one `_same_process_pids` — a ~6,400x step on a path that runs for every identity-resolving coord MCP call. `_ps_starts` caches the snapshot for `_PS_CACHE_TTL_S` (2s), which collapses a burst to a single `ps` — measured after: 33.9 ms cold, 0.041 ms warm — while staying far shorter than any plausible pid-recycling interval. A FAILED probe is NOT cached, so a transient `ps` error cannot pin an empty answer for the window. Related: `_pid_alive` also catches `OverflowError`, which is not an `OSError`. THAT PATH WAS ALWAYS REACHABLE, not newly so — `live_sessions` checks the TTL BEFORE the pid (the same ordering the `_durable_name` invariant below relies on), so a FRESH sidecar with such a pid always raised and only STALE ones were discarded first; presence widened the door rather than opening it. The fix is worth more than one record: `_resolve_session_id` wraps the lookup in `except Exception`, so ONE unprobeable pid anywhere in the directory silently disabled the #573 guard for every caller.
DELIVERY: push — post_tool_use hook injects unread into next tool call; session-start banner shows unread + who's live. NOT INTO A SUBAGENT (techne#929): a subagent presents the PARENT'S session_id, so the rail resolved to the parent's inbox and handed peer traffic to an agent spawned to read untrusted pages — and, because the rail is surface-once, CONSUMED the message so the parent never got the pushed copy. post_tool_use now returns early on `agent_id` (subagent-only; `agent_type` is NOT usable, it is also set for a top-level `--agent` session). The message stays unread, so the banner and techne_inbox still deliver it — push is suppressed there, not delivery.

REDACTION (techne#1037): `send()` runs `body` through `redact_credentials` before the INSERT, so a token pasted into a message is stored as `<redacted:tag>` and every inbox nudge replays the redacted form. Pattern-based and best-effort, like every other sink. Rows written before this change are not rewritten.

INVARIANTS:
- resolve_recipient(to): 'coord' passthrough | live display-name alias→session_id | v4-UUID passthrough; unmatched name → raise ValueError (dead-letter, NEVER silent-store).
- name tie → newest-active session wins.
- **IDENTITY IS TWO DIFFERENT THINGS AND THEY ARE NOT INTERCHANGEABLE (techne#446).** A message's AUTHOR and a reader's RECEIPT both used to key on the session UUID, which Claude Code mints fresh per launch — so a relaunched session had no receipts and did not recognise its own past sends. It re-read the entire backlog every launch and the unread count only ever grew (measured: 97 messages, the bus's whole life, reported unread; 56 of them the reader's own). Both now key on the DURABLE identity — the `-n` display name — via `reader_key()`, falling back to the UUID when unnamed. `coord_reads.reader_session` is namespaced (`name:` / `uuid:`) because the column holds two KINDS of identity and a bare value cannot say which.
- PER-READER FANOUT IS NOT THE BUG AND MUST STAY. `coord` is a broadcast: if one peer marking a message read cleared it for everyone, a slower peer would silently never see it.
- **A NAME IS DURABLE ACROSS TIME, NOT ACROSS CONCURRENCY — and merging identity IS merging cardinality.** #446's first cut claimed it changed the receipt's identity and never its cardinality; that was FALSE for two LIVE sessions sharing a `-n` name (duplicate names are reachable — see `resolve_recipient`). Both keyed on `name:poe_1`, so one marking a message read emptied the other's inbox silently, and since the authorship filter matched the name too, same-named peers were invisible to each other — a regression, since distinct UUIDs used to work. Caught in review (#490), not by the change's own tests, which used two DIFFERENT names. `_durable_name()` now returns None when another LIVE session holds the same name, so both fall back to the UUID: two concurrent twins each re-read the backlog (the old, NOISY behaviour) rather than silently swallowing each other's messages. Prefer noise to silence WHERE THE RIVAL IS VISIBLE — and it is not always visible, see the next invariant. Dead sidecars do NOT count as rivals — presence is TTL+reap and never deregisters, so counting corpses would permanently demote a name that is unique right now.
- **A DORMANT TWIN IS A RIVAL — FIXED IN #492, and the fix is `procStart`, not a stricter TTL.** `live_sessions()` drops a record on `updatedAt` BEFORE consulting `_pid_alive`, so a twin that was running but idle past the 90-min TTL was invisible to `_durable_name`'s rival check. BOTH halves leaked: the authorship filter `from_name != 'poe_1'` dropped the dormant twin's sends outright, and — because the key is recomputed per call while `coord_reads` rows are PERMANENT — twins whose active windows are more than the TTL apart took TURNS being the unique name-holder, shared one receipt row, and consumed each other's messages. That second half is the #446 fanout collapse itself, in a configuration this card previously called impossible.
  THE FIX: a rival is heartbeat-fresh OR (pid-alive AND `_is_same_process`). The sidecar records `procStart`, the kernel's process start time, so a dormant twin (alive, matching) is distinguishable from a corpse whose pid was RECYCLED (alive, not matching). That guard is what makes a TTL-free rival check safe — a pid-only check would demote a name permanently off a lingering sidecar, i.e. #446 restored, which is why the issue warned against the obvious fix.
  **COMPARE AS EPOCHS.** `procStart` is UTC; `ps -o lstart=` prints local. The two renderings of one instant differ by the UTC offset (measured 4h here) and are EQUAL to the second once parsed. `startedAt` is the app's own clock and drifts ~2s from the kernel's — the wrong field.
  PRODUCTION STILL CANNOT TELL A DEAD PREDECESSOR FROM A DORMANT TWIN BY NAME ALONE, and `test_a_relaunched_session_does_not_re_read_the_backlog` is the boundary: same arrangement, opposite intent. `procStart` separates them without moving that test — an implementer who "fixes" it instead trades this bug for #446.
  COST, MEASURED WITH DISTINCT LIVE PIDS (batching is not a uniform win — see the crossover). One `ps` for all candidates. Medians through `_durable_name`: no same-name rival 0.00ms; 1 candidate ~5ms; 2+ candidates ~26-30ms FLAT. macOS `ps` takes a single-pid fast path while a pid LIST costs ~26ms regardless of length. BATCHED VS PER-CANDIDATE, measured: 1 -> 4.8 vs 4.9ms; 2 -> 25.9 vs 9.6; 3 -> 25.9 vs 13.9; 4 -> 25.9 vs 19.0; 5 -> 25.7 vs 23.7; 10 -> 26.1 vs 46.6; 20 -> 26.8 vs 93.0. So BATCHING IS A NET LOSS FROM 2 TO 4 CANDIDATES and only crosses over at ~5. Kept anyway: the 1-twin case (the #492 repro) takes the 5ms fast path either way, 2-4 dormant same-name twins is rarer than that, and ~14ms worst-case on a path that only runs while several twins are dormant buys a bound that does not grow. Do not cite it as a uniform win. An earlier revision of this paragraph claimed ~5.2ms flat with '20 candidates cost the same as 1' — that benchmark built every record from a helper defaulting `pid` to `os.getpid()`, so all 20 shared ONE pid, `wanted` collapsed to a single key, and it measured the 1-pid fast path. The benchmark was a live instance of the dict-collapse bug below.
  `wanted` MAPS pid -> SET OF CLAIMED procStarts, never a scalar. Two same-name sidecars can carry one pid (a corpse whose pid was recycled onto a running twin) and a dict comprehension keeps only the LAST write — which can be the corpse, losing the twin and reinstating #492 for the exact case this exists to catch. It fails SILENTLY and SAFELY (toward pre-#492, never toward #446), so nothing goes red when it regresses: the guard has to be a test. `test_a_corpse_does_not_hide_a_twin_that_shares_its_pid` is PARAMETRISED ON ORDER because only corpse-LAST fails — corpse-first lets the twin's claim win the dict and passes on the buggy code.
  DST FALL-BACK: `timegm` has no DST and `mktime` guesses `tm_isdst`, so a start inside the repeated hour can miss by 3600s — one hour a year, failing safe (no match -> pre-#492 behaviour).
  THE SUITE COULD NOT SEE THIS UNTIL THE FIXTURE WAS HONEST: `_live` pinned `live_sessions` to return every record as live, defining the concept the assertions turn on. It now stamps a fresh `updatedAt`, a real pid and a real `procStart`, and lets liveness be computed.
- **THE SIDECAR DIRECTORY IS SCANNED EXACTLY ONCE PER UNREAD-PATH CALL — AND THAT MUST BE MEASURED ON THE UNPINNED PATH.** (FIXED for send too, #494: it scanned TWICE — `session_name()` then `resolve_recipient()` → `live_sessions()`. Both now take an optional `records`, and `send` reads once and threads it. NOT a dedup: the two ask different questions — "what is MY name?" vs "who is THAT name?" — so only the READ is shared. `send` still snapshots the RAW `session_name()`, deliberately, NOT `_identity()`'s durable name: that is None when a rival holds the name, which would blank `from_name` on a twin's rows and change the authorship filter.) `_identity` resolves identity once per `inbox()`/`unread_count()`/`mark_read()`, not per use. The first cut scanned `~/.claude/sessions` 2-3x with no cache — ~6ms per tool call on the post_tool_use hot path, landing immediately after techne#470 took hooks from 100ms to 50ms. The SECOND cut still scanned 2x on the NAMED path, because `_durable_name` calls `live_sessions()`, which re-globs and re-parses the whole directory itself; `live_sessions(records=...)` now accepts the records already read. Measured with 61 sidecars: 2 scans / ~7ms → 1 scan / ~4ms.
  THE TEST THAT GUARDED THIS WAS HOLLOW IN THE EXACT DIMENSION IT MEASURED — it pinned `live_sessions`, i.e. the second scanner, so it counted 1 while production did 2. It now pins the reaper (`_pid_alive`) and NEITHER reader.
  **THE RULE, in Prudence's formulation (#490 round 2), which is better than the one I first wrote here: A STUB MUST NOT REDEFINE THE CONCEPT THE ASSERTION TURNS ON.** My version — "a test that counts work done by a collaboration may pin neither collaborator" — was both too narrow and too absolute. Too narrow: the `_live` fixture in tests/test_coord.py pins `live_sessions` while counting nothing, redefining what *live* MEANS (every record, no TTL), which is exactly why the whole suite was blind to the dormant-twin leak above. Too absolute: the `named` fixture pins `live_sessions` to `[]` honestly, to ARRANGE a precondition the assertions do not turn on. The usable test: name the concept the assertion turns on, then check that no stub owns its definition.
- THE DURABLE KEY COSTS TWO THINGS, both deliberate: a recycled name inherits the previous holder's receipts (the name denotes a persistent ROLE, which is what makes it stable enough to key on), and an unnamed session keeps the old re-read-everything behaviour (no `-n`, no durable identity to offer).

API: MCP techne_send / techne_inbox / techne_mark_read / techne_coord_threads; CLI `techne coord`.
CONSUMERS: every live session sharing techne.db; MCP SERVER_INSTRUCTIONS tell agents to announce branch/commit intent on 'coord' (reflex).
