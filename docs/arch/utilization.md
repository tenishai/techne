# utilization — is the read path earning its tokens? (techne#329)

WHAT: techne writes constantly and reads rarely. This seam MEASURES the read side — what we inject into an agent's context, and whether the agent then did anything that suggests the injection mattered. It exists because #329's audit found we were write-mostly and the auto-recall rail was **unmeasurable**: 306 memory writes to 116 reads, 43 code-graph queries against 3,296 hand edits, and `pattern_search` never called at all. The rule that came out of it — INSTRUMENT READS BEFORE ADDING RETRIEVAL — is why this module exists and why ranking work (#349, #442) is gated behind it.

SURFACE: `techne audit` (`cli.py`, text + `--json`). Four functions, all read-only over `context_injections` + `observations`, all accepting `since_days`:

- `injection_utilization` — per-source volume and token cost. What the rails SPENT.
- `read_write_ledger` — read-vs-write ratios per domain. #329's original audit, re-runnable.
- `edit_rail_attribution` — did a codex edit-rail injection precede an edit to a file/symbol it named?
- `recall_attribution` — did the agent go on to CITE an injected knowledge id (`techne#237` / `knowledge#956`)? This is #416, #329's deferred join, shipped in #560.

## THE THING TO UNDERSTAND BEFORE QUOTING ANY NUMBER FROM HERE

**Every attribution figure is a FLOOR, not a measurement of usefulness.** An explicit citation is strong evidence a fact was used; its absence is WEAK evidence it was not, because most use of a recalled fact never names it. A low `cited_pct` means "we cannot see whether these mattered" — NOT "these did not matter". The docstrings say so; this card says so because a number lifted out of context loses its caveat and someone will delete a rail with it.

Live figures as of 2026-08-16 (all-time): 1,601 injections analysed, 28 cited in the tight window (1.7%), 166 cited anywhere in-session (10.4%, a deliberate CEILING), 746 distinct items injected of which 639 were never cited (85.7%).

## INVARIANTS

- **TWO WINDOWS, AND BOTH ARE DELIBERATE.** `window` = within N following actions AND M minutes, so a citation plausibly follows FROM the injection. `session` = anywhere later, which OVER-credits (the agent may have reached the id via its own recall call, or been re-shown it) and exists only to bound how much the tight window could be missing. Report both or neither; a single number invites the wrong reading.
- **THE DENOMINATOR IS `attributable`, NOT `injections`.** Sessions that took an injection and then produced NO observations cannot be scored either way, and there are a lot of them — `unobserved_sessions` was 309 of 357 sessions' worth at last count. Dividing by all injections reports a capture gap as agent indifference. #562 is the cost side of that same population.
- **ECHO TOOLS CANNOT EARN CREDIT.** An observation that is the store quoting its own output back (a recall result containing the id it just returned) must not count as the agent citing it — it still consumes a window slot, but it scores nothing.
- **THE FLAG AND THE COUNT ARE ONE FACT.** `_DOMAIN_READ_TOOLS` is the single source: the ledger counts through it and `mcp_read_tool` asks through it, so they cannot disagree by construction. They WERE two facts — the predicate asked "is a tool named `<domain>_*` registered?", a naming convention, while the counters name tools that do not match their own domain prefix at all (`techne_archivist_query`, `pattern_search`, `pattern_related`). They agreed on the boolean only by luck of which tools existed. Demonstrated by Prudence: seed reads through `techne_archivist_query`, drop `archivist_search`, and the panel prints "no MCP read tool — not visible to this ledger" over a dict holding `read: 7` — the count discarded and the operator told the opposite of the truth, the same inversion one bullet down through a different door.
- **`mcp_read_tool` IS DERIVED FROM THE TOOL REGISTRY, NEVER FROM A LIST OF NAMES.** The first attempt at this invariant was `domain in DOMAIN_NAMES` — a CONSTANT WEARING A DERIVATION'S CLOTHES, since both call sites pass literals that are in that tuple forever, so a hardcoded `False` had simply been replaced by a hardcoded `True`. Proved by removing `librarian_search` from `TOOL_HANDLERS`: the tool was gone, the function still said `True`, and the whole suite stayed green (Prudence, #725 r4). It consults `TOOL_HANDLERS` now, and the test's teeth are the REMOVAL, not the assertion. The import is lazy on purpose — `mcp_server` imports from `core`, never the reverse.
- **`mcp_read_tool` IS DERIVED, NEVER HARDCODED.** It separates "0 because agents ignore an existing tool" (a real behavioural signal — this seam's founding finding was `pattern_search` never called at all) from "0 because there is nothing to call" (ledger-invisible, not neglect). Getting it wrong INVERTS THE MEANING OF EVERY ZERO in the report. It was a hardcoded `False` for librarian beside a PREFIX MATCHER that had already started counting once #724 added `librarian_search` — the ledger had the number and printed "no MCP read tool" anyway, for a tool the docs tell operators to call. A hardcoded boolean beside a derived count is two answers to one question and drifts the moment the surface grows (#727, found by Prudence).
- **EVERY DOMAIN NEEDS ITS OWN READ TUPLE, INCLUDING THE ARCHIVIST.** `archivist_search` was counted by nothing — three of the four domain-named tools landed in the ledger and the archivist's vanished. The bite does not need an archivist row: when a read MIGRATES from `techne_recall` to `archivist_search`, which the docs now tell operators to do, `memory.read` falls and the panel reports a read-path DECLINE that is actually a read-path migration.
- **THE PANEL IS THE ONLY THING AN OPERATOR SEES, SO SOMETHING MUST RENDER IT.** Every ledger test asserts the dict `read_write_ledger` returns; none rendered it, so `techne audit` died with a NameError partway through the panel while the full suite stayed green at 3367. A shallow smoke test now runs the command and asserts every domain is named.
- **THE READ TUPLES ARE EXACT MATCHES, SO A NEW TOOL MUST BE ADDED TO THEM.** `_ARCHITECT_READ` missed `architect_search` for the same reason, and the failure is the nasty direction: successful adoption reads as `never queried`, i.e. the ledger reports neglect at precisely the moment the tool is being used. A test asserts the domain-named tool is counted; the older test that asserted the stale constant is why the suite stayed green through the regression, and it now asserts the DERIVATION instead — a test pinning a constant cannot notice the constant going stale.
- **THE PER-ITEM TABLE IS WHERE THE ACTION IS.** `items` gives encounters vs citations per injected id. An item with many encounters and zero citations is EITHER load-bearing-and-silent OR pure token cost, and no automated signal can tell those apart — only an operator can.

## KNOWN GAPS

- **THE COUNTERFACTUAL IS UNMEASURED AND IS techne#682 — not #105, not #416 (corrected 2026-08-19).** "Would it have happened WITHOUT the injection" is the question both attribution figures fail to answer, and four source sites claimed it was tracked, by two different numbers, neither of which is it. #105 is the EVIDENCE GATE (does an agent's CLAIM have ledger backing — a different question, and shipped); #416 is closed and built the PROXY, deferring the judge. One of the wrong pointers was in `techne audit`'s operator-facing output. Found while closing #105 for the #647 Tier 8 pass, which would otherwise have left three comments citing a closed issue for a live problem.
- The LLM-judge half of #416 is deliberately unbuilt. The proxy is free, deterministic and CI-runnable; the judge costs model calls and should be reached for only where the proxy is ambiguous (relevant injection, turn happened not to act on it).
- Nothing here scores the SESSION-START rail's prose blocks — only id-bearing hits.
- `recall_attribution` was invisible to `codex_search` when this card was written (#595), which is part of why it was nearly rebuilt from scratch. If you are reading this card INSTEAD of grepping, that is the intended path (techne#812).
