# search / embeddings — hybrid FTS + vector recall

TRUST IS A FILTER, NOT A RANK PENALTY (techne#501). `knowledge.status` is current | uncertain | archived, and `_cascade_uncertain` flips live dependents to `uncertain` when a trigger is superseded. Only `archived` ever filtered; `uncertain` merely fed `decay_score` as — in this module's own words — "a tiebreak/penalty, not a primary signal", default weight 0.1. So a memory we are ON RECORD AS NOT BELIEVING still surfaced, still injected, and still read to the agent as true, just slightly lower down. That is the collapse the distinction exists to prevent: a CONFIDENCE answers "how sure" and belongs in ranking (we already have `confidence` + `confidence_numeric` for that); a STATE answers "may this be acted on" and belongs in a filter. `include_uncertain` now gates both channels — FTS and vec, deliberately together, since a per-channel divergence would make an uncertain row reachable by vector and not by FTS, which is worse than either. ITS DEFAULT IS FAIL-CLOSED (False), unlike `include_archived`'s permissive default, and the asymmetry is deliberate because this one is FREE: measured 2026-08-18, all 1091 knowledge rows are `current` and `knowledge_deps` is empty, so the cascade has never fired in production. Filtering by default changes nothing today and protects the moment #443 populates the deps. AUTOMATIC RAILS FILTER, EXPLICIT SURFACES TAG: `techne_search` and `techne search` pass `include_uncertain=True` and render the row's `status`, because the reader ASKED — injection rails do not, because nobody chose to look at what they surface. The vec row now carries `status` too; it did not before, so a tagged explicit search could have returned a vec-only hit with nothing to tag it by.

THE PER-ROW CHARACTER CAP IS A DEFAULT, AND IT USED TO BE A CEILING — WHICH MADE A CONFIG KNOB INERT (techne#842). Every result row is truncated in this module before any caller sees it, and `_ROW_CHAR_CAP = 500` was applied unconditionally at all six sites. So `hooks.per_turn_recall_chars` — whose own comment says it "decides whether a multi-step SOP arrives as a procedure or as its title" — governed nothing above 500: the rail asked for 600 and search had already cut the row to 500, and the hook then CLAMPED its own request to `_SEARCH_ROW_CEILING - 1` to keep the arithmetic self-consistent, encoding the bug as a contract. The second consequence was worse than the first and is the reason the fix is not just "raise the number": a row cut to exactly the cap reads as WHOLE to `_truncate_for_injection`, whose test is `len(content) <= limit`, so the "…" that tells the agent something was withheld was suppressed at EVERY cap — measured absent at 600, 500 and 200. Truncation that announces itself degrades; truncation that lies presents a fragment as the entire memory. `search()` now takes `row_chars`, threaded to `search_fts` and `search_vec`, and the rail asks for `per_turn_recall_chars + 1`: THE +1 IS LOAD-BEARING, not defensive rounding — it is what leaves the marker something to detect, and dropping it restores the silent-fragment failure while every length assertion still passes. THE KNOB MOVES KNOWLEDGE ONLY, and the asymmetry is the design rather than an unfinished edge: the four thread/observation sites stay pinned to `_ROW_CHAR_CAP`. Those are the tool ledger — mostly shell echoes — so letting them ride the same knob would grow the injected payload by transcript instead of by the curated row the operator raised the cap to get. Both halves are pinned by source-level tests as well as behavioural ones; the ledger pin and the knowledge pin are separate tests on purpose, since a failure of each means the opposite thing. AND A SOURCE PIN IS NOT A WITNESS FOR A BINDING — the first cut of this change said the VEC channel could not be driven in the default environment, so a name-pin was its only guard, and Prudence falsified both halves in one move (#869 r2). Rebinding `_cap = _ROW_CHAR_CAP` inside `search_vec`, which deletes the entire fix on the channel this card elsewhere calls the one that serves the head of the page, left 4,011 tests passing and BOTH source pins green: they assert the slice expression reads `_cap` and never that `_cap` holds `row_chars`, and the binding is the fix. The premise was wrong too. `sqlite_vec` loads and the model is cached, so a behavioural vec witness costs one `backfill_vectors()` call and 0.63 s — measured, not estimated. It lives in `tests/eval/test_row_chars_vec_channel.py` under the `eval_vec` marker so it runs in the CI leg that installs `.[dev,codex,vectors]` rather than skipping in the legs that do not, since a guard that skips where it should run witnesses nothing. The general form, worth more than the instance: pinning the NAME at a call site tests the spelling, and any test whose subject is a variable's VALUE has to read the value. THEN THE SAME SHAPE APPEARED ONE WIRE FURTHER OUT (#869 r3), which is why this paragraph is longer than the defect deserves. With both endpoints witnessed — a direct `search_vec` test and an end-to-end `search()` test — deleting `row_chars=row_chars` from `search()`'s own `search_vec(...)` call was STILL green across the full suite, `eval_vec` and `crash`. The direct test bypasses `search()`; the end-to-end one never called `backfill_vectors`, so `vec_results` was empty and it silently measured the FTS page. Two tests covering both ends of a wire do not cover the wire. `search()` is what the per-turn rail calls, so that one deletion failed all three of #842's claims at once on an `fts+vec` row at the head of the page: delivered 500 rather than the requested 1201, marker suppressed, `chars_dropped` back to 0. The guard now drives `search()` after a backfill and asserts all three together, because they fail together. WHAT THE VEC SITE REPORTS AS `content_chars_total` IS ALSO ONLY WITNESSED END-TO-END: changing it to the delivered length (`len(k[2][:_cap])`) survived everything until that test existed, while the identical mutation at the FTS site already died — an asymmetry that is the signature of a channel reachable by only one path in the tests.

A KNOWLEDGE ROW CARRIES ITS PRE-TRUNCATION LENGTH, BECAUSE THE CALLER CANNOT RECOVER IT (techne#853, repaired by #842). `search()` cuts before any caller sees a row, so a consumer differencing against what it was handed measures the cut it can see rather than the content the reader lost. That was merely misleading while the cap was a hidden 500; #842 made it useless, because the per-turn rail now asks for `cap + 1` and the difference collapsed to the marker's width — measured 2/4/2/2 at caps 200/450/1200/2000 on a 3,199-char row whose true losses are 3000/2752/2000/1200. A CONSTANT IS WORSE THAN A WRONG NUMBER here: #853 was bought so that raising or lowering `per_turn_recall_chars` could be evaluated from data, and a constant answers every cap identically, which is precisely the question it exists to answer. So both knowledge sites now emit `content_chars_total` alongside the truncated `content`, and the rail differences against that; the test asserts MOVEMENT across caps as well as exactness, since a regression to any fixed value is the failure mode. Consumers that do not supply the key fall back to the delivered length and under-report rather than raise. IT IS A PUBLIC OUTPUT FIELD, not an internal one, and the card says so because nothing else does: `_techne_search` returns these rows raw and `mcp_server` `json.dumps` them, so `content_chars_total` reaches the model on every `techne_search` at roughly 30 characters per row. That is additive and arguably useful — the agent can see the row was cut rather than inferring it from a marker — but it is a surface, and a surface nobody documented is one the next change breaks silently.

RESULT-ROW CONTRACT, AND `type` IS DELIBERATELY ABSENT (techne#579). A row carries TWO notions of kind and they were once ONE key, which made the wrong reading the obvious one: `source_table` is the table it came from (thread | observation | knowledge), `knowledge_type` is the knowledge row's OWN kind (fact | decision | procedure | evaluation | document_card | pattern), present on knowledge rows only. The old single `type` held the FIRST of those and cost two live bugs. #565: the per-turn pull-only guard shipped as `[r for r in rows if r.get("type") not in PULL_ONLY_TYPES]` — it passed nothing and blocked nothing, because `type` was always the literal "knowledge"; a fail-without-fix test caught it, review did not. #566: `_build_context` rendered `[{r.get("type")}]`, so EVERY injected line read `[knowledge]` regardless of kind, collapsing decision-vs-evaluation exactly where the agent decides how much to trust the line. THE KEY IS REMOVED RATHER THAN ALIASED, and that choice is the fix: an alias preserves the trap for whoever reaches for the obvious name first, and "the natural code is the broken code" IS the defect. A stale consumer now raises KeyError at its own call site — loud, and in the right place — instead of silently comparing against a plausible wrong string. `_techne_search` returns these rows straight to the agent, so this is an agent-facing surface too; `source_table` + `knowledge_type` is honest where `type` was not. The survey that preceded the change found all eight non-test consumers were using `type` CORRECTLY as the table — nobody was broken, the NAME was the defect.

NEITHER CHANNEL CAN ANSWER "DO WE KNOW THIS AT ALL" — WHICH IS WHY `has_direct_match` EXISTS (techne#552). The ladder's S5 outcome has to tell "we have worked on this" apart from "we have never heard of it", and BOTH obvious signals in this module were measured dead before a third was written. DISTANCE cannot: a nearest-neighbour query returns k rows however far away they are, and on the live store the nonsense query "zzzqqxx" produced a NEARER top neighbour (0.961) than a real query about work done that same day (0.974) — there is no cutoff between them, so any threshold would have been a number invented to make a feature look like it worked. `match_source` cannot either, and the reason is the vec-first union documented above: fusion fills the page from the vector channel first, so "tier ladder recall archivist" returned 10 FTS rows through `search_fts` alone yet 10/10 `vec` through `search()`. THE MEASURED 10/10 IS PRE-#827 — the floor now guarantees the lexical channel some of the page, so the ratio is no longer 10/10. THE CONCLUSION IS UNCHANGED AND `has_direct_match` IS STILL REQUIRED, BUT NOT FOR THE REASON A FIRST DRAFT OF THIS SENTENCE GAVE (Prudence, #829 r1 nit 6). It is NOT true that a query with nothing lexical behind it still yields `fts` rows — if `search_fts` returns nothing the floor is 0 and no row carries `"fts"` at all, so the presence of a reserved slot is weak evidence of lexical evidence, which is closer to the thing #552 said `match_source` could not be. What actually carries the argument is a difference in QUERY CONSTRUCTION between the two: `search_fts` runs the #70 OR-fallback, while `has_direct_match` deliberately runs implicit-AND with NO OR-fallback. A reserved floor slot can therefore be filled by a row matching a SINGLE term of the query — exactly the row `has_direct_match` exists to reject. `match_source` measures FUSION, not matching, and reading it as a relevance signal is the trap in either regime. So `has_direct_match` asks the question directly: `prepare_fts_query` + one MATCH at LIMIT 1, with NO #70 OR-fallback and NO vector channel. An empty result is a fact about the store rather than a score. ASK IT OF `knowledge`, NEVER `all`: with `capture_bash` on, every term an operator types to TEST recall lands in the observation ledger within seconds, so `all` matches the probe itself — that silently defeated this check during development ("zzzqqxx" matched 6 observations, every one of them the test). A missing FTS table returns False rather than raising, because making recall claim "no experience" is a louder and more misleading answer than declining to characterise the result.

WHAT: recall over knowledge/threads/observations = hybrid BM25 (FTS5) + vector (sqlite-vec, vec0). search()/search_vec() in core/search.py; embedding-backend abstraction in core/embeddings.py.
MMR — CODE EXISTS, NO CONFIG SURFACE (techne#420): `_mmr_reorder()` is implemented and `_rerank`/`search_fts` accept `mmr_lambda`, but every live caller leaves it at the `0.0` function default, so the λ=0 guard returns at search.py:81 and ordering stays pure relevance. THE `search.mmr_lambda` CONFIG KNOB WAS REMOVED — parsed, defaulted to 0.3 and serialized while reaching no search function, so it read back correctly and did nothing. FIVE exits return the input unchanged: empty/limit<=0 (:77), λ=0 (:81), no numpy (:86), no embedding backend (:98), embed raised (:112); `sqlite-vec` gates NONE of them — it indexes `search_vec`, while MMR reaches the backend via `_get_embedding_model()`. WHERE A RE-PLUMBING MEASUREMENT BELONGS: the `eval-vec` CI leg, which already has what it needs — installs `.[dev,codex,vectors]` (numpy + model2vec on 3.14) with `potion-base-8M` pre-cached, and its `search(use_vectors=True)` path runs through `_mmr_reorder`. MEASURE VIA `search_fts` DIRECTLY, not through `search()`: `_mmr_reorder` reorders only the FTS channel, and the vec-first union walks `vec_results` first, so for any row in BOTH channels the vector order wins and MMR's effect is discarded — through `search(use_vectors=True)` only the FTS-only tail and `_rerank`'s truncation still show it. Since #827 that tail is a RESERVED slice rather than whatever survived truncation, which makes the residual effect observable at all but does not change where to measure. `tests/eval/test_ranking_ablation_vec.py` already calls `search_fts` directly. The deterministic `eval`/`eval_gate` legs install `.[dev,codex]` only, so they lack numpy and cannot observe MMR at any λ.
FUSION (techne#401/#402) — VEC-FIRST UNION, **NOT RRF**: vector hits come first (ascending distance, already sorted by search_vec), then FTS-only hits appended in search_fts's order. A row in BOTH channels keeps its vector position; agreement is recorded as provenance (`match_source: fts+vec`, `fusion: vec_first`), NOT as a rank boost. RRF was REMOVED — the #399 ablation showed its rank-sum buries a strong single-channel (vector-only) hit under lexically-tempting FTS distractors: paraphrase recall@10 0.667 vs 1.0, MRR 0.144 vs 0.546, while only TYING on exact/filter/negative. `_rrf_fuse`/`RRF_K` are deliberately RETAINED in the module as an unused library primitive (the #399 ablation arm) — do NOT read their presence as "RRF is live".

AND THE UNION RESERVES A TAIL FLOOR FOR THE LEXICAL CHANNEL, OR IT HAS NO LEXICAL CHANNEL AT ALL (techne#827). As shipped, #401 appended the whole vector channel, THEN the FTS-only hits, then truncated with `out[:limit]` — so a vector channel that filled the page discarded every lexical-only hit before any caller saw it. That is the normal case, not an edge: on a 2,619-row knowledge store the vec channel always fills a 10-row page. MEASURED on the live store, 15 identifier-shaped queries at limit=10: 108 FTS-only hits, 108 dropped, 0 survived. `techne_recall("PR 815")` returned outcome `found` while returning none of the six knowledge rows whose text contains "815", offering PR #402 and #439 instead — and all three read paths (techne_recall, techne_search, the per_turn_recall rail) land here, so exact-identifier recall — PR numbers, commit shas, symbol names, config keys — was answered by cosine distance alone. THE FIX REACHES ONLY TWO OF THOSE THREE, and the card says so rather than letting the list imply otherwise (#829 r3): the rail calls `search()` at `limit = per_turn_recall_limit * _RESEND_OVERFETCH` = 15, not 5, then cuts to 5 itself after dedup and the relevance floor — so the TAIL-reserved row lands at index 14 and the rail's own `[:k]` usually drops it before the session sees it. Cost is unaffected (measured at limit=15, floor 1: paraphrase r@10 1.0 / MRR 0.546); delivery on that path is not fixed, and belongs with techne#831. `_fts_floor(limit, n_fts_only)` reserves ONE slot of the page tail at any limit above 1, and 0 at limit=1 where there is no room. THE SIZE IS A MEASUREMENT AND THE FIRST CUT GOT IT WRONG (Prudence, #829 r1): a `limit // 3` floor was proposed on the argument that a minority slice is cheap, and the eval leg the default suite deselects (`pytest -m eval_vec`) says otherwise — floor 0 and floor 1 both hold the paraphrase arm at recall@10 1.0 / MRR 0.546, while floor 2 and floor 3 both drop it to 0.833 / 0.528 by truncating gold `g385_dbpool` off the vec head at rank 9 and replacing it, on a zero-token-overlap query, with lexical distractors. The gate still passed at 0.833 against its 0.8 floor, but retrieval_gold.yaml:97-99 reserves that margin for cross-machine BLAS drift, so spending it deterministically would leave the next real wobble looking like flake. So: vectors hold the head, the paraphrase win #401 bought is measured intact AT FLOOR 1, and the floor does NOT scale with the page — widening it requires re-running that ablation. The cost is not always a pure-vec row either: an `fts+vec` row can be the one displaced, and it cannot be rescued into the tail because `fts_only` excludes every vec key. A floor of 0 (channels agree, or nothing lexical-only) returns the identical pre-#827 page. WHAT THE FLOOR DID NOT BUY ON ITS OWN, AND HOW THAT WAS CLOSED (techne#831, FIXED): making the lexical channel REACHABLE is not the same as retrieving a KNOWN entry by its identifier. At floor 3 the live queries "issue 814" and "ae219b5" reached knowledge #1810; at floor 1 the single slot went to a raw observation instead. That shortfall was a RANKING defect, not a slot-count one — AND THE RANKING PATH IS NOT THE ONE THIS CARD DESCRIBED BEFORE (Prudence measured it dead, #934 r1; the card claimed ONE POOL over all three tables plus a shorter-document BM25 advantage, and neither exists). There is no single pool: `_fts_match_rows` queries each table under its OWN `LIMIT candidate_limit` (search.py:336/:363/:412), so the curated layer has its own quota and the corpus ratio cannot starve it out of the candidate set. `_rerank` then min-max normalises `rank` WITHIN each `source_table` (:252-272, techne#56, added for exactly this reason), so each table's best row reaches `_combined` at `_norm_bm25 = 1.0` and the shorter-document advantage is cancelled before the tables compete. WHAT DECIDES IT IS THE CONFIDENCE-DECAY TIEBREAK (:285-286, techne#214, weight 0.1): `_knowledge_decay_score` returns a flat 1.0 for any row without `confidence_numeric`, so an observation collects +0.100 against a `medium`-confidence knowledge row's +0.060 — `_combined` 1.1000 vs 1.0600 at equal recency and equal normalised BM25. THAT IS THE WIDE CASE AND #1810 IS NOT IT: `medium` is only the default (knowledge.py:63), while #1810 is `high`/0.9 and collects +0.090, so the real margin on the query this card names is 0.0100 — measured on "issue 814", observation #35460 at 0.9988 against #1810 at 0.9888, the entire delta in the decay term (Prudence, #934 r2), and on four of six identifier queries the BM25 and recency deltas are both exactly 0.0000. THAT FIGURE DOES NOT DRIFT, and the reason is a schema divergence worth knowing: the decay term is confidence TIMES age (`confidence_numeric * 0.5 ** (days/30)`), but #1810's `last_confirmed_at` is NULL — as it is for 2,823 of 2,914 live knowledge rows — so it takes `decay_score`'s no-timestamp branch and never decays. `last_confirmed_at` USED TO BE `NOT NULL DEFAULT CURRENT_TIMESTAMP` in the CREATE TABLE while a migrated store had plain nullable `TIMESTAMP`, so a FRESH install and a migrated one ordered this term differently at the same schema_version (techne#938). FIXED: the declaration now matches what the v5 ALTER can produce -- nullable, no default -- and every INSERT INTO knowledge sets the value instead, so the two shapes agree. The 2,823 rows already NULL are deliberately NOT backfilled, because that re-ranks every existing install and needs its own measured decision. Where the timestamp IS set (91 rows here), age WIDENS the margin toward 0.1000 and a stale `high` sits wider than a fresh `medium`. The code comment at :282-284 is scoped honestly ("ordering among non-knowledge rows is unchanged"); the CROSS-TABLE consequence is what no card recorded. The ~16:1 corpus ratio (re-measured 2026-09-15: 46,489 observations, 2,904 live knowledge, 2,458 threads) still pushes the same way, but as ORDER STATISTICS — the best of 20 drawn from 46k is better-selected than the best of 20 from 2.9k — so a wider floor buys more tickets without changing the draw. `_curated_first` therefore ORDERS the lexical tail so a `knowledge` row takes the reserved slot when one matched at all. MEASURED on the live store, six identifier-shaped queries at `table="all"`, limit=10: a curated row held the reserved slot 1/6 before and 6/6 after, and "issue 814" and "ae219b5" reach #1810 again — what floor 3 bought, without the paraphrase cost that got floor 3 rejected. IT REORDERS, IT DOES NOT FILTER, and that distinction is load-bearing: an identifier that exists only in the raw trace still reaches the caller, and non-curated rows still spend the slack a thin vec channel leaves. A curated-only filter would delete the only answer in exactly the case where it is the only answer. The partition is STABLE on both sides, so BM25 order survives within each — this reorders the tail and never reranks. THE FLOOR STAYS AT 1: this spends no head slot, which is the whole reason it is affordable where widening was not. ONLY THE limit=10 ARM CAN SHOW THE COST, so read the other two as context rather than as reassurance (#829 r4). The cost is `g385_dbpool` at vec-rank 9 being truncated off the head, which needs the head budget `limit - floor` to fall below 9: at limit=5 the gold is off the page at ANY floor, so that arm is FLAT everywhere; at limit=15 it is flat through floor 6 and only bites at 7. "Identical at limit=5" and "identical at limit=15" are therefore true and nearly uninformative. THE TRAP THIS CREATES, stated because the card foregrounds 15 as the rail's real page: a future widener who re-runs the ablation at 15 sees a clean 1.0 / 0.546 up to floor 6 and ships a regression limit=10 would have caught. Re-run the limit=10 arm. A thin vec channel lets the tail spend the slack rather than returning a short page. THIS IS #401's OWN CANDIDATE 4, which the module comment had named as the reason `_rrf_fuse` was kept.
BACKEND (techne#601/#602): ONE interface (EmbeddingModel) over TWO backends — fastembed (TextEmbedding, MiniLM-384) OR model2vec (StaticModel, potion-base-8M, 256-dim, numpy-only static). config `search.embedding_backend=''` = AUTO-SELECT (NOT disabled): model2vec on Python 3.14+ or when fastembed is absent, else fastembed.
DTYPE: `embed()` yields float32 rows on both backends. fastembed below 0.9 returns float64, so the fastembed path casts each row (issue 536; 0.8.1 float64 and 0.9.0 float32, measured 2026-10-08).
CONSTRAINT — fastembed is UNUSABLE on Python 3.14: its dep onnxruntime ships no 3.14 wheel. On 3.14 the live backend is model2vec/potion (dim 256). Do NOT try to "enable fastembed" on 3.14 — it cannot load.

MODEL2VEC IS LOADED WITHOUT IMPORTING MODEL2VEC (techne#1096). `_build_backend`'s model2vec branch first calls `core/static_direct.load()`, which reads the cached `config.json` + `model.safetensors` + `tokenizer.json` with `tokenizers`/`safetensors` and repeats `StaticModel.encode`'s steps (char pre-cut, no special tokens, unk dropped, 512-id cut, mean, float64 zero row, per-1024 batch, `norm + 1e-32`). Vectors are bit-identical to model2vec 0.9.0 and the backend keeps the name `model2vec:<model>`, so `_ensure_vec_backend_identity` sees no swap. It exists because `import model2vec` (huggingface_hub, joblib, tqdm) cost ~400 ms of every per-turn hook process; measured hook wall 743 → 333 ms median. It applies to EVERY caller, not just hooks: one construction point means stored and query vectors always come from the same code. Anything it cannot reproduce exactly (vocabulary-quantized `weights`/`mapping` tensors, a sentence-transformers layout, another `model_type`, a vocab/table mismatch, a cache miss) raises `Unsupported` and falls through to model2vec with a debug log, so downloads still happen only there and only under `allow_download=True`. `_model2vec_importable()` is now a `find_spec` check, since a real import in `backend_available()` would spend the same 130+ ms. `tests/test_static_direct.py` pins equality against the installed model2vec; a model2vec release that changes `encode` fails there first.
THE QUERY IS EMBEDDED WITHOUT NUMPY, AND sqlite-vec IS LOADED WITHOUT IMPORTING ITS PACKAGE (issue 1217). Every per-turn hook is a fresh process, and after techne#1096 the query embed still cost numpy (~55 ms, imported twice over: by `static_direct` and by `import sqlite_vec`, whose `__init__` runs `import numpy.typing`) plus reading the whole 30 MB table to embed one prompt. `_query_embedding` now asks `core/query_embed.embed_query_bytes` first: it memory-maps `model.safetensors`, reads only the query's rows with `struct.unpack_from`, and returns float32 `bytes`, which `search_vec` passes to sqlite-vec as they are (an ndarray still works). THE BYTES ARE THE NUMPY PATH'S BYTES, NOT AN APPROXIMATION: each step is rounded to float32 in numpy's order (row-by-row axis-0 sum from 0, then numpy's pairwise sum for both norms), and a double result rounded to float32 is the correctly rounded float32 result for +, *, / and sqrt. Measured on a 71,900-observation store copy: 3,509 store texts byte-equal (8M, and 1,509 each on base-32M and retrieval-32M, which are 512-dim), 510 `search()` pages byte-equal, `eval_vec` metrics byte-equal. `tests/test_query_embed.py` pins it against the installed numpy; a numpy that changed its summation order would fail there. IT ANSWERS ONLY WHERE `static_direct` WOULD, and only for float32 tables: anything else (fastembed, a quantized or F16 table, a cache miss, a vocab/table mismatch, an unk token not in the vocab, no `tokenizers`) returns None and the numpy path runs, so the `allow_download=False` / `_VEC_CHANNEL_ERROR` contract below is untouched. The model is the built singleton's when there is one, else `_select_backend(None)`, the same choice `_get_embedding_model` would make. IT RUNS ONLY IN FRONT OF THE STOCK RESOLVER (`_get_embedding_model is _STOCK_EMBEDDING_RESOLVER`): a caller or test that replaced the resolver gets its own embedder. THE INDEX-STAMP GUARD SEES THE FAST PATH'S MODEL: the fast path never builds the embeddings singleton, so `query_embed` records the `(model2vec:<model>, dim)` it last embedded with (`served_identity()`), and `_index_backend_mismatch` (techne#1049) uses it when no singleton exists. Without it the guard would skip on every per-turn hook. `_reset_embedding_model` clears it too. The median token length (`np.median` over the vocab, ~35 ms) is cached in `$TECHNE_HOME/.query_embed.json`, keyed by snapshot folder and `tokenizer.json` mtime/size. `core/vec_ext.py` probes sqlite-vec with `find_spec` and loads `<package dir>/vec0` directly, using the package's own `load` when it is already in `sys.modules` (test stubs, backfill); the extension-load exit catches the same errors as before plus ImportError. Backfill and `vector_status` still import the package; they embed with numpy anyway. Hook median on that store, 9 runs each, interleaved: 341-345 ms on main, 259-264 ms here.

QUERY TEXT IS CLEANED WHERE IT ENTERS SQLITE OR THE EMBEDDER (techne#1249). `clean_query_text` maps NUL, the other C0 controls (tab, LF and CR excepted) and DEL to spaces and turns lone surrogates into U+FFFD (a valid surrogate pair held as two code points is joined). Before it, a NUL ended the FTS5 phrase literal at SQLite's C boundary (`unterminated string`) and a surrogate raised `UnicodeEncodeError` at bind time, out of every read path. It runs in TWO places and both are needed: `_fts_terms`, which every MATCH string built from a query passes through (search, documents, patterns, codegraph, the identifier pool, the phrase seat), and `_query_embedding`, the one place a query is embedded. A caller that also WRITES the query (the recall hooks log it as the trigger) must clean its own copy: `recall_block` does, because a surrogate there made the best-effort log drop the row silently.

THE #70 AND-THEN-OR FALLBACK IS TWO HELPERS NOW, `fts_and_or_split(query, run, want=None, key=...)` returning `(and_rows, or_rows)` SEPARATELY, and `fts_with_or_fallback(query, run, want=None, key=...)` — the old merged-list shape, implemented as `fts_and_or_split` plus a concat-and-cap (issue #559, techne#1079). Both own the control flow (the #143 empty-query guard, the implicit-AND pass, the OR-of-terms pass); each caller's `run` closure owns its SQL, which differs by table, joins and status filter.
SINCE techne#1079 THE OR PASS TOPS UP A SHORT AND PASS, IT DOES NOT ONLY FILL AN EMPTY ONE. A single row matching every query term used to REASSIGN the whole result — the empty-AND-pass check was the only trigger — so it silently replaced every row that matched only SOME terms instead of ranking alongside them (the litestream/eval-quoting-its-own-gold-query bug the issue opened with). `want` is the caller's pool size (`search_fts`/the knowledge-conn search pass `candidate_limit`; `search_symbols`/`search_patterns` pass `limit`, since their `run` closure's own SQL already bounds each pass to `limit`); when the AND pass returns fewer than `want` rows the OR pass runs too. `fts_and_or_split`'s OR rows are deduped against the AND rows by `key` (a caller-supplied function — `(source_table, id)` for the two `search.py` callers, whose rows aren't table-scoped; bare `id` for `search_symbols`/`search_patterns`, which query one table) — NOT against each other, since `run` returns each row at most once per call. `want=None` (the default) is byte-for-byte the pre-#1079 behaviour: OR only on an empty AND pass, no cap, no dedup pass.
`fts_with_or_fallback`'s callers (`search_symbols`, `search_patterns`) do NO reranking, so AND-then-OR concatenation is the final order unconditionally — there is no score that could put an OR row ahead of an AND row for them. `search_fts` and `search_knowledge_conn` DO rerank, and that is why they call `fts_and_or_split` directly instead: see the next two paragraphs for why the two blocks must be reranked SEPARATELY rather than merged first.
`search_fts(table="all")` TOPS UP PER SUB-TABLE, NOT ON THE POOLED TOTAL (techne#1079, `_and_or_pools`). `_fts_match_rows(..., "all", candidate_limit, ...)` internally runs three separate `LIMIT candidate_limit` queries (threads/observations/knowledge) and concatenates them, so comparing the SUMMED row count across tables against one `want` lets one table's AND pass alone reaching `candidate_limit` (e.g. observations) satisfy the comparison even while another table's AND pass (e.g. knowledge) returned nothing, silently skipping that table's top-up. `_and_or_pools` calls `fts_and_or_split` ONCE PER SUB-TABLE instead, each with its own `want=candidate_limit`, then hands `search_fts` the two pools (`and_pool`, `or_pool`) to rerank. A single-scoped `table` was never affected — `_fts_match_rows` runs one query either way, so the pooled-total and per-table counts already coincided.
EACH FTS SUB-TABLE RANKS BEFORE IT FETCHES (techne#1092, `_fts_sub_table_rows`). The OR pass matches most of a table (p50 47,399 of 59,836 observations on the 2026-09-29 snapshot), and the old single statement (`FTS JOIN base ... ORDER BY rank LIMIT`) carried every matching row's content through the sort. Step 1 now sorts `(rowid, bm25)` alone and keeps `candidate_limit`; step 2 fetches those base rows by id (`json_each`). Knowledge's superseded/archived/uncertain clauses are on base columns, so its step 1 still joins `knowledge` to apply them BEFORE the LIMIT, sorting only `(rowid, rank)`; a filter applied after the LIMIT would return a short page. (`rowid IN (SELECT id FROM knowledge WHERE ...)` was measured and rejected: FTS5 takes the rowid constraint and re-runs the MATCH per id, 136 ms for one term.) Step 2 repeats the filter, and any id it cannot resolve sends that sub-table through the old single statement, so the page and every `rank` value equal the single-statement result. THE OR PASS DROPS TERMS MATCHING OVER HALF THE TABLE (techne#1093, `_drop_clamped_or_terms`), via `fts_and_or_split(..., run_or=...)`: only `_and_or_pools` and `search_knowledge_conn` pass a pruning `run_or`, the AND pass never prunes, and `search_symbols`/`search_patterns` keep plain `run` (small tables, nothing to win). The 50% is FTS5's IDF clamp (`idf <= 0`, i.e. `df >= N/2`, becomes 1e-6), not a tuning knob: at 20% the prune measured lossy. `N` is the FTS index's own row count (`<fts>_docsize`). If every term qualifies the query is left whole. The pruned result is kept only when it provably holds the full query's top `candidate_limit` rows: it must be full (else rows matching only dropped terms would fill the rest), and the bm25 gap at the LIMIT boundary must exceed `dropped terms x 2.2e-6` (`_CLAMPED_TERM_MAX_BM25`, the most a clamped term adds), else a clamped term decides a tie for the last slot. That guard exists because the 2026-09-29 snapshot had exactly that case: knowledge 3712 and 2202 tied once `the`/`and` were dropped, and the rowid tie-break swapped which one made the pool. Failing either check, the sub-table re-runs the full OR query. What remains different: rows that tie on every kept term can swap places inside the pool, and `rank` differs by the dropped terms' clamped contributions (max 3e-5 measured).
ONE CONNECTION, ONE sqlite-vec LOAD AND ONE QUERY EMBED PER `search()` CALL (techne#1094). `search()` opens the connection and passes it to `search_fts`, `search_vec`, the #1078 `_identifier_pool` and the #946 curated-pool `search_vec`; it embeds the query once (`_query_embedding`) and hands the vector to both `search_vec` calls, and `_ensure_sqlite_vec` probes `vec_version()` so the extension loads once per connection. It closes the connection in a `finally`. Before this each channel opened its own: 3.02 connections, 1.63 loads and 1.63 embeds per `search(all,10)` on the 2026-09-28 snapshot, each connection starting with a cold page cache. The standalone functions keep their signatures; `conn=` (and `query_vec=` on `search_vec`) are optional keywords, and without them each function opens and closes its own connection as before. `search_vec`'s four degrade exits are unchanged in behaviour but now sit in two helpers: the sqlite-vec probe (a `find_spec` since issue 1217), backend and model-resolve exits in `_query_embedding` (which returns None), the extension-load exit in `_ensure_sqlite_vec`. When `_query_embedding` returns None, `search()` still calls `search_vec`, which repeats the checks and returns []: on a model that cannot load, that path costs a second resolve and no embed, and it keeps a stubbed `search_vec` reachable in tests. The reads run in autocommit, so no transaction spans the channels. PRAGMA changes were measured and rejected in the issue: mmap, a 64 MB `cache_size` and `temp_store=MEMORY` on short-lived connections were no faster, and `ANALYZE` made `search(knowledge,15)` slower (19 to 24 ms p50).

THE MCP SERVER KEEPS ONE READ CONNECTION FOR ITS PROCESS'S LIFE (techne#1095). `search()` takes an optional `conn=`; with it, it runs on that connection and leaves it open. `mcp_server.main()` builds a `core/read_conn.ReadConnection` (512 MB `mmap_size`, `query_only`, sqlite-vec loaded on first use) and `techne_search`/`techne_recall` pass it through `_local_search`; `main()` closes it on exit. Nothing else builds one: hooks and the CLI are a new process per call, and a handler called outside `main()` (tests, the CLI) sees `_READER is None` and opens per call as before. Rules the code relies on: (1) no read transaction spans calls: reads run in autocommit and `run()` rolls back any transaction a call left open, so each call sees every write committed before it starts, and a `wal_checkpoint(TRUNCATE)` is never blocked by the server — that guarantee also depends on no cursor from `fn` outliving the call: `run()`'s rollback checks `conn.in_transaction`, which reflects an explicit BEGIN, not an unexhausted SELECT cursor, so a half-read statement still pins the WAL snapshot into the next call while `in_transaction` stays False; (2) every call first stats the path and compares `(st_dev, st_ino)` and `PRAGMA schema_version`/`user_version` with the values at open, and reconnects on a mismatch (`techne restore` `os.replace`-s a new file in, which an open connection would never see); (3) any `sqlite3.Error`/`OSError` on the cached connection drops it and reruns the call on a fresh connection, so the cache can cost a retry but never a tool call; (4) the server dispatches calls serially from its stdin loop, and the lock is non-blocking, so a second thread gets a fresh connection rather than sharing or waiting. mmap is address space, not heap: on the 2026-09-28 snapshot (247 MB) the mapping was 247 MB virtual and 96 MB resident, all clean file-backed pages the kernel can drop, which moved process RSS from about 106 MB to 192 MB after 392 warm `techne_search` calls.
AND ROWS AND OR ROWS ARE RERANKED IN SEPARATE BLOCKS, NEVER TOGETHER (techne#1079 v2 — THIS IS THE PART THAT SHIPPED, REGRESSED, AND WAS REVERTED). The first cut at this issue (#1081, techne#1079 v1) merged `and_pool + or_pool` into one list and called `_rerank` once. Measured on the 2026-09-28 03:30 snapshot: a short on-topic OR row's normalised BM25 + recency beat a long exact-match AND row's, dropping identifier queries that resolved at rank 1 from FTS-only search_fts to rank 2 or 3, and losing `reflect-drain --go techne.db` from the HYBRID `search()` page entirely (`@10` lexical-tail slot → miss) even though its FTS-only rank was untouched — the joint rerank changed which rows entered `search_fts`'s output at all, which then changed what `_fts_floor`'s tail had to work with. PR #1081 merged, was measured broken against the live store, and was reverted as #1084; techne#1079 reopened over it. THE FIX: `search_fts` reranks `and_pool` and `or_pool` with two SEPARATE `_rerank` calls — `and_ranked = _rerank(and_pool, limit, ...)`, then `or_ranked = _rerank(or_pool, limit - len(and_ranked), ...)` only if slots remain — and concatenates AND-first. Within `search_fts` and `search_knowledge_conn`, no OR row's score is ever compared against an AND row's, so precedence there is structural, not a side effect of recency/BM25 magnitudes — but this is a claim about THESE TWO FUNCTIONS, not the whole system: see the next paragraph for the one place it was still false. When `or_pool` is empty (the common case — most queries resolve on AND alone), `and_ranked` is computed from the exact same `and_pool` and `limit` the pre-#1079 single `_rerank` call would have used, so the page is BYTE-IDENTICAL to origin/main. `search_knowledge_conn` (the federation entrypoint) applies the same split-rerank-concatenate shape, with one shared `event_at` enrichment query covering both blocks before either is reranked. Every row either function returns is tagged `_match_pass: "and" | "or"` — the mechanism the next paragraph's fix depends on.
FEDERATION'S `merge_and_rank` RECREATED THE #1081 BUG ONE HOP FURTHER OUT, AND WAS THE ONE PLACE THE STRUCTURAL-PRECEDENCE CLAIM ABOVE DIDN'T REACH (Prudence, #1088 review Important 1). `search_fts` and `search_knowledge_conn` each keep their own AND/OR blocks apart, but `mcp_server._techne_recall`'s federation path pools `local_results` (from `search()`) and `remote_deduped` (one `search_knowledge_conn` call per remote) and used to make ONE `_rerank` call over the union — reuniting AND and OR rows from every store and re-normalising BM25 across them, exactly the shape that broke identifier ranking in #1081. Probe-measured: a stale long exact-match row and a fresh short partial-match row, correctly `[and, or]` through both producers, came out `[or, and]` through the old `merge_and_rank`. FIXED THE SAME WAY: `merge_and_rank` splits `local_results + remote_deduped` into two evidence tiers (the exact rule is `federation._second_tier`'s docstring, not restated here — see the next paragraph), reranks the first tier (from every store) as one block, then fills the remaining slots from the second tier (from every store) as a second block, and concatenates first-tier-first — the identical pattern as the two producers, one level up. SUPERSEDED BY techne#1089, two paragraphs down: the merge no longer reranks at all, but the tier rule survives as its tie-break between stores.
THE TIER RULE LIVES IN ONE PLACE, `federation._second_tier`'s docstring (techne#1079 review round 3; it was `merge_and_rank`'s until techne#1089 split it out) — read it there rather than here; this paragraph is the history, not the current rule, so it can't drift out of sync with the code. Three rounds, three different bugs, all shaped the same way: promoting or demoting a row by a SINGLE signal that doesn't capture "how much evidence does this row actually carry". Round 1 demoted every untagged row (`== "and"` / `!= "and"`) — a local hybrid page is mostly untagged `vec`/`fts+vec` rows, so a remote filling `limit` with AND rows could empty a federated page of local content (`team x10` where main gave `local x8, team x2`). Round 2 fixed that by demoting only an explicit `"or"` tag, but once `_as_page_row` (`search.py:1799`) started copying `_match_pass` onto `fts+vec` overlaps so those rows could be told apart from AND overlaps at all, an OR-tagged row with independent vector agreement (strictly MORE evidence than an untagged vec-only row) still got demoted below it. Round 3's `match_source != "fts+vec"` check is what actually captures "sole evidence is a partial lexical match" — the property both `_match_pass` alone and copy-vs-no-copy alone failed to express.
FEDERATION MERGES PAGES; IT DOES NOT RE-SCORE THE LOCAL ONE (techne#1089). Even with the tier split, `merge_and_rank` still ran `_rerank` (BM25 / recency / decay) over the local `search()` page, which is already fused: vec-first head, `identifier_head`, `curated_head`, the #827 `lexical_tail`. Re-scoring discarded that order and every reserved seat. Measured on the 2026-09-28 snapshot with NO remote rows, 40 real per-turn prompts, frozen clock: the page's #1 stayed #1 in 6 of 40, the page came back identical in 1 of 40, and 37 of 102 reserved seats kept their index. Each remote's rows also arrive ranked (by `search_knowledge_conn`). So the merge now keeps both orders: a local row tagged `reserved_slot` keeps its index, and every other seat takes the next row from one of the streams (the local page's unreserved rows, then one stream per remote store), choosing the smallest `(tier, position in own stream, stream)` among the stream heads, local first on ties. One remote and one tier means local, remote, local, remote. Only heads are compared, so no stream is ever reordered. With no remote rows the merged page IS the local page (40/40 identical, 102/102 seats kept on the same snapshot); remote rows take the lowest unreserved seats and never a reserved one. The rule and its edge cases are `merge_and_rank`'s docstring; `tests/test_federation_page_merge.py` pins both invariants end to end through `techne_recall`. Cross-corpus BM25 is no longer compared anywhere, so the old "remote corpus compressed toward the low end" caveat went with it.
RECALL'S PROVENANCE KEYS ARE PUBLIC, AND THE UNDERSCORE NAMES ARE DEPRECATED (techne#1102). The federation path tags each memory row `_store` (connection name, or `local`) and `_role`; `merge_and_rank` copies them through, `tiers.tier_of` and the local-only freshness filter read them. `mcp_server._public_rows` strips every other underscore key at the tool boundary and keeps these two (`_PUBLIC_UNDERSCORE_KEYS`), then `_with_public_provenance` copies them to `store` / `role` on the output copies only. TOPPED-UP OR ROWS COMPETE WITH AND ROWS ONLY ON THE COMBINED SCORE `_rerank` PRODUCES FOR THEIR OWN BLOCK, NEVER ACROSS BLOCKS. Inside `and_ranked`, `_rerank`'s normal recency×BM25+decay scoring applies exactly as before — an AND row that matches more terms does not automatically outrank another AND row on recency alone. The one thing separate-block reranking removes is cross-block competition: an OR row cannot score high enough to jump the AND block, because the two `_rerank` calls never see each other's candidates. MMR (`mmr_lambda`; see the paragraph above — no live caller sets it above 0) would, if ever revived, diversify within each block independently rather than across the merged pool; not measured, since nothing exercises it today.

AND THE HEAD RESERVES SLOTS FOR THE CURATED LAYER, BECAUSE THE TAIL FLOOR CANNOT REACH A ROW THE VECTOR CHANNEL FOUND (techne#946). #827 and #831 reserve and order the lexical TAIL, so between them they rescue a curated row the FTS channel matched. THE TWO REGIONS ARE DISJOINT IN THE PAGE AND NOT IN THE CANDIDATE SET, and this card said otherwise until Prudence measured it (#966 r1): the promotion pool is not deduped against `fts_only`, so a curated row the vector channel never fetched but FTS matched can be promoted into the head AND be the tail floor's only candidate — `seen` then empties the tail and the page comes back one row SHORT, having surrendered a head slot to seat a row `_curated_first` would have put in the floor slot anyway. Measured: 12 observations plus one lexical-only curated row, limit 10, 9 rows returned. A displaced row is therefore carried as OVERFLOW appended after the tail, where the closing `[:limit]` either drops it (the ordinary case, unchanged) or spends it refilling a short page. THE CANDIDATES COME FROM A SECOND, SCOPED ANN QUERY AND THE FIRST CUT DID NOT, WHICH MADE IT A RESERVATION IN NAME ONLY: `search_vec` is itself capped at `limit`, so the union's own `vec_results` hold at most `limit` rows across all tables and the curated row worth promoting was usually never fetched. Measured on the live store before that fix — 12 real queries at `table="all"`, limit 10 — mean curated rows per page 4.00 -> 4.08, one extra row across twelve pages. With a scoped `table="knowledge"` fetch of `deficit + in_head` (the surplus is the dedup buffer against curated rows already seated): 4.00 -> 5.00, and the per-page minimum 1 -> 3. WHY SLOTS AND NOT A SCORE PRIOR, which is a live disagreement rather than an obvious call: the architect store holds both sides — `Confidence-banded rerank` fuses a provenance weight into the score, `Relevance and trust as two fields, never fused into one number` answers that the fused number is undecomposable, so you cannot tell afterwards whether a row placed low because it matched poorly or because its source is trusted less, and cannot move one policy without moving the other. Both are shipped patterns in industry (Elasticsearch `function_score` and Vertex AI boost/bury for the prior; Google Cloud Search "crowding", default cap 3 per source, for the quota), and Google's own docs warn that undisciplined boost tuning degrades search with no documented safe range. The reservation is the decomposable form and rows say so: `reserved_slot` is `"curated_head"` (#946) or `"lexical_tail"` (#827), and ABSENT on a row that earned its place on rank — which is the field a ranking complaint is answered from. RANK FUSION IS NOT A SUBSTITUTE AND THE SAME SWEEP SETTLES IT: RRF took the best MRR on the worst recall tier, because it reorders what the page already holds and cannot surface what `all` never retrieved; stacking it on the reservation measured identical to the reservation alone.
