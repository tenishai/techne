# search / embeddings — hybrid FTS + vector recall

TRUST IS A FILTER, NOT A RANK PENALTY (techne#501). `knowledge.status` is current | uncertain | archived, and `_cascade_uncertain` flips live dependents to `uncertain` when a trigger is superseded. Only `archived` ever filtered; `uncertain` merely fed `decay_score` as — in this module's own words — "a tiebreak/penalty, not a primary signal", default weight 0.1. So a memory we are ON RECORD AS NOT BELIEVING still surfaced, still injected, and still read to the agent as true, just slightly lower down. That is the collapse the distinction exists to prevent: a CONFIDENCE answers "how sure" and belongs in ranking (we already have `confidence` + `confidence_numeric` for that); a STATE answers "may this be acted on" and belongs in a filter. `include_uncertain` now gates both channels — FTS and vec, deliberately together, since a per-channel divergence would make an uncertain row reachable by vector and not by FTS, which is worse than either. ITS DEFAULT IS FAIL-CLOSED (False), unlike `include_archived`'s permissive default, and the asymmetry is deliberate because this one is FREE: measured 2026-08-18, all 1091 knowledge rows are `current` and `knowledge_deps` is empty, so the cascade has never fired in production. Filtering by default changes nothing today and protects the moment #443 populates the deps. AUTOMATIC RAILS FILTER, EXPLICIT SURFACES TAG: `techne_search` and `techne search` pass `include_uncertain=True` and render the row's `status`, because the reader ASKED — injection rails do not, because nobody chose to look at what they surface. The vec row now carries `status` too; it did not before, so a tagged explicit search could have returned a vec-only hit with nothing to tag it by.

RESULT-ROW CONTRACT, AND `type` IS DELIBERATELY ABSENT (techne#579). A row carries TWO notions of kind and they were once ONE key, which made the wrong reading the obvious one: `source_table` is the table it came from (thread | observation | knowledge), `knowledge_type` is the knowledge row's OWN kind (fact | decision | procedure | evaluation | document_card | pattern), present on knowledge rows only. The old single `type` held the FIRST of those and cost two live bugs. #565: the per-turn pull-only guard shipped as `[r for r in rows if r.get("type") not in PULL_ONLY_TYPES]` — it passed nothing and blocked nothing, because `type` was always the literal "knowledge"; a fail-without-fix test caught it, review did not. #566: `_build_context` rendered `[{r.get("type")}]`, so EVERY injected line read `[knowledge]` regardless of kind, collapsing decision-vs-evaluation exactly where the agent decides how much to trust the line. THE KEY IS REMOVED RATHER THAN ALIASED, and that choice is the fix: an alias preserves the trap for whoever reaches for the obvious name first, and "the natural code is the broken code" IS the defect. A stale consumer now raises KeyError at its own call site — loud, and in the right place — instead of silently comparing against a plausible wrong string. `_techne_search` returns these rows straight to the agent, so this is an agent-facing surface too; `source_table` + `knowledge_type` is honest where `type` was not. The survey that preceded the change found all eight non-test consumers were using `type` CORRECTLY as the table — nobody was broken, the NAME was the defect.

NEITHER CHANNEL CAN ANSWER "DO WE KNOW THIS AT ALL" — WHICH IS WHY `has_direct_match` EXISTS (techne#552). The ladder's S5 outcome has to tell "we have worked on this" apart from "we have never heard of it", and BOTH obvious signals in this module were measured dead before a third was written. DISTANCE cannot: a nearest-neighbour query returns k rows however far away they are, and on the live store the nonsense query "zzzqqxx" produced a NEARER top neighbour (0.961) than a real query about work done that same day (0.974) — there is no cutoff between them, so any threshold would have been a number invented to make a feature look like it worked. `match_source` cannot either, and the reason is the vec-first union documented above: fusion fills the page from the vector channel before appending FTS-only hits, so "tier ladder recall archivist" returns 10 FTS rows through `search_fts` alone yet 10/10 `vec` through `search()`. The lexical evidence is real and simply crowded out — `match_source` measures FUSION, not matching, and reading it as a relevance signal is the trap. So `has_direct_match` asks the question directly: `prepare_fts_query` + one MATCH at LIMIT 1, with NO #70 OR-fallback and NO vector channel. An empty result is a fact about the store rather than a score. ASK IT OF `knowledge`, NEVER `all`: with `capture_bash` on, every term an operator types to TEST recall lands in the observation ledger within seconds, so `all` matches the probe itself — that silently defeated this check during development ("zzzqqxx" matched 6 observations, every one of them the test). A missing FTS table returns False rather than raising, because making recall claim "no experience" is a louder and more misleading answer than declining to characterise the result.

WHAT: recall over knowledge/threads/observations = hybrid BM25 (FTS5) + vector (sqlite-vec, vec0). search()/search_vec() in core/search.py; embedding-backend abstraction in core/embeddings.py.
MMR — CODE EXISTS, NO CONFIG SURFACE (techne#420): `_mmr_reorder()` is implemented and `_rerank`/`search_fts` accept `mmr_lambda`, but every live caller leaves it at the `0.0` function default, so the λ=0 guard returns at search.py:56 and ordering stays pure relevance. THE `search.mmr_lambda` CONFIG KNOB WAS REMOVED — parsed, defaulted to 0.3 and serialized while reaching no search function, so it read back correctly and did nothing. FIVE exits return the input unchanged: empty/limit<=0 (:52), λ=0 (:56), no numpy (:61), no embedding backend (:67), embed raised (:81); `sqlite-vec` gates NONE of them — it indexes `search_vec`, while MMR reaches the backend via `_get_embedding_model()`. WHERE A RE-PLUMBING MEASUREMENT BELONGS: the `eval-vec` CI leg, which already has what it needs — installs `.[dev,codex,vectors]` (numpy + model2vec on 3.14) with `potion-base-8M` pre-cached, and its `search(use_vectors=True)` path runs through `_mmr_reorder`. MEASURE VIA `search_fts` DIRECTLY, not through `search()`: `_mmr_reorder` reorders only the FTS channel, and the vec-first union (search.py:817-846) walks `vec_results` first, so for any row in BOTH channels the vector order wins and MMR's effect is discarded — through `search(use_vectors=True)` only the FTS-only tail and `_rerank`'s truncation still show it. `tests/eval/test_ranking_ablation_vec.py` already calls `search_fts` directly. The deterministic `eval`/`eval_gate` legs install `.[dev,codex]` only, so they lack numpy and cannot observe MMR at any λ.
FUSION (techne#401/#402) — VEC-FIRST UNION, **NOT RRF**: vector hits come first (ascending distance, already sorted by search_vec), then FTS-only hits appended in search_fts's order. A row in BOTH channels keeps its vector position; agreement is recorded as provenance (`match_source: fts+vec`, `fusion: vec_first`), NOT as a rank boost. RRF was REMOVED — the #399 ablation showed its rank-sum buries a strong single-channel (vector-only) hit under lexically-tempting FTS distractors: paraphrase recall@10 0.667 vs 1.0, MRR 0.144 vs 0.546, while only TYING on exact/filter/negative. `_rrf_fuse`/`RRF_K` are deliberately RETAINED in the module as an unused library primitive (the #399 ablation arm + a possible single-channel-floor fallback) — do NOT read their presence as "RRF is live".
BACKEND (techne#601/#602): ONE interface (EmbeddingModel) over TWO backends — fastembed (TextEmbedding, MiniLM-384) OR model2vec (StaticModel, potion-base-8M, 256-dim, numpy-only static). config `search.embedding_backend=''` = AUTO-SELECT (NOT disabled): model2vec on Python 3.14+ or when fastembed is absent, else fastembed.
CONSTRAINT — fastembed is UNUSABLE on Python 3.14: its dep onnxruntime ships no 3.14 wheel. On 3.14 the live backend is model2vec/potion (dim 256). Do NOT try to "enable fastembed" on 3.14 — it cannot load.
CHECK, DON'T ASSUME: the live backend is machine/python-version dependent and `embedding_backend=''` means auto — so read it from `techne vectors status`, never infer it from the (often empty) config value.
DEGRADE: vector search silently falls back to FTS-only when sqlite-vec/the backend is unavailable OR the vec tables are stale after a backend swap. Distances are normalized so model2vec L2 stays comparable to the fastembed baseline (tag_threshold ceiling is backend-dependent: potion tops ~0.59).
BUILD/REPAIR: `techne vectors backfill` embeds un-embedded rows (and does a full drop+re-embed on a backend/model swap via _ensure_vec_backend_identity).
ORPHANED EMBEDDINGS (techne#408) — TWO PURGES, NOT ONE, AND THEY ARE NOT INTERCHANGEABLE. `_purge_superseded_knowledge_vec` deletes `WHERE rowid IN (SELECT id FROM knowledge WHERE superseded_by IS NOT NULL)` — it selects FROM the parent, so a vec rowid with NO parent row behind it is never matched (`vectors:coverage` verified this: it removed 0 of 2 in that state, which is why that check REPORTS dangling rows without failing). `_purge_orphaned_vec` is the complement: `DELETE FROM <vec> WHERE rowid NOT IN (SELECT <id> FROM <parent>)`, run for all three indexes from `backfill_vectors`. TWO LEAK SOURCES: threads rotate their rowid on `INSERT OR REPLACE` (thread_orchestrator.py:443 — one stranded embedding per summary update, unbounded), and a HARD-deleted knowledge row goes through a plain `connect()` which cannot touch vec0. Recall stays CORRECT either way (`search_vec`'s post-cut `if row:` guard drops dead-rowid hits) — the cost is that an orphan can occupy a top-k ANN slot first, #168's shape bounded by `_VEC_SUPERSEDE_OVERFETCH`. So this is index hygiene, not correctness.
OBSERVABILITY GAP (techne#408) — `vectors:coverage` counts dangling rows for `knowledge_vec` ONLY (checks.py, `SELECT COUNT(*) FROM knowledge_vec_rowids`). The LARGER leak — threads rotating their rowid on `INSERT OR REPLACE`, one stranded embedding per summary update, unbounded — is counted by NO check. The sweep fixes it; nothing reports it. Also: `dangling` is surfaced in that check's detail but excluded from `healthy`, and the comment saying "no remedy clears it" was true only until #408 shipped one — folding it into the verdict changes doctor output on live stores and is a deliberate follow-up, not an oversight.
THE ORPHAN SWEEP RUNS BEFORE THE BACKEND GATE, DELIBERATELY: deleting an orphan is pure SQL and needs sqlite_vec loaded but NOT an embedding model. Below `backend_available()` it would never fire on an install with sqlite-vec and no model2vec/fastembed, while `vectors:coverage` kept reporting dangling rows and naming `techne vectors backfill` as the remedy — a check whose remedy provably does nothing, the never-green defect #496 was fixed for. Do not 'tidy' it back under the gate. RETURN CONTRACT, load-bearing: `backfill_vectors` includes `orphans_swept` ONLY when the sweep actually ran — its ABSENCE means the function returned early (no numpy, no sqlite_vec, no loadable extensions) and the CLI must not report hygiene as having happened. `sweep_errors` separates a sweep that failed on every index from one with nothing to do. Tidying `return counts` back to `return {}` breaks the CLI's message silently.
INVARIANT (techne#382, FIXED in #407, schema v19): any path that edits a knowledge row's `content` IN PLACE must set `vec_stale=1`. `connect()` never loads sqlite_vec (techne#168), so the mutation site physically cannot re-embed; `backfill_vectors` reconciles the flag where the extension IS loaded (re-embeds rows missing from *_vec OR carrying vec_stale=1, then clears it). WAS (pre-#407, do not re-derive this from old notes): backfill embedded only rows MISSING from *_vec, so an edited gist kept matching its OLD text forever.
OPERATOR ACTION IS STILL REQUIRED — the flag fixed the MECHANISM, not the need to act: nothing auto-runs `backfill_vectors` in production ("nothing auto-runs backfill_vectors in production today", search.py:945; "never hook-invoked", embeddings.py:45). Its only caller is the `techne vectors backfill` CLI command, which since #408 NO LONGER gates on a backend — it calls through so the orphan sweep runs, then reports that it could not embed (the unconditional `counts = backfill_vectors(config.db_path)` at cli.py:3170, with the backend report below it). So a `vec_stale=1` row stays dirty — and semantic recall keeps matching the OLD text — until a human runs backfill.
