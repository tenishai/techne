# custodian — headless emit→ingest rails (techne#555)

WHAT: binds a model to the emit→ingest rails so they can run with no live session. A CUSTODIAN THAT ONLY WORKS WHILE YOU ARE WATCHING IS NOT A CUSTODIAN — everything genuinely custodial (dedup, merge/supersede, faithfulness on rewrites, contradiction classification) sat on the resident path, which has no daemon.
SEAM: `Rail(name, emit, ingest, what)` registry + `run_rail` / `run_custodian` / `resolve_generate_fn` / `record_rail_marker` / `clear_rail_marker`. Five rails: consolidate, dream, faithfulness, conflict, memory_claims.
THE RESIDENT PATH IS UNCHANGED. Unbound (the default) every rail behaves exactly as before; borrowed inference stays right for judgment work the operator is present for. This adds a second way to ANSWER the prompts, not a replacement.
ADAPTERS, NOT RAIL EDITS: the five rails disagree on key names (`target_ids` / `group_ids` / `candidate_id` / `focus_id`+`comparison_ids` / `prompt_hash`). Each `_<rail>_ingest` re-states that mapping; NO RAIL IS MODIFIED, which is what keeps "resident path unchanged" provable. A wrong key is a TypeError at 3am in an unattended run — pinned per-rail by a parametrized arg-capture test.
PROVIDER-AGNOSTIC: the binding is `str -> str`, resolved through the same `_make_generate_fn` as the operator-model path, so any LiteLLM id works (ollama/*, vertex_ai/claude-* via ADC, openai/*, a proxy api_base). THE CREDENTIAL QUESTION BELONGS IN CONFIG, NOT THIS CODE PATH — five viable transports were enumerated on #555 and the right one differs per operator and per pass.

THE FAILURE THIS EXISTS TO NOT REPEAT — MEASURED 2026-08-21 on the operator's store:
The automatic session-end reflect rail had produced ZERO candidates in its ENTIRE HISTORY (since 2026-06-20), while `check_maintenance_rails` reported it LIVE. All 444 candidates carried `model_used='agent-assisted'` — the resident route — and not one came from the operator-model path. Cause: `config.model` is an Anthropic id, the operator holds Pro/Max OAuth and no Console API key, `litellm.completion` raised `AuthenticationError`, and `reflect_on_session` caught it, incremented `result["errors"]`, logged, and let teardown proceed. Two months of a rail reading healthy while doing nothing.
WHY THE EXISTING CHECK COULD NOT SEE IT: it keys on `knowledge_candidates.origin` (the rail's OUTPUT), and `origin` does not record WHICH PRODUCER wrote the row. The resident route filled the table the whole time. `model_used` is the discriminator — the automatic path writes the model id, the resident path writes 'agent-assisted'.

INVARIANTS — the ones a diff will not show you:
- **NO FALLBACK TO `Config.model`, EVER.** `resolve_generate_fn` resolves rail_models → custodian.model → NOTHING. Inheriting the session-wide model is precisely how reflect came to be bound to a credential plane the operator does not hold. AN ABSENT BINDING MUST READ AS ABSENT (dormant, runs nothing), never as bound-to-something-unreachable. Pinned by `test_does_not_fall_back_to_config_model`.
- **AND REFLECT NOW OBEYS THE SAME RULE (2026-08-23).** This card stated the invariant for the five custodian rails while naming reflect as the cautionary tale — and left reflect itself still falling back, because it has its own runner and was never routed through `resolve_generate_fn`. #709's marker made that visible the moment it deployed: `rail:reflect:bound` went BROKEN with `RuntimeError: requires litellm` on the operator's own box. A RULE STATED IN THE DOCSTRING OF ONE CODE PATH IS NOT ENFORCED IN THE OTHER. `reflect_on_session` now requires an explicit `config.reflect.model` and skips the automatic pass when it is empty.
- **UNBINDING RETRACTS THE MARKER — `clear_rail_marker`.** The marker's contract is "the LAST MODEL-BOUND RUN, and how it went". Once a rail has no binding there is no such run to describe, so the payload stops being a statement about now. THE JUSTIFICATION FOR BOTH HALVES LIVES IN `clear_rail_marker`'s DOCSTRING AND IS NOT REPEATED HERE (techne#735) — this line used to say the payload "reports a months-old failure as the current state" and that the check "reads DORMANT off a marker's ABSENCE", and both stopped being true when the check started asking `_rail_binding` first. The retraction must still be a DELETE rather than a payload saying "unbound", now for a measured reason about RE-BINDING rather than about being unbound. One copy, in the function; pointers everywhere else, because two spellings of one justification is how techne#429 happened. Only a path that positively establishes "there is no binding" retracts; `reflect.enabled=False` returns before the binding question is asked and leaves the last bound run readable.
  **AND THE RETRACTION IS NO LONGER WHAT MAKES THAT SAFE (techne#735).** This bullet used to add "every `noop:*` maps to LIVE, which an unbound rail is not" — true, and it was the whole protection, which meant the protection only existed on the ONE path that retracts. `clear_rail_marker` has exactly one caller (`reflect._clear_reflect_marker`), so no custodian rail has ever retracted anything, and `reflect.enabled=False` cannot reach the retracting code at all. All of them read LIVE off a stale `ok` indefinitely. The verdict is now gated at READ time on whether the rail is bound (`checks._rail_binding`), which covers every path including the ones with no retraction. Retraction still happens and is still correct — it is simply no longer load-bearing for honesty. NOTE THE TENSION IT EXPOSES, deliberately left rather than resolved here: the unbound path DELETES the payload while the disabled path KEEPS it, so the same operator question gets an answer on one path and not the other.
- **A BOUND RAIL THAT FAILS MUST LEAVE A TRACE.** Every run records `rail:<name>:last_run` in `extension_state` — success AND failure, with the reason — via the same mechanism the hooks use. An unattended custodian that fails silently is strictly WORSE than none: it reports success while doing nothing.
- **FOUR OUTCOMES, and answered-zero is NOT ok**: `ok` / `partial` / `error` / `noop:nothing-to-do`. Emitting 20 and answering 0 must never summarise as "ran"; answered-some must be distinguishable from answered-all, or a rail degrading toward zero reads healthy until it arrives.
- **THE MARKER CARRIES THE EXCEPTION TYPE, not just the message.** `AuthenticationError` tells an operator "this needs a credential it was never given" in one word — a different remedy from "this is broken".
- **NO MARKER = DORMANT, NOT BROKEN.** An install that only ever uses the resident route never writes one; that is the default and correct posture. Crying wolf on every such install is how a check gets trained into noise.
- **A PER-CALL TIMEOUT IS LOAD-BEARING, NOT A NICETY.** A call that never returns is NOT an exception, so `run_rail`'s per-item try/except cannot catch it — the runner would hang forever and never report. `_make_generate_fn` gained an OPTIONAL `llm_timeout` (unset for every pre-existing caller, so their behaviour is unchanged); the custodian sets it on its SCOPED COPY so no interactive caller inherits a headless deadline.
- **A HEADLESS ROW MUST NAME THE MODEL THAT JUDGED IT (`model_used`).** This is the invariant the feature nearly violated. `model_used` is the ONLY column recording WHICH PRODUCER judged a candidate, and the whole #555 finding turned on it — the automatic reflect rail was invisible for two months because nothing distinguished its output from the resident route's. Three insert sites hardcoded the literal `'agent-assisted'` in their VALUES clause, so the first working headless run wrote 6 rows claiming a resident agent had judged them. THE FEATURE WOULD HAVE MANUFACTURED THE EXACT HOLE IT EXISTS TO FIX, for five rails at once. Now a bound parameter, threaded from `run_rail` through each adapter; `RESIDENT_PRODUCER` is ONE constant (conflict imports sleepdream's, never a second copy — techne#518). The resident path is unchanged because the kwarg defaults. CAUGHT BY READING THE ROW A REAL RUN WROTE — 47 tests and 9 killed mutants were green over it.
- **THE LABEL IS A REQUIRED KWARG ON THE PRIVATE INSERTERS — MECHANISM, NOT DISCIPLINE.** `conflict._insert_candidate`, `sleepdream._insert_*_candidate` and both conflict handlers take `model_used` with NO DEFAULT, so omitting it is a TypeError at the call rather than a row that quietly claims a resident agent judged it. This was not caution: mutating each forward one line at a time found FOUR unguarded sites in conflict.py alone, all green under the full suite. Making it required immediately surfaced a caller nobody had threaded — `federation_conflict_ingest` has SIX insert sites of its own, a THIRD producer. The public `*_ingest` entry points keep the default, which is what leaves the resident path unchanged.
- **THE PRODUCER TEST HAS TO ASSERT THE KEYWORD, NOT JUST THE POSITIONALS.** The adapter test captured `args` and `kwargs` and asserted only on `args`; the label travels as a kwarg, so the conflict adapter's forward sat unguarded under a green suite. 18 forwards exist across four modules — all 18 are now individually mutated and killed. Verdict families take DIFFERENT insert paths (SUPERSEDE/UPDATE from inside the handlers, DISTINCT/NOOP and no-verdict markers straight from the ingest body), so a test covering one family proves nothing about the others; the federation test is parametrized over all four for that reason.
- **`faithfulness` and `memory_claims` take the label and ignore it, on purpose**: the first annotates an EXISTING candidate, the second returns an ephemeral report and persists nothing. Neither has a `model_used` of its own to set; the parameter exists so every adapter has one signature.
- **AN UNRECOGNISED MARKER OUTCOME FAILS CLOSED (Prudence, #709).** The first cut mapped everything that was not literally `error`/`partial` to LIVE — including a missing, empty or garbled outcome, since `str(marker.get("outcome", ""))` yields `""`. Fail-OPEN in the one check whose entire job is catching silent nothing. Now: `error`/`partial` → BROKEN, `ok`/`noop:*` → LIVE, anything else → UNKNOWN. **AND ALL THREE ROWS ARE NOW CONDITIONAL ON THE RAIL BEING BOUND (techne#735).** `check_model_bound_rails` asks `_rail_binding` FIRST; an unbound rail reads DORMANT for every outcome — `error`, `ok` and unrecognised alike — because a marker describes a run under a configuration that no longer exists. The mapping stated ABOVE is for a BOUND rail. Measured unbound: error -> DORMANT, ok -> DORMANT, "" -> DORMANT.
- **`partial` IS BROKEN ON PURPOSE, AND THE NOISE HAZARD IS BOUNDED.** One refusal in twenty marks the rail for ONE SCHEDULING INTERVAL — `rail:<name>:last_run` is a LAST-RUN record, overwritten by the next run whatever it reports, so a subsequent `ok` OR `noop:*` clears it. (An earlier draft of this line said "until the next fully clean run", repeating Prudence's round-1 phrasing; she corrected it herself in round 2 and the trade is materially cheaper than both of us first priced it.) Kept because "ran and reported trouble" has no other verdict here — DORMANT ties with LIVE, UNKNOWN means a probe that could not run, STALE means overdue — and a rail answering some of its prompts is not healthy. The detail carries the ratio. Revisit with a policy about acceptable failure fractions, never by quietly greening it. CONDITIONAL ON BINDING (techne#735): an unbound rail's `partial` reads DORMANT, not BROKEN.
- **A RAIL THAT RESOLVES AMBIENT STATE MUST SAY WHAT IT RESOLVED.** `memory_claims` gets its project from `Path.cwd()`, and a scheduled run's cwd is whatever the scheduler hands it — so "no curated memory for this project" and "looked in the wrong project" are the SAME empty batch. MEASURED: from a non-project cwd the rail made ZERO model calls across its life and the check reported LIVE — techne#555's own shape reproduced inside the check written to close it. `Rail.context` now records the resolved slug into the marker. THIS MAKES THE AMBIGUITY VISIBLE; IT DOES NOT RESOLVE IT — where a headless run should learn its project is an open design question, deliberately not answered here.
- **THE CAP HAS ONE OWNER, AND `effective_limit` IS IT.** THREE surfaces decide how many prompts leave the box — `run_custodian`, `run_rail`, and the CLI's `--dry-run` branch — and they must not each re-derive `max_items_per_rail`. Dry-run was the last holdout: it called `rail.emit()` directly, bypassing both runners, and reported the UNCAPPED length (measured: cap 5, dry-run said 50, real run answered 5; `--limit 3` was silently inert). It over-reported, so nobody would have overspent — but this is the ONE surface an operator reads BEFORE wiring cron, and a number you would trust being wrong is worse than a missing one. Pinned by a test asserting dry-run's reported count EQUALS the real run's `emitted` on the same config.
- **AND SELECTION IS THE SECOND AXIS — `effective_rails` OWNS IT.** The count fix left dry-run falling back to every registered rail while the runner honours `config.custodian.rails`. Measured: `rails = ["conflict"]`, dry-run promised FIVE rails' worth of prompts, the runner sent one — quantitatively a larger over-report than the cap error it followed. THE ROUND-2 GUARD COULD NOT SEE IT BY CONSTRUCTION: that test pinned both paths to the same explicit `--rail`, so the one axis where they still diverged was the axis it held constant. The current guard passes NO `--rail` and sets `custodian.rails` instead, so one equality assertion covers selection and count together. A card claiming "the three surfaces agree" must name WHICH axes, or it asserts more than the tree does — which this bullet's predecessor did.
- **THE MODEL IS THE THIRD AXIS, AND `effective_model` OWNS IT.** `custodian status` — THE surface built to answer "what is bound" — never read `rail_models`, so a rail carrying a per-rail override reported the GLOBAL model and a bare `bound: yes` while the runner used the override; dry-run named no model at all while its docstring claimed it did. In THIS feature that is a wrong belief about `model_used`, the one column recording which producer judged a candidate and the column the whole techne#555 finding turned on. All three surfaces — status, dry-run, and the producer label the runner writes — now name one model per rail, pinned together by `test_all_three_surfaces_agree_on_the_model`.
- **`rails=[]` MEANS RUN NOTHING; `rails=None` MEANS THE CONFIGURED SELECTION.** Consolidating selection flipped `rails is not None` to `if rails`, so an explicit empty list went from zero rails to EVERY registered rail — fail-open in the token-spending direction, which is the wrong way for a headless runner to be wrong. Latent (no in-tree caller reaches it) and caught by review rather than by the suite, which is the case for pinning it.

**THE AXIS ENUMERATION (Prudence, #709 round 4) — the method, not just the findings.** Three consecutive rounds found the same defect class because there was no systematic way to look for it. There is one: ENUMERATE WHAT THE RUNNER DECIDES, THEN ASK WHAT EACH REPORTING SURFACE SAYS ABOUT EACH DECISION. The runner decides four things — (1) how many, (2) which rails, (3) which model, (4) what gets recorded. Every one of 1-3 had a surface that disagreed with it, each found a round apart; (4) was sound because `run_rail` records ok/partial/error/noop and the check maps them fail-closed. The enumeration is now exhausted. THE COROLLARY IS THE TEST LESSON: a guard that holds a variable constant cannot see divergence in it — the round-2 count test pinned both paths to the same explicit `--rail`, which is precisely why it could not catch the selection divergence.

- **A LIMIT OWNER MUST DECIDE WHETHER, NOT ONLY WHICH.** `effective_limit` validates as well as resolves: the config path rejected `0` and negatives at load while `--limit` walked past the same guard into `batch[:limit]`. `--limit -1` reads as "no cap" and means "all but the last item of every batch" (measured 49 of 50) — and since dry-run now agrees with the runner, it CONFIRMS the wrong number rather than contradicting it. `--limit 0` is a rail that never runs, records a `noop:` that maps to LIVE, and exits 0, because the CLI's failure check is `if run["emitted"] and run["answered"] == 0`: techne#555's own shape, through a flag on the command written to close it. Pinned by `test_an_unusable_limit_is_rejected_rather_than_sliced` (parametrized over 0/-1/-5) and `test_the_cli_rejects_a_bad_limit_without_a_traceback` on both the real and dry-run paths.
- **`run_rail`'s `limit=None` MEANS NO CAP — the cap is the caller's.** It is exported and directly tested, so that is stated in its docstring rather than inferred from the one in-tree caller that happens to resolve it correctly.
- **A RAIL'S EMPTY-BATCH REASON BELONGS IN `outcome`, NOT ONLY IN `detail`.** `outcome` is what the check keys on; `detail` is free text. `memory_claims` reports `noop:no-memory-for-project`, so the ambiguity is visible to a PROGRAM and not just to a reader — the follow-up design work can act on it without parsing prose. Every `noop:*` still maps to LIVE, so this costs nothing today. AND "every `noop:*` still maps to LIVE" holds for a BOUND rail only (techne#735).
- `run_custodian` applies `max_items_per_rail` when no explicit limit is given; the CLI passes `limit` straight through rather than keeping a second copy. It was CLI-only at first, so a scheduler calling the documented "headless entry point" got no cap at all (measured: cap 5, answered 50 of 50) — bounded in practice only by each rail's own emit cap, which is luck.
- **A BOUND THAT DISABLES A GUARD IS REJECTED AT CONFIG LOAD.** `max_items_per_rail: 0` makes every rail a permanent no-op; negative becomes `batch[:-1]`, silently dropping the last item of each batch; `timeout_seconds: 0` is FALSY so `_make_generate_fn` skips the timeout kwarg entirely and an unattended run can hang forever. A config that switches off a protection must say so.
- **ONE BAD PROMPT DOES NOT ABORT THE RAIL.** A model that refuses one cluster must not cost the other nineteen; failures are counted and both numbers reported.
- **A TYPO'D RAIL NAME IS REJECTED AT CONFIG LOAD**, against the registry. Otherwise it is a rail that silently never runs — #555's own failure class reproduced inside its own config.
- **NOT SCHEDULED FROM HERE.** `run_custodian` is what a scheduler calls; installing the schedule is a separate deliberate act, because switching it on means spending tokens or GPU on a timer with nobody watching.

MEASURED, so nobody re-derives it (2026-08-21). TEST AGAINST THE INFERENCE HOST, NOT THE DEV BOX — the first round of these numbers was taken on the author's laptop CPU and produced a WRONG CONCLUSION, retracted below.
- ON THE INFERENCE HOST (192.168.10.118, `ornith:9b`): a real 1,568-char `conflict` prompt answers in **11.6s** (`ornith:9b-q8_0`: 22.3s), with a well-formed JSON verdict. Full CLI run: 2 prompts, 23s wall, `supersede=1 distinct=2`, rows labelled `ollama/ornith:9b`.
- ON THE DEV LAPTOP (ollama llama3.2, i7 CPU): a 20-char prompt answers in 1.3s but the same class of real prompt had NOT returned after 240s.
- **RETRACTED**: an earlier draft of this card concluded that #555's premise — "a small local model is adequate for the mechanical passes" — did not hold at real prompt sizes. THAT CONCLUSION WAS WRONG, and it was wrong because the measurement was taken on hardware that cannot serve a model, not because the premise is. Ornith 9B answers the same prompt in 11.6s. THE LESSON IS ABOUT THE TEST BED, NOT THE MODEL: a latency number measured on the wrong host is not evidence about the model, and generalising from it produced a confident, load-bearing, false claim in a design document.
- With `timeout_seconds: 60` (against the slow local model) the run terminated at 63.7s, exited 1, and recorded `error — APIConnectionError … Timeout` where before it would have hung indefinitely. THE TIMEOUT DEFECT IS UNAFFECTED BY THE RETRACTION ABOVE: it is about a hung call not being an exception, which is true at any latency — the slow host only made it visible.
- With a 900s timeout the same rail completed end-to-end: `emitted 1, answered 1, failed 0`, verdicts `supersede=3, noop=2`, marker `ok — answered 1/1`, and the 5 written rows carry `model_used='ollama/llama3.2'` rather than 'agent-assisted'.
CONSUMERS: `techne custodian run|status` (cli.py); `checks.check_model_bound_rails` (subsystem `custodian`, one CheckResult per rail plus `reflect`).
FAIL-MODES: unbound → runs nothing, exit 0, no marker (correct, not a failure). Bound + answered-zero-of-N → exit 1 so a scheduler whose only signal is exit status can tell it did nothing.
TESTING: tests/test_custodian.py. Guards mutated and killed, plus all 18 producer-label forwards mutated line-by-line. TWO LESSONS WORTH MORE THAN THE TESTS:
  1. THE TIMEOUT GAP WAS INVISIBLE TO MUTATION AND TO THE SUITE. 9/9 guard mutants died and told us nothing; a call that never returns is not an exception, so no assertion in the harness could observe it. Running the real CLI against a real model found it in one command.
  2. THE PRODUCER-LABEL BUG WAS FOUND BY READING THE ROW A REAL RUN WROTE, not by any test. The suite was green while the first working headless run wrote 6 rows attributing a model's judgement to a resident agent.
  Both are the same shape: A HARNESS CANNOT OBSERVE A FAILURE MODE IT HAS NO ASSERTION FOR, and "add more tests" does not fix that — exercising the real surface does.
