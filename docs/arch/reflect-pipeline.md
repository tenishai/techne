# reflect / consolidate / dream — self-maintenance

OPERATOR-FACING COUNTERPART: [`docs/reflect-guide.md`](../reflect-guide.md) — the learner-altitude explanation of this seam, plus the agent-trigger block indexed in `AGENTS.md`. Several of its claims are witnessed by tests in `tests/test_agent_triggers.py`; changing the behaviour behind one fails there, which is the signal to update the guide in the same change.

SEAM: resident-model emit/ingest (techne#19) — self-maintenance runs on the AGENT'S OWN model in its own loop, NOT a headless API call → no API key / inference bill. _emit packages a prompt (PROMPT_TEMPLATE) + injectable generate_fn (core/threads.py:_make_generate_fn); the agent answers; _ingest parses the JSON-array (core/_resident.py:extract_json_array) into knowledge_candidates rows. NEVER auto-mutates live knowledge/identity (opt-in via config.reflect.enabled, off by default).
TRIGGER (techne#514): reflection debt is DURABLY QUEUED, not re-derived from recency. session_end enqueues one reflection_queue row per thread (THREAD IDS, re-rendered at drain time — a stored prompt would embed a snapshot that drifts from the ledger it renders from). Before #514 session_end COUNTED the debt and enqueued nothing, so reflection survived only the polite exit path; every crash/timeout dropped it silently. The queue DECOUPLES producer from reflector: any session can drain another's threads, because answering a rendered prompt needs the thread's observations, not the original session's context.
PIECES:
- reflect.py: per fresh thread → proposes durable facts/decisions/procedures/identity claims (candidates, human-reviewed).
- reflect.py queue quartet (#514): emittable_thread_ids (THE predicate for "is this thread owed reflection" — enqueue and emit MUST both come here; the threads table has no observation linkage so it cannot be expressed in SQL) / enqueue_reflection_debt (session_end and redetect, INSERT OR IGNORE on the UNIQUE thread_id — idempotent by schema) / pending_reflection_queue (SessionStart nudge reads it) / drain_reflection_queue (called from ingest_one_and_drain — the SHARED path, not one caller — STAMPS drained_at, never deletes).
- Drain fires ONLY on a pass that happened: gated on `not parse_failures and not errors`. The parse-failure branch is the one whose comment reads "THE PASS DID NOT HAPPEN"; draining there stamps a DISCARDED reflection as paid, permanently, since drain is guarded on `drained_at IS NULL`.
- ONE IMPLEMENTATION PER HALF, and this is the load-bearing lesson (#642): emit_reflection_pass / ingest_one_and_drain / ingest_reflection_batch live in reflect.py and BOTH the MCP tools and the `techne reflect` CLI are thin wrappers over them. They were separately implemented, and the CLI copy — the one the documented /techne-promote skill runs — omitted the two BOOKKEEPING writes: it never drained the queue (#644) and never advanced the `reflect:emitted:` cursor (#645). A two-implementation rail drifts on its bookkeeping FIRST, because that half is invisible to whoever runs it: the work succeeds and only the record is missing. Add a new caller by calling these, never by re-deriving them.
- UNEMITTABLE ROWS ARE REPORTED, NEVER SWEPT (#646) — AND THE CAUSE IS NOT THE ONE THIS LINE USED TO NAME. It said emittable_thread_ids "is evaluated TWICE against separately-derived observation buckets ... when they disagree the queue row is real and its prompt is impossible", and asked which evaluation moved. MEASURED 2026-08-27: neither. The predicate is fine; the two calls run over DIFFERENT PARTITIONS. save_threads writes INSERT OR IGNORE on bucket_hash(session_id, first_obs_id, boundary_signal), run_session_end fires once per turn, and it deleted thread_boundaries but NOT threads — so every re-detection over a grown observation set left a superseded partition behind (86 rows in threads against 51 current threads on the operator's store). load_session_for_reflection re-detects from scratch, so the queue holds ids no current detection produces. reflection_queue.thread_id is ON DELETE CASCADE precisely to retire those and never fired, because nothing deleted the stale partition. FIXED by lifecycle.persist_detection, the ONE replace-and-restore sequence both run_session_end and redetect_threads now call. THE STANDING RULE IS UNCHANGED: unemittable_queue_rows names them, emit_reflection_pass reports the count, and blanket-draining is still forbidden — it would destroy the only evidence the class exists, which is how it survived #527 r4. superseded_queue_rows is the strict subset that is PROVABLY stale (id absent from the current detection); reconcile_reflection_queue retires exactly those, dry by default, and leaves the below-threshold remainder standing because that is the real signal.
- document_card is a MANAGED type and neither promote nor merge may mint one (#633). _card_type_or_fact demotes a `document_card` whose tags carry no `doc:<id>` pointer down to `fact`: the content is real prose about a document, it just is not a card, and an unbacked card leaves `fsck` dangling_cards red forever (four such rows exist from before the guard).
- Enqueue INSIDE the deleting transaction, on the caller's conn (#527 r5). REVERSES an earlier card line saying the opposite ("after COMMIT, never inside"), which was true of the code and wrong about the cause: persisted_thread_id opened its own connection, so it could not see the caller's uncommitted rows and the insert hit a FOREIGN KEY failure. The seam was a missing `conn=` param, not an ordering constraint. Out of the transaction a failed enqueue leaves a permanent half-applied redetect — nothing re-derives debt for an emittable thread with no queue row.
- enqueue_reflection_debt takes thread_ids as a REQUIRED argument; the "queue every thread" default is gone. With no observation list you cannot apply min_observations_per_thread, so it queued sub-threshold threads emit never produces a prompt for and the drain could never clear (#527 r4/r5).
- sleepdream.py (techne#108):
  - consolidate (sleep): find dup/overlapping live knowledge — Tier0 exact content_fingerprint buckets | Tier1 FTS self-sim top-neighbor | Tier2 vector dup-band (deferred) → action='merge'.
  - dream (recombine): non-obvious A+B→C across a shared-tag group → action='add', origin='dream', confidence='low' (abstention-first; most groups yield nothing).
API: MCP pairs techne_reflect_emit/ingest, techne_consolidate_emit/ingest, techne_faithfulness_emit/ingest, techne_dream_emit/ingest, techne_memory_claims_emit/ingest; CLI techne reflect/consolidate/dream. The /techne-promote skill drives this end-to-end each session.
INVARIANTS:
- reflection_queue.drained_at is NULLABLE, not a status enum: pending is the ABSENCE of a drain, so there is no second source of truth to disagree with the timestamp. Drain is guarded on `drained_at IS NULL` so a re-drain never rewrites the first payment.
- THE FK GRAPH AROUND threads(id), WHICH IS WHAT #797 TURNED ON. FOUR columns reference it and only ONE cascades: reflection_queue.thread_id (CASCADE), threads.parent_thread_id, knowledge_candidates.source_thread_id and observations.thread_id (all NO ACTION). The CASCADE on reflection_queue is REQUIRED and load-bearing — pruning a superseded thread retires its queue row for free, which is how #646's stale rows are cleared. THE OTHER THREE ARE WHY re-detection NO LONGER DELETES A SESSION'S WHOLE THREAD SET. This line used to say it did, and that a plain reference would make the queue block re-detection; the second half is still true, but the first half described behaviour that raised `IntegrityError: FOREIGN KEY constraint failed` on any store with history and took run_session_end down with it (#793 put it on the per-turn path; the defect was latent in redetect_threads long before). `lifecycle.persist_detection` now PRUNES: it deletes only session threads that are (1) absent from the detection about to be saved, (2) unreferenced by any of the three NO ACTION columns, and (3) not carrying a DRAINED queue row. Condition (1) also preserves reflection-debt AGE — the cascade would take a still-current thread's PENDING row and the re-enqueue would re-date it, and nothing restores enqueued_at. Threads the prune SPARES keep their stale queue rows; `techne reflect reconcile` retires those. tests/test_detection_replace.py derives the guard list from `PRAGMA foreign_key_list` so a fifth referencing column is caught when it is added rather than when it breaks.
- Every consolidate cluster has a stable cluster_hash (prompt_hash col) → a cluster already proposed (pending, promoted, OR kept-distinct) is never re-judged (_already_proposed) — stops the anti-bloat feature from bloating its own review queue.
- _FAITHFULNESS_GATED_ACTIONS={'merge','supersede'}: promoting a merge/supersede candidate needs a prior faithfulness check (raises FaithfulnessGateError unless force=True); keep this gate in sync with faithfulness_emit's SQL filter.

**THE AUTOMATIC PATH RECORDS A LIVENESS MARKER NOW (techne#555).** `reflect_on_session` catches every LLM failure, counts it in `result["errors"]`, and lets teardown proceed — correct, because teardown must not fail on reflection. But a counter nobody reads is not a signal: MEASURED 2026-08-21, this rail had produced ZERO candidates since 2026-06-20 (every one of the 444 in the store came from the RESIDENT emit→ingest route, `model_used='agent-assisted'`), because `config.model` is an Anthropic id and the operator holds no Console API key. `AuthenticationError` on every session, for two months, while `check_maintenance_rails` read the rail LIVE off the resident route's output. It now writes `rail:reflect:last_run` via `custodian.record_rail_marker` on EVERY outcome — ok / partial / error / noop — carrying the exception TYPE, because "AuthenticationError" says *needs a credential it was never given* where a generic failure says only *broken*. Never raises into teardown.

**THE EMIT CURSOR IS KEYED ON `thread_id`, AND THE REASON IS THE WHOLE LESSON (techne#733, 2026-08-23).** It used to hold `prompt_hash`, called in its own comment "the stable, always-present per-thread id". IT IS NOT STABLE: `_prompt_hash` hashes the RENDERED prompt, and `_build_prompt` embeds a freshly-retrieved existing-knowledge block, so the hash of a thread whose observations are frozen still moves whenever LIVE KNOWLEDGE changes — every reflect, promote or `techne_store` call. The old comment scoped that to `write_to='live'`; the real trigger is any knowledge write from any session, continuously.
THE FAILURE ACCUMULATES, WHICH IS WHY IT RAN SO LONG. A drifted hash matches nothing, so the thread is re-emitted AND a second entry is appended. MEASURED: session 0ae96e10 held 51 entries for 23 renderable threads, 48 matching no current render, `remaining` = -27; six sessions were in this state.
AND IT HID ITSELF. `_marker_has_unemitted_threads` answers `len(emitted) < total`, so an OVER-FULL cursor reads as fully emitted — every corrupted session dropped out of the SessionStart nudge, and 126 owed queue rows were reported to the operator as 50. A corrupt cursor now reads as PENDING. "We do not know" is a reason to re-surface, never to stay silent (same fail-open shape as #709's UNKNOWN verdict).
THE KEY IS NOT ARBITRARY: `thread_id` is what `reflection_queue` is keyed on and what `drain_reflection_queue` stamps, so the cursor and the ledger now agree BY CONSTRUCTION rather than by coincidence — two derivations of one fact, collapsed to one. **READ THAT SENTENCE AS SCOPED TO THE KEY, WHICH IS NOT HOW IT WAS WRITTEN (techne#900).** Sharing a key makes the two COMPARABLE; it does not make them agree, and for two more weeks nothing compared them. See the #900 section at the end of this card. `prompt_hash` stays exactly where it belongs, on candidate dedup (#236), which WANTS to notice a re-render. A pre-#733 marker is not migrated (its contents are unrecoverable); the delivered set is rebuilt from drained queue rows.
ORDERING IS PART OF THE CONTRACT: the char budget is spent in batch order, so owed threads sort ahead of paid ones. Without that, a session whose early threads are already drained spends every pass re-rendering them and never reaches what it owes — the reported symptom was 11 emitted prompts containing ZERO owed threads. And `emit_reflection_batch` now yields one item per persisted thread: two Thread objects can resolve to one `threads.id`, and the duplicate is rendered and answered twice.

**THE CURSOR IS RECONCILED AT WRITE TIME, NOT APPENDED TO — AND THAT IS THE HALF THE RE-KEY ALONE DID NOT FIX (Prudence, #734 r1).** Re-keying stopped the drift; it did not give a corrupt cursor a way back out, and reading one as PENDING without a repair path is the same defect wearing the opposite sign. THE MARKER WRITE WAS GATED ON `bool(batch)`, so once a session was fully emitted nothing could rewrite it: an over-full or legacy marker read pending on every pass with NO OPERATION ABLE TO CLEAR IT (measured: five consecutive passes, `key` never leaving None). A banner that cannot go green trains the operator to ignore the rail, which loses owed work by a different route than #733 did.
THREE SYMPTOMS, ONE MISSING STEP. The persisted set is now intersected with what the session can render RIGHT NOW before it is stored, which (a) drops keys that no longer render instead of hoarding them, (b) stops the legacy-rebuild path writing an over-full marker in the NEW format — which recorded `remaining: 0` while reading pending, internally incoherent — and (c) BOUNDS the `prompt_hash` fallback. That fallback is not merely "inherited instability": before reconciliation it grew 1,2,3,4,5,6 across six passes, which is #733 verbatim inside the branch that closes it. Reconciliation turns accumulation into re-offering, which is what the fallback's docstring always claimed it was.
`oversized` STILL WITHHOLDS THE ADVANCE (#268 footgun 3) — a lone thread too big to deliver must keep re-surfacing. Only the completed-but-empty case now writes.
AND THE INVARIANT IS ASSERTED AT THE WRITE POINT: `len(emitted) <= total`, raising rather than clamping. It cannot fire today because the reconciliation makes it unreachable, WHICH IS THE POINT — #733 survived two months because this was only ever checked by arithmetic (`len(emitted) < total`) that failed open and answered "done" for the markers that were worst.
COLLISION RESOLUTION IS LOSSLESS — THE BUCKETS ARE UNIONED, NOT PICKED BETWEEN (Prudence, #734 r2). `obs_by_thread` is keyed on `thread_num`, so two Thread objects resolving to one `threads.id` carry DIFFERENT observations and `_build_prompt` renders only what it is handed. PICKING a winner therefore discards the loser's observations permanently, by either rule: measured across three trees, main emitted both (3 and 11), first-wins dropped the 11, richest-wins dropped the 3. Against the merge base either choice converts "both reflected, one wasted drain" into "one reflected, the rest discarded" — and the duplicate drain being avoided was ALREADY a no-op, since `drain_reflection_queue` is guarded on `drained_at IS NULL`. The index sets are disjoint BY CONSTRUCTION on the default `heuristic` detector (`split_at_boundaries` appends each index once, ascending; `merge_pass` concatenates adjacent segments only) — on `detector: llm` the indices come from parsing an LLM's free-text `Observations:` line and nothing validates them for order, duplicates or overlap, so the union is still correct there but for a WEAKER reason. Unioning is both smaller and correct; the representative thread supplies label/summary only.
A MARKER MUST BE ABLE TO RE-OPEN ITS OWN SESSION. Writing on a completed-but-empty pass closed the uncleanable cursor and opened a new silence: a session with nothing renderable was stamped `total: 0`, and `_marker_has_unemitted_threads` reads `total` OUT OF THE MARKER and never recomputes it, so `0 < 0` is false forever. Measured: origin/main nudged such a session after a 12-observation backfill; the new marker returned `[]` while an explicit emit returned `count: 1`. The marker now records the observation count it was written at, and a caller that knows the current count can say "this session has grown". Legacy markers carry no count — absent means CANNOT TELL, which keeps old behaviour rather than re-surfacing every historical session.

**THE AUTOMATIC PASS IS UNBOUND BY DEFAULT, AND THAT IS THE FIX (2026-08-23).** The marker above did its job on first contact: `rail:reflect:bound` read BROKEN the day #709 deployed. THE CAUSE WAS THE FALLBACK ITSELF — `reflect_on_session` used `config.reflect.model or config.model`, so an operator who never chose a headless model still got an unattended call to whatever the session used. It now requires an explicit `reflect.model`; empty means the automatic pass does not run, and no LLM is called.
TWO SWITCHES, NOT ONE, and confusing them is the trap. `reflect.enabled` turns the FEATURE on — including the SessionStart nudge and the reflection-debt queue, which drive the RESIDENT route. `reflect.model` binds only the automatic pass. So the obvious remedy for a noisy unbound rail — `reflect.enabled: false` — trades the working path for the dead one: it silences a rail that produces nothing by switching off the one that produces everything. Enabled-and-unbound is a normal, fully-working posture.
UNBINDING RETRACTS THE MARKER (`custodian.clear_rail_marker` over `extension_state.clear_state`), because a marker describes the last BOUND run and there is no longer any such run to describe. THE JUSTIFICATION IS NOT REPEATED HERE — it lives in `clear_rail_marker`'s docstring, one copy, since techne#735 retired the original one ("absence is what the check reads as DORMANT") and replaced it with a measured argument about RE-BINDING.
BUT THE RETRACTION IS WRITE-TIME AND THEREFORE COVERS ONLY THIS PATH (techne#735). It fires inside `reflect_on_session`, so it needs a session to actually end; `reflect.enabled=false` never reaches it at all, because `lifecycle.py` gates the call site on that flag. Both left `rail:reflect:bound` reading LIVE off a stale `ok` — permanently on the disabled path. The verdict is now gated at READ time on `checks._rail_binding`, which asks whether the rail is bound before trusting the payload. Read this bullet as "retraction keeps the store tidy", not as "retraction is what makes the doctor honest".

**CANDIDATE ROWS NOW NAME THEIR PRODUCER (techne#555).** `_insert_consolidation_candidate` / `_insert_dream_candidate` hardcoded `model_used='agent-assisted'` in their VALUES clause. That was correct while the RESIDENT agent was the only thing answering these prompts; the custodian makes a second producer real, and a headless row claiming a resident agent judged it destroys the one column that distinguishes them — the same blindness that hid the automatic reflect rail for two months. Now a bound parameter, REQUIRED on the private inserters (no default, so a missed forward is a TypeError rather than a silent lie) and defaulted to `RESIDENT_PRODUCER` on the public `*_ingest` entry points, which is what leaves the resident path byte-for-byte unchanged. `RESIDENT_PRODUCER` is defined here ONCE; conflict.py and federation.py import it rather than re-typing the literal (techne#518).

**THE CURSOR DOES NOT OUTRANK THE LEDGER, AND THE #733 RE-KEY DID NOT ALREADY GUARANTEE THAT (techne#900, 2026-09-07).** The re-key made cursor and queue agree "by construction"; the card says so two sections up, and `_emitted_keys` says so in prose. NOTHING ENFORCED IT. `delivered` is set when a batch is RENDERED, so a pass whose answers never come back stamps its threads emitted while their queue rows stay undrained — permanently, because `_emitted_keys` trusts a `key: thread_id` marker unconditionally. Every later emit returns `count: 0` for a session the banner still reads as PENDING, and `reconcile` cannot classify the rows: they are neither superseded nor below-threshold, they RENDER FINE. That is a third population, and it was invisible to both reporters because both classify rows that cannot render.
THE TRIGGER IS THE ROUTINE CASE, NOT AN EDGE ONE. `techne_reflect_emit` regularly exceeds the MCP tool-result token cap and spills to a file, so the agent never receives the batch the cursor was just advanced for. MEASURED: session e9be3469 listed 12 emitted against 4 drained — 8 orphaned threads of 42 to 172 observations each; session eec74e57 orphaned one thread of 287. The oversized call is not tied to either of those: on 2026-09-07 an emit RENDERED FOR e9be3469 and issued from session 18f13f92 came back 52,068 characters across 37 lines and spilled to a file.
THE FIX IS SCOPED TO AN EMPTY BATCH, WHICH IS THE ONLY PLACE THE CURSOR IS PROVABLY WRONG. An empty batch is the cursor claiming "nothing left" about a session whose ledger still records owed rows that render today; those keys are dropped and re-offered. A NON-EMPTY BATCH CHANGES NOTHING, and that restraint is load-bearing: `techne reflect emit -o file` legitimately renders a whole batch long before `ingest file` pays it, so a ledger that simply overruled the cursor would re-render everything already in the file. Advancing the cursor on ingest instead — the more obviously correct rule — breaks that same path, which is why it was rejected.
PARTIAL BY DESIGN, STATED RATHER THAN HIDDEN — TWO CASES, THE SECOND FOUND IN REVIEW. (1) A session holding both orphaned and never-emitted threads heals only once the never-emitted ones drain and the batch goes empty; `_owed_first` sorts owed rows to the front, so it gets there, just not immediately. (2) An OVERSIZED never-emitted sibling keeps the batch non-empty forever, so the heal never fires at all (Prudence, #901 r1). That is subsumed by the blocking `oversized` already documents — a lone thread too big to deliver blocks every thread after it — but it is a second way an orphan can sit unreached, and it clears when per-thread chunking lands (#269 follow-up).
A DECLINE IS NOT AN ORPHAN, AND CONFLATING THEM COST A TERMINATION PROOF (Prudence, #901 r1). `ingest_reflection_batch` blesses a blank `raw_response` as a deliberate refusal: skipped WITHOUT draining, debt stays owed. That is byte-for-byte the shape the heal fires on, so `reflect-guide.md`'s documented "repeat until the batch comes back empty" loop STOPPED TERMINATING — measured at 6 iterations, the same thread every time, where the pre-#900 code stopped at 2. THE DISCRIMINATOR IS WHETHER INGEST EVER SAW THE THREAD: an orphan is one it never saw, a decline is one it saw and refused, and only the first is a bookkeeping accident. Declines are recorded in the marker's `declined` list, carried forward across the wholesale marker rewrite (dropping that field re-arms the loop), excluded from the heal and from `orphaned_queue_rows`, retired by a later real answer, and reported by `reconcile` as their own population. THEY ARE COUNTED APART BECAUSE THEY PROMISE OPPOSITE THINGS: an orphan clears on the next emit, a decline never will.
TWO WAYS THE DECLINE RECORD ITSELF WENT WRONG, both found by running it (Prudence, #901 r2). (1) IT MINTED A MARKER. `_record_declines` built the payload with `dict(get_state(...) or {})`, so a decline against a session that never emitted wrote `{"declined": [...]}` with no `emitted` key — and `_marker_has_unemitted_threads` reads `emitted is None` as a #268-era marker, NOT PENDING, permanently and ahead of the observations-growth re-open. That is wider than the nudge: `pending_reflection` is where `emit_reflection_pass` picks its default target, so the session went unreachable from both hooks AND both emit entry points, leaving only an explicit id. It now writes into an EXISTING marker or not at all, which is correct rather than merely safe — with no marker, `_emitted_keys` rebuilds from drained rows, a declined row is not drained, so the cursor never claims it and there is nothing for the heal to suppress. (2) IT WAS A ONE-WAY DOOR. `techne reflect emit` PRE-FILLS `raw_response: ""` as its placeholder and `ingest` reads that same literal as refusal, so an ordinary partial fill is indistinguishable from a deliberate one. That collision was harmless while #900's heal re-offered; r1 removed the recovery to stop the loop spinning and added none, so a declined thread whose batch file was lost was owed forever and unpayable. `clear_declines` / `techne reflect undecline` is the way back, and the emit CLI now says at write time what leaving an item blank costs. THE DESIGN CALL IS UNCHANGED — a decline is a decision and nothing re-offers it on its own; it is just no longer irreversible.
`orphaned_queue_rows` AND `declined_queue_rows` REPORT AND NEVER SWEEP (#646's rule, unchanged) — `reconcile` counts it as a third population alongside superseded and below_threshold and removes none of it. With the self-heal in place a nonzero count is a REGRESSION SIGNAL, not a work list.
AND ONE #733 TEST WAS AMENDED, WHICH IS THE PART TO DISTRUST FIRST. `test_a_drifting_hash_does_not_re_emit_or_inflate_the_cursor` skipped the ingest and still demanded `count == 0`, conflating "a knowledge write must not re-emit" (#733, true) with "an un-ingested thread stays delivered forever" (#900, the bug). It now drains between the two emits, which isolates hash drift — the only thing #733 is about — and its teeth were re-verified by mutation: forcing `_cursor_key` back to `prompt_hash` still fails it.
