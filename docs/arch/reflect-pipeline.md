# reflect / consolidate / dream — self-maintenance

OPERATOR-FACING COUNTERPART: [`docs/reflect-guide.md`](../reflect-guide.md) — the learner-altitude explanation of this seam, plus the agent-trigger block indexed in `AGENTS.md`. Several of its claims are witnessed by tests in `tests/test_agent_triggers.py`; changing the behaviour behind one fails there, which is the signal to update the guide in the same change.

SEAM: resident-model emit/ingest (techne#19) — self-maintenance runs on the AGENT'S OWN model in its own loop, NOT a headless API call → no API key / inference bill. _emit packages a prompt (PROMPT_TEMPLATE) + injectable generate_fn (core/threads.py:_make_generate_fn); the agent answers; _ingest parses the JSON-array (core/_resident.py:extract_json_array) into knowledge_candidates rows. NEVER auto-mutates live knowledge/identity (opt-in via config.reflect.enabled, off by default).
TRIGGER (techne#514): reflection debt is DURABLY QUEUED, not re-derived from recency. session_end enqueues one reflection_queue row per thread (THREAD IDS, re-rendered at drain time — a stored prompt would embed a snapshot that drifts from the ledger it renders from). Before #514 session_end COUNTED the debt and enqueued nothing, so reflection survived only the polite exit path; every crash/timeout dropped it silently. The queue DECOUPLES producer from reflector: any session can drain another's threads, because answering a rendered prompt needs the thread's observations, not the original session's context.
PIECES:
- reflect.py: per fresh thread → proposes durable facts/decisions/procedures/identity claims (candidates, human-reviewed).
- reflect.py queue quartet (#514): emittable_thread_ids (THE predicate for "is this thread owed reflection" — enqueue and emit MUST both come here; the threads table has no observation linkage so it cannot be expressed in SQL) / enqueue_reflection_debt (session_end and redetect, INSERT OR IGNORE on the UNIQUE thread_id — idempotent by schema) / pending_reflection_queue (SessionStart nudge reads it) / drain_reflection_queue (called from ingest_one_and_drain — the SHARED path, not one caller — STAMPS drained_at, never deletes).
- Drain fires ONLY on a pass that happened: gated on `not parse_failures and not errors`. The parse-failure branch is the one whose comment reads "THE PASS DID NOT HAPPEN"; draining there stamps a DISCARDED reflection as paid, permanently, since drain is guarded on `drained_at IS NULL`.
- PER-SESSION STATE: ONE PRUNED, ONE KEPT (#1073). `heuristic_threads.<session>` (lifecycle's skip-unchanged-detection cursor) is pruned after 7 days by `extension_state.prune_stale` at the write; losing an old cursor costs one redundant detection. `reflect:emitted:<session>` is NOT pruned, on purpose: it is the emit cursor and the decline record, and `_marker_has_unemitted_threads` reads an ABSENT marker as "never emitted, pending". An age prune would re-open every old session for emit and forget its declines. It grows one row per reflected session, the same order as `sessions` itself.
- BARE EMIT IS UNWINDOWED; THE HOOKS ARE NOT (techne#1158). `pending_reflection` applies its LIMIT (default 5, newest first) BEFORE the marker filter, which is right for the SessionStart nudge and per-turn recall: they care about the newest unreflected session and run inside a bounded hook. `emit_reflection_pass` with no session id used the same default, so once the 5 newest were emitted it reported "no session with unreflected work" while older sessions were owed (Grip: 168 imported sessions; the operator store: 4 visible of 70 pending). It now calls `pending_reflection(config, limit=None)`, which checks every session (measured 13 ms against 10 ms on that store), so its "nothing pending" note is true when it says it.
- ONE IMPLEMENTATION PER HALF, and this is the load-bearing lesson (#642): emit_reflection_pass / ingest_one_and_drain / ingest_reflection_batch live in reflect.py and BOTH the MCP tools and the `techne reflect` CLI are thin wrappers over them. They were separately implemented, and the CLI copy — the one the documented /techne-promote skill runs — omitted the two BOOKKEEPING writes: it never drained the queue (#644) and never advanced the `reflect:emitted:` cursor (#645). A two-implementation rail drifts on its bookkeeping FIRST, because that half is invisible to whoever runs it: the work succeeds and only the record is missing. Add a new caller by calling these, never by re-deriving them.
- UNEMITTABLE ROWS ARE REPORTED, NEVER SWEPT (#646) — AND THE CAUSE IS NOT THE ONE THIS LINE USED TO NAME. It said emittable_thread_ids "is evaluated TWICE against separately-derived observation buckets ... when they disagree the queue row is real and its prompt is impossible", and asked which evaluation moved. MEASURED 2026-08-27: neither. The predicate is fine; the two calls run over DIFFERENT PARTITIONS. save_threads writes INSERT OR IGNORE on bucket_hash(session_id, first_obs_id, boundary_signal), run_session_end fires once per turn, and it deleted thread_boundaries but NOT threads — so every re-detection over a grown observation set left a superseded partition behind (86 rows in threads against 51 current threads on the operator's store). load_session_for_reflection re-detects from scratch, so the queue holds ids no current detection produces. reflection_queue.thread_id is ON DELETE CASCADE precisely to retire those and never fired, because nothing deleted the stale partition. FIXED by lifecycle.persist_detection, the ONE replace-and-restore sequence both run_session_end and redetect_threads now call. THE STANDING RULE IS UNCHANGED: unemittable_queue_rows names them, emit_reflection_pass reports the count, and blanket-draining is still forbidden — it would destroy the only evidence the class exists, which is how it survived #527 r4. superseded_queue_rows is the strict subset that is PROVABLY stale (id absent from the current detection); reconcile_reflection_queue retires exactly those, dry by default, and leaves the below-threshold remainder standing because that is the real signal. STANDING IS NOT OWING (techne#870, schema v28): `--apply` also PARKS the below-threshold rows (`parked_at`), which keeps them undrained and in the table but takes them out of `pending_reflection_queue`, the banner's debt figure and `reflection_debt_stats.pending`. The banner counts them on a separate line. A parked row UN-PARKS wherever the code learns it renders again: `enqueue_reflection_debt` (every id it gets is emittable), `emit_reflection_pass`, and the next `reconcile`. emit reports the split as NUMBERS (`unemittable_superseded`, `unemittable_below_threshold`, techne#805), computed by `_split_unemittable` from the detection emit already holds rather than two more.
- AN OBSERVATION'S HEAD IS NOT ITS POINT (issue #907). `_clip_observation` keeps the first MAX_OBS_CONTENT_CHARS of each observation and then rescues up to MAX_SALVAGED_LINES failure-shaped lines (error/fail/traceback/…, each capped) from the elided tail, the LAST ones, before the newline flatten, because salvage needs line structure. A Bash row's head is its command echo, so a prefix slice alone asked the model what a session concluded while hiding every error. The cap is what keeps the rescue from becoming a second uncapped channel into a 40-observation prompt.
- `run_session_end(derive_if_idle_hours=…)` is for REPLAY callers (issue #986). The `techne session-end` CLI passes the sweep's idle window, so a session silent past it gets `ended_at` = last activity stamped `derived` (the same value `close_abandoned_sessions` writes, from the shared `_LAST_SEEN_SQL`), and an existing end at or after last activity is left alone. The SessionEnd hook passes nothing: it fires as the session ends, where now/`clean` is right. The Stop hook stamps no end at all (`mode="checkpoint"`, next bullet).
- LESSON TYPES ARE OUTSIDE EVERY RAIL HERE (techne#1195). lesson/grant/charter need a lesson_meta row, which only core/lessons.py writes, so: reflect's prompt and promote dispatch use knowledge.GENERIC_TYPES (a lesson-typed candidate promotes as `fact`, never as a meta-less lesson); consolidate/dream select with `type NOT IN LESSON_TYPES_SQL` (sleepdream._CLUSTERABLE and the recombine query), and so does conflict.conflict_check_emit's live-row query (select_conflict_candidates only ever sees what that hands it); _merge_in_conn refuses a lesson-type old; consolidate_ingest refuses a merge naming a lesson-type target (the direct-ingest backstop, as for document_card); _retire_in_conn refuses every lesson type, since retiring a principle into another row strands its family (they retire with `techne lesson retire`); and _supersede_in_conn refuses every lesson type unless lessons.refine passes `lesson_path=True`, because any other supersede copies the old meta rule and the band keeps rendering it. A grant or charter also needs `operator=True`, which only the CLI passes. A supersede of a lesson CARRIES its lesson_meta and family to the new revision (knowledge._carry_lesson_meta).
- `run_session_end(mode=…)` (techne#1187): Claude Code's Stop fires every TURN, so the Stop hook runs `mode="checkpoint"` — threads are still re-detected and reflection debt still enqueued, but a `sync:thread_summary` row goes out only for a thread that grew by `threads.checkpoint_min_new_observations` since its last send, at least `checkpoint_min_interval_minutes` later, and `ended_at` is NOT stamped. SessionEnd runs `mode="final"` (every thread with new work, then the end stamp); PreCompact runs `"compact"` (every thread with new work, no end). Per-thread send state lives in `extension_state` under `thread_sync.<session>`; `finalize_quiet_sessions` gives a session that never fired SessionEnd its final pass once it has been quiet for `ABANDONED_SESSION_IDLE_HOURS`. A pending summary for the same `thread_id` is replaced, not duplicated (`enqueue(supersede_key=…)`).
- document_card is a MANAGED type and neither promote nor merge may mint one (#633). _card_type_or_fact demotes a `document_card` whose tags carry no `doc:<id>` pointer down to `fact`: the content is real prose about a document, it just is not a card, and an unbacked card leaves `fsck` dangling_cards red forever (four such rows exist from before the guard).
- Enqueue INSIDE the deleting transaction, on the caller's conn (#527 r5). REVERSES an earlier card line saying the opposite ("after COMMIT, never inside"), which was true of the code and wrong about the cause: persisted_thread_id opened its own connection, so it could not see the caller's uncommitted rows and the insert hit a FOREIGN KEY failure. The seam was a missing `conn=` param, not an ordering constraint. Out of the transaction a failed enqueue leaves a permanent half-applied redetect — nothing re-derives debt for an emittable thread with no queue row.
- enqueue_reflection_debt takes thread_ids as a REQUIRED argument; the "queue every thread" default is gone. With no observation list you cannot apply min_observations_per_thread, so it queued sub-threshold threads emit never produces a prompt for and the drain could never clear (#527 r4/r5).
- sleepdream.py (techne#108):
  - consolidate (sleep): find dup/overlapping live knowledge — Tier0 exact content_fingerprint buckets | Tier1 FTS self-sim top-neighbor, queried with a DIGEST of the row (its top tf-idf terms that another live row also holds, OR-joined) — the whole row as an implicit-AND query matched only itself, so Tier 1 never formed a cluster (techne#987) | document_card rows are never clustered, and consolidate_ingest refuses a merge naming one, because a card's identity is its `doc:` pointer and a merge mints a pointerless fact (techne#823) | Tier2 vector dup-band (deferred) → action='merge'.
  - dream (recombine): non-obvious A+B→C across a shared-tag group → action='add', origin='dream', confidence='low' (abstention-first; most groups yield nothing).
  - LIVE, for both, is `superseded_by IS NULL AND status != 'archived'` (techne#1033 review round 2), not `superseded_by IS NULL` alone: `knowledge.delete()` can archive a chain-head's predecessor (superseded_by NULL, status='archived') rather than resurrecting it, and a status-blind cluster/group source would otherwise merge or recombine that retired fact into a fresh `current` row — `merge_into`'s live-row guard was given the same `status != 'archived'` check for the same reason.
API: MCP pairs techne_reflect_emit/ingest, techne_consolidate_emit/ingest, techne_faithfulness_emit/ingest, techne_dream_emit/ingest, techne_memory_claims_emit/ingest; CLI techne reflect/consolidate/dream. The /techne-promote skill drives this end-to-end each session.
INVARIANTS:
- reflection_queue.drained_at is NULLABLE, not a status enum: pending is the ABSENCE of a drain, so there is no second source of truth to disagree with the timestamp. Drain is guarded on `drained_at IS NULL` so a re-drain never rewrites the first payment.
- THE FK GRAPH AROUND threads(id), WHICH IS WHAT #797 TURNED ON. FOUR columns reference it and only ONE cascades: reflection_queue.thread_id (CASCADE), threads.parent_thread_id, knowledge_candidates.source_thread_id and observations.thread_id (all NO ACTION). The CASCADE on reflection_queue is REQUIRED and load-bearing — pruning a superseded thread retires its queue row for free, which is how #646's stale rows are cleared. THE OTHER THREE ARE WHY re-detection NO LONGER DELETES A SESSION'S WHOLE THREAD SET. This line used to say it did, and that a plain reference would make the queue block re-detection; the second half is still true, but the first half described behaviour that raised `IntegrityError: FOREIGN KEY constraint failed` on any store with history and took run_session_end down with it (#793 put it on the per-turn path; the defect was latent in redetect_threads long before). `lifecycle.persist_detection` now PRUNES: it deletes only session threads that are (1) absent from the detection about to be saved, (2) unreferenced by any of the three NO ACTION columns, and (3) not carrying a DRAINED queue row. Condition (1) also preserves reflection-debt AGE — the cascade would take a still-current thread's PENDING row and the re-enqueue would re-date it, and nothing restores enqueued_at. Threads the prune SPARES keep their stale queue rows; `techne reflect reconcile` retires those. tests/test_detection_replace.py derives the guard list from `PRAGMA foreign_key_list` so a fifth referencing column is caught when it is added rather than when it breaks.
- THE EMIT BUDGET IS MEASURED ON WHAT THE MCP SERVER SENDS (techne#993): `_sent_chars` is `len(json.dumps(result, indent=2))` over the whole result, envelope and notes included, matching `mcp_server.handle_request`. It summed compact per-item JSON before, and the 100,000 default sat above the client's 25K-token cap (the smallest recorded refusal was 56,974 chars); it is now 45,000.
- Every consolidate cluster has a stable cluster_hash (prompt_hash col) → a cluster already proposed (pending, promoted, OR kept-distinct) is never re-judged (_already_proposed) — stops the anti-bloat feature from bloating its own review queue.
- _FAITHFULNESS_GATED_ACTIONS={'merge','supersede'}: promoting a merge/supersede candidate needs a prior faithfulness check (raises FaithfulnessGateError unless force=True); keep this gate in sync with faithfulness_emit's SQL filter.
- reflect.py's two public entry points, ingest_one_and_drain and ingest_reflection_response, plus ingest_reflection_batch's forwarding call into ingest_one_and_drain, now import `RESIDENT_PRODUCER` from sleepdream.py instead of re-typing `"agent-assisted"` at three sites (#712). They were the one place the literal drifted from the constant unnoticed — `reflect` is one of the rails `check_model_bound_rails` enumerates, but #709's guard only pinned consolidate_ingest/dream_ingest/conflict_check_ingest/federation_conflict_ingest. The two public entry points are now in `test_resident_ingest_still_labels_rows_agent_assisted`'s tuple too. THE THIRD SITE NEEDED A DIFFERENT GUARD: `ingest_reflection_batch`'s forward is a `dict.get(..., RESIDENT_PRODUCER)` fallback, invisible to `inspect.signature` (that test's mechanism), so `test_batch_ingest_labels_an_unset_item_agent_assisted` pins it behaviorally instead — a batch item with no `model_used` key must still write a row labelled `agent-assisted`. Mutating the fallback fails that test while leaving the signature-based one green.

**THE AUTOMATIC PATH RECORDS A LIVENESS MARKER NOW (techne#555).** `reflect_on_session` catches every LLM failure, counts it in `result["errors"]`, and lets teardown proceed — correct, because teardown must not fail on reflection. But a counter nobody reads is not a signal: MEASURED 2026-08-21, this rail had produced ZERO candidates since 2026-06-20 (every one of the 444 in the store came from the RESIDENT emit→ingest route, `model_used='agent-assisted'`), because `config.model` is an Anthropic id and the operator holds no Console API key. `AuthenticationError` on every session, for two months, while `check_maintenance_rails` read the rail LIVE off the resident route's output. It now writes `rail:reflect:last_run` via `custodian.record_rail_marker` on EVERY outcome — ok / partial / error / noop — carrying the exception TYPE, because "AuthenticationError" says *needs a credential it was never given* where a generic failure says only *broken*. Never raises into teardown.

**THE PROPOSING PROMPT FAILS TWO OPPOSITE WAYS, AND AN INSTRUCTION THAT PUSHES ONLY ONE WAY TRADES ONE FOR THE OTHER (techne#950).** Measured, not argued -- but on ONE candidate set judged TWICE, not two independent runs, and the two judges DISAGREE about which failure is larger. #950 reports 32 candidates from 13 threads, 26 promoted; #951 reports self 26/32 on the same 32. So the self-judge's "specifics, 4 of 6 discards" and the blind judge's "obvious, 4 of 9" are two readings of overlapping evidence (the blind judge's 9 also span 22 live candidates). Self-judge ranks specifics larger; blind judge ranks obvious larger at 4 against 2. Treat the two failure MODES as established and their relative size as unsettled. (1) TOO SPECIFIC: "durable, evidence-anchored" pushes toward details, and details are what go stale — four of six discards in the 2026-09-17 run were counts a later fix changes, image tags, a pinned Python version upstream will bump, and supersession status on a ticket. The clearest case is two candidates from ONE thread, one quoting the image tags and one stating the rule; only the rule stays true. (2) TOO GENERIC: in the blind-judged run (techne#951) the judge's TOP discard reason was `obvious`, 4 of 9, AHEAD of decaying specifics at 2 — "a Job uses the CronJob spec as it stood at creation time" (standard Kubernetes), "a fresh clone has no git identity" (standard git, and wrong where a global identity exists -- which is why the PROMPT teaches the mode with "re-read the repo before citing it" instead: a false claim is a poor model of an already-known fact), "re-read the repo before citing it" (generic hygiene). So the prompt NAMES both failures explicitly, with an example of each drawn from the real discards, and then describes the band between them: non-obvious to a competent practitioner, and still true once the identifiers change. A "prefer the rule" instruction alone would have driven candidates into the other ditch. WHAT SHIPPED IS A THIRD VARIANT: #950's comment proposed replacing the original wording outright, and this keeps the original instruction AND adds the named failures, so it is neither the issue's text nor the comment's. Nobody has measured it -- see the unmeasured caveat below.
  NOT YET MEASURED, AND THE ISSUE ASKS FOR IT: a before/after run on the same threads. Self-judging would reproduce exactly the bias techne#950 already flags in its own caveat — Grip proposed AND judged, so their promote rate is not a quality measure, and neither would ours be. The reasons for discarding are the signal; the rate is not.
**`high` REQUIRES VERIFICATION AT AUTHORSHIP (techne#790).** The prompt tells the author the observation block is an INDEX, not evidence (head-only, clipped), and that a `high` item naming a number, issue/PR, state or mechanism must be checked against the source first, else written at `medium` with what is unconfirmed, or dropped. It is a stated expectation, not a rail: nothing verifies it. It is placed at authorship because that is where the one measured catch happened (two of three stops-to-verify changed the claim during the 2026-08 drain; the pending queue caught none), and it holds under either `write_to` -- it does not answer techne#828. The same rule is in the `techne-promote` skill and the reflect guide's agent block, pinned together by `test_high_confidence_requires_verification_in_every_authoring_surface`. A headless rail cannot run commands, so for it the rule reduces to "do not write `high` on those claims".
**PROMOTION STAMPS `last_confirmed_at`, AND IT HAS TO (techne#938).** `_apply_add` is `promote_candidate`'s "add" dispatch -- the main way curated knowledge grows -- and its INSERT did not name the column. That was harmless only while the CREATE TABLE carried `NOT NULL DEFAULT CURRENT_TIMESTAMP`. #938 removed that default (it could not be reconciled with what the v5 ALTER produces, so a fresh and a migrated store disagreed at the same schema_version), which means EVERY writer now owns the value -- and a promotion path that omits it writes NULL, putting the row on `decay_score`'s no-decay branch forever. The first cut of #938 patched three INSERT sites and missed this one and `cards.py`, so it briefly moved FRESH installs toward the migrated store's broken state for exactly the rows this rail produces. `test_every_insert_into_knowledge_sets_the_timestamp` derives the writer list from source rather than enumerating it, because an enumerated test cannot catch the path nobody enumerated.
  THE DEFERRED HALF HAS A COST, AND A SUCCESSOR (techne#979). Not backfilling the 2,823 existing NULLs is the right call -- the blast radius is every install and the eval gate is the right arbiter -- but it is NOT cost-free, and an earlier version of this entry implied it was. It makes a within-store INVERSION the dominant regime: a legacy NULL row scores 0.9 forever while a 60-day-old new row scores 0.225, a 0.0675 delta at `confidence_decay_weight` 0.1 against the 0.0100 margin that decides real identifier queries on this store. Where 96.9% of rows are NULL, everything written from now on is progressively out-ranked by everything written before it -- the decay term running backwards for the dominant population.
  THE TRIGGER ALTERNATIVE WAS CONSIDERED AND NOT TAKEN, recorded so it is not re-derived. `CREATE TRIGGER IF NOT EXISTS ... AFTER INSERT ON knowledge WHEN NEW.last_confirmed_at IS NULL` would bind ad-hoc SQL and future writers that never run the test, is identical on both store shapes, needs no rebuild, and the repo already uses triggers for `knowledge_fts`. Against: a write per insert, and the trigger must then be created identically in init_db AND the migration -- the two-shapes-must-agree problem one level up, though a more tractable one. The derived writer test was judged a reasonable substitute.


**THE EMIT CURSOR IS KEYED ON `thread_id`, AND THE REASON IS THE WHOLE LESSON (techne#733, 2026-08-23).** It used to hold `prompt_hash`, called in its own comment "the stable, always-present per-thread id". IT IS NOT STABLE: `_prompt_hash` hashes the RENDERED prompt, and `_build_prompt` embeds a freshly-retrieved existing-knowledge block, so the hash of a thread whose observations are frozen still moves whenever LIVE KNOWLEDGE changes — every reflect, promote or `techne_store` call. The old comment scoped that to `write_to='live'`; the real trigger is any knowledge write from any session, continuously.
THE FAILURE ACCUMULATES, WHICH IS WHY IT RAN SO LONG. A drifted hash matches nothing, so the thread is re-emitted AND a second entry is appended. MEASURED: session 0ae96e10 held 51 entries for 23 renderable threads, 48 matching no current render, `remaining` = -27; six sessions were in this state.
AND IT HID ITSELF. `_marker_has_unemitted_threads` answers `len(emitted) < total`, so an OVER-FULL cursor reads as fully emitted — every corrupted session dropped out of the SessionStart nudge, and 126 owed queue rows were reported to the operator as 50. A corrupt cursor now reads as PENDING. "We do not know" is a reason to re-surface, never to stay silent (same fail-open shape as #709's UNKNOWN verdict).
THE KEY IS NOT ARBITRARY: `thread_id` is what `reflection_queue` is keyed on and what `drain_reflection_queue` stamps, so the cursor and the ledger now agree BY CONSTRUCTION rather than by coincidence — two derivations of one fact, collapsed to one. **READ THAT SENTENCE AS SCOPED TO THE KEY, WHICH IS NOT HOW IT WAS WRITTEN (techne#900).** Sharing a key makes the two COMPARABLE; it does not make them agree, and for two more weeks nothing compared them. See the #900 section at the end of this card. `prompt_hash` stays exactly where it belongs, on candidate dedup (#236), which WANTS to notice a re-render. A pre-#733 marker is not migrated (its contents are unrecoverable); the delivered set is rebuilt from drained queue rows.
ORDERING IS PART OF THE CONTRACT: the char budget is spent in batch order, so owed threads sort ahead of paid ones. Without that, a session whose early threads are already drained spends every pass re-rendering them and never reaches what it owes — the reported symptom was 11 emitted prompts containing ZERO owed threads. And `emit_reflection_batch` now yields one item per persisted thread: two Thread objects can resolve to one `threads.id`, and the duplicate is rendered and answered twice.

**THE CURSOR IS RECONCILED AT WRITE TIME, NOT APPENDED TO — AND THAT IS THE HALF THE RE-KEY ALONE DID NOT FIX (Prudence, #734 r1).** Re-keying stopped the drift; it did not give a corrupt cursor a way back out, and reading one as PENDING without a repair path is the same defect wearing the opposite sign. THE MARKER WRITE WAS GATED ON `bool(batch)`, so once a session was fully emitted nothing could rewrite it: an over-full or legacy marker read pending on every pass with NO OPERATION ABLE TO CLEAR IT (measured: five consecutive passes, `key` never leaving None). A banner that cannot go green trains the operator to ignore the rail, which loses owed work by a different route than #733 did.
THREE SYMPTOMS, ONE MISSING STEP. The persisted set is now intersected with what the session can render RIGHT NOW before it is stored, which (a) drops keys that no longer render instead of hoarding them, (b) stops the legacy-rebuild path writing an over-full marker in the NEW format — which recorded `remaining: 0` while reading pending, internally incoherent — and (c) BOUNDS the `prompt_hash` fallback. That fallback is not merely "inherited instability": before reconciliation it grew 1,2,3,4,5,6 across six passes, which is #733 verbatim inside the branch that closes it. Reconciliation turns accumulation into re-offering, which is what the fallback's docstring always claimed it was.
`oversized` STILL WITHHOLDS THE ADVANCE (#268 footgun 3) — a lone thread too big to deliver must keep re-surfacing. Only the completed-but-empty case now writes.
AND THE INVARIANT IS ASSERTED AT THE WRITE POINT: `len(emitted) <= total`, raising rather than clamping. It cannot fire today because the reconciliation makes it unreachable, WHICH IS THE POINT — #733 survived two months because this was only ever checked by arithmetic (`len(emitted) < total`) that failed open and answered "done" for the markers that were worst.
COLLISION RESOLUTION IS LOSSLESS — THE BUCKETS ARE UNIONED, NOT PICKED BETWEEN (Prudence, #734 r2). `obs_by_thread` is keyed on `thread_num`, so two Thread objects resolving to one `threads.id` carry DIFFERENT observations and `_build_prompt` renders only what it is handed. PICKING a winner therefore discards the loser's observations permanently, by either rule: measured across three trees, main emitted both (3 and 11), first-wins dropped the 11, richest-wins dropped the 3. Against the merge base either choice converts "both reflected, one wasted drain" into "one reflected, the rest discarded" — and the duplicate drain being avoided was ALREADY a no-op, since `drain_reflection_queue` is guarded on `drained_at IS NULL`. The index sets are disjoint BY CONSTRUCTION on the default `heuristic` detector (`split_at_boundaries` appends each index once, ascending; `merge_pass` concatenates adjacent segments only) — on `detector: llm` the indices come from parsing an LLM's free-text `Observations:` line and nothing validates them for order, duplicates or overlap, so the union is still correct there but for a WEAKER reason. Unioning is both smaller and correct; the representative thread supplies label/summary only.
A MARKER MUST BE ABLE TO RE-OPEN ITS OWN SESSION. Writing on a completed-but-empty pass closed the uncleanable cursor and opened a new silence: a session with nothing renderable was stamped `total: 0`, and `_marker_has_unemitted_threads` reads `total` OUT OF THE MARKER and never recomputes it, so `0 < 0` is false forever. Measured: origin/main nudged such a session after a 12-observation backfill; the new marker returned `[]` while an explicit emit returned `count: 1`. The marker now records the observation count it was written at, and a caller that knows the current count can say "this session has grown". Legacy markers carry no count — absent means CANNOT TELL, which keeps old behaviour rather than re-surfacing every historical session.

**THE AUTOMATIC PASS IS UNBOUND BY DEFAULT, AND THAT IS THE FIX (2026-08-23).** The marker above did its job on first contact: `rail:reflect:bound` read BROKEN the day #709 deployed. THE CAUSE WAS THE FALLBACK ITSELF — `reflect_on_session` used `config.reflect.model or config.model`, so an operator who never chose a headless model still got an unattended call to whatever the session used. It now requires an explicit `reflect.model`; empty means the automatic pass does not run, and no LLM is called.
TWO SWITCHES, NOT ONE, and confusing them is the trap. `reflect.enabled` turns the FEATURE on — including the SessionStart nudge and the reflection-debt queue, which drive the RESIDENT route. `reflect.model` binds only the automatic pass. So the obvious remedy for a noisy unbound rail — `reflect.enabled: false` — trades the working path for the dead one: it silences a rail that produces nothing by switching off the one that produces everything. Enabled-and-unbound is a normal, fully-working posture.
UNBINDING RETRACTS THE MARKER (`custodian.clear_rail_marker` over `extension_state.clear_state`), because a marker describes the last BOUND run and there is no longer any such run to describe. THE JUSTIFICATION IS NOT REPEATED HERE — it lives in `clear_rail_marker`'s docstring, one copy, since techne#735 retired the original one ("absence is what the check reads as DORMANT") and replaced it with a measured argument about RE-BINDING.
BUT THE RETRACTION IS WRITE-TIME AND THEREFORE COVERS ONLY THIS PATH (techne#735). It fires inside `reflect_on_session`, so it needs a session to actually end; `reflect.enabled=false` never reaches it at all, because `lifecycle.py` gates the call site on that flag. Both left `rail:reflect:bound` reading LIVE off a stale `ok` — permanently on the disabled path. The verdict is now gated at READ time on `checks._rail_binding`, which asks whether the rail is bound before trusting the payload. Read this bullet as "retraction keeps the store tidy", not as "retraction is what makes the doctor honest".

**CANDIDATE ROWS NOW NAME THEIR PRODUCER (techne#555).** `_insert_consolidation_candidate` / `_insert_dream_candidate` hardcoded `model_used='agent-assisted'` in their VALUES clause. That was correct while the RESIDENT agent was the only thing answering these prompts; the custodian makes a second producer real, and a headless row claiming a resident agent judged it destroys the one column that distinguishes them — the same blindness that hid the automatic reflect rail for two months. Now a bound parameter, REQUIRED on the private inserters (no default, so a missed forward is a TypeError rather than a silent lie) and defaulted to `RESIDENT_PRODUCER` on the public `*_ingest` entry points, which is what leaves the resident path byte-for-byte unchanged. `RESIDENT_PRODUCER` is defined here ONCE; conflict.py and federation.py import it rather than re-typing the literal (techne#518).

**THE CURSOR DOES NOT OUTRANK THE LEDGER, AND THE #733 RE-KEY DID NOT ALREADY GUARANTEE THAT (techne#900, 2026-09-07).** The re-key made cursor and queue agree "by construction"; the card says so two sections up, and `_emitted_keys` says so in prose. NOTHING ENFORCED IT. `delivered` is set when a batch is RENDERED, so a pass whose answers never come back stamps its threads emitted while their queue rows stay undrained — permanently, because `_emitted_keys` trusts a `key: thread_id` marker unconditionally. Every later emit returns `count: 0` for a session the banner still reads as PENDING, and `reconcile` cannot classify the rows: they are neither superseded nor below-threshold, they RENDER FINE. That is a third population, and it was invisible to both reporters because both classify rows that cannot render.
THE TRIGGER IS THE ROUTINE CASE, NOT AN EDGE ONE. `techne_reflect_emit` regularly exceeds the MCP tool-result token cap and spills to a file, so the agent never receives the batch the cursor was just advanced for. MEASURED: session e9be3469 listed 12 emitted against 4 drained — 8 orphaned threads of 42 to 172 observations each; session eec74e57 orphaned one thread of 287. The oversized call is not tied to either of those: on 2026-09-07 an emit RENDERED FOR e9be3469 and issued from session 18f13f92 came back 52,068 characters across 37 lines and spilled to a file.
THE FIX IS SCOPED TO AN EMPTY BATCH, WHICH IS THE ONLY PLACE THE CURSOR IS PROVABLY WRONG. An empty batch is the cursor claiming "nothing left" about a session whose ledger still records owed rows that render today; those keys are dropped and re-offered. A NON-EMPTY BATCH CHANGES NOTHING, and that restraint is load-bearing: `techne reflect emit -o file` legitimately renders a whole batch long before `ingest file` pays it, so a ledger that simply overruled the cursor would re-render everything already in the file. Advancing the cursor on ingest instead — the more obviously correct rule — breaks that same path, which is why it was rejected.
PARTIAL BY DESIGN, STATED RATHER THAN HIDDEN — TWO CASES, THE SECOND FOUND IN REVIEW. (1) A session holding both orphaned and never-emitted threads heals only once the never-emitted ones drain and the batch goes empty; `_owed_first` sorts owed rows to the front, so it gets there, just not immediately. (2) An OVERSIZED never-emitted sibling keeps the batch non-empty forever, so the heal never fires at all (Prudence, #901 r1). That is subsumed by the blocking `oversized` already documents — a lone thread too big to deliver blocks every thread after it — but it is a second way an orphan can sit unreached, and it clears when per-thread chunking lands (#269 follow-up).
A DECLINE IS NOT AN ORPHAN, AND CONFLATING THEM COST A TERMINATION PROOF (Prudence, #901 r1). `ingest_reflection_batch` blesses a blank `raw_response` as a deliberate refusal: skipped WITHOUT draining, debt stays owed. That is byte-for-byte the shape the heal fires on, so `reflect-guide.md`'s documented "repeat until the batch comes back empty" loop STOPPED TERMINATING — measured at 6 iterations, the same thread every time, where the pre-#900 code stopped at 2. THE DISCRIMINATOR IS WHETHER INGEST EVER SAW THE THREAD: an orphan is one it never saw, a decline is one it saw and refused, and only the first is a bookkeeping accident. Declines are recorded in the marker's `declined` list, carried forward across the wholesale marker rewrite, excluded from the heal and from `orphaned_queue_rows`, retired by a later real answer, and reported by `reconcile` as their own population. THEY ARE COUNTED APART BECAUSE THEY PROMISE OPPOSITE THINGS: an orphan clears on the next emit, a decline is not re-offered while the cursor claims the thread. READ THAT SCOPING LITERALLY — "never re-offered" is what this card said until #901 r3, and Prudence built the counterexample: a decline recorded against a thread the cursor does NOT claim (a marker holding `emitted: []`) is offered normally, because the exclusion it would need never applies. Benign, and the safe direction, but the absolute form was false.
THE CARRY-FORWARD IS LOAD-BEARING, AND MY FIRST ACCOUNT OF WHY WAS WRONG (Prudence, #901 r2 correction). I claimed dropping `declined` from emit's marker write "re-arms the infinite loop". It does not: the heal reads `declined` BEFORE emit's write erases it, so the mutation is caught by a visibility assertion and the behaviour it produces is "re-offered once per drain run", not a spin. Keep the field, and keep the reason accurate — a mutation that fails for a different reason than the comment claims is how a suite drifts into theatre.
TWO WAYS THE DECLINE RECORD ITSELF WENT WRONG, both found by running it (Prudence, #901 r2). (1) IT MINTED A MARKER. `_record_declines` built the payload with `dict(get_state(...) or {})`, so a decline against a session that never emitted wrote `{"declined": [...]}` with no `emitted` key — and `_marker_has_unemitted_threads` reads `emitted is None` as a #268-era marker, NOT PENDING, permanently and ahead of the observations-growth re-open. That is wider than the nudge: `pending_reflection` is where `emit_reflection_pass` picks its default target, so the session went unreachable from both hooks AND both emit entry points, leaving only an explicit id. It now writes into an EXISTING marker or not at all, which is correct rather than merely safe — with no marker, `_emitted_keys` rebuilds from drained rows, a declined row is not drained, so the cursor never claims it and there is nothing for the heal to suppress. (2) IT WAS A ONE-WAY DOOR. `techne reflect emit` PRE-FILLS `raw_response: ""` as its placeholder and `ingest` reads that same literal as refusal, so an ordinary partial fill is indistinguishable from a deliberate one. That collision was harmless while #900's heal re-offered; r1 removed the recovery to stop the loop spinning and added none, so a declined thread whose batch file was lost was owed forever and unpayable. `clear_declines` / `techne reflect undecline` is the way back, and the emit CLI now says at write time what leaving an item blank costs. THE DESIGN CALL IS UNCHANGED — a decline is a decision and nothing re-offers it on its own; it is just no longer irreversible.
`orphaned_queue_rows` AND `declined_queue_rows` REPORT AND NEVER SWEEP (#646's rule, unchanged) — `reconcile` counts it as a third population alongside superseded and below_threshold and removes none of it. With the self-heal in place a nonzero count is a REGRESSION SIGNAL, not a work list.
AND ONE #733 TEST WAS AMENDED, WHICH IS THE PART TO DISTRUST FIRST. `test_a_drifting_hash_does_not_re_emit_or_inflate_the_cursor` skipped the ingest and still demanded `count == 0`, conflating "a knowledge write must not re-emit" (#733, true) with "an un-ingested thread stays delivered forever" (#900, the bug). It now drains between the two emits, which isolates hash drift — the only thing #733 is about — and its teeth were re-verified by mutation: forcing `_cursor_key` back to `prompt_hash` still fails it.

**A REVIEWER CAN PROMOTE AN EDIT, AND THE PROPOSAL IS NEVER OVERWRITTEN (techne#952, 2026-09-17).** Review had promote and discard. A blind-judged external run found the common disagreement was a durable claim wrapped in counts or ids that go stale: discard lost the claim, promote stored the wrapper. `promote_candidate(revised_content=...)` / `techne reflect promote --content` applies the edit through the same applier by handing it a copy of the row with `content` swapped, and stores the edit in `knowledge_candidates.revised_content`.
`content` STAYS AS PROPOSED, FOR TWO REASONS. It is half of `idx_kc_reflect_dedup (prompt_hash, content)`, so rewriting it would let a re-ingest of the same answer insert a fresh pending duplicate. And it is the record of what the model proposed, which is what a prompt change (#950) is measured against; `candidate_stats` reports `revised` for that.
ADD-ONLY (`_REVISABLE_ACTIONS`). A merge or supersede carries a faithfulness verdict computed on its original text. Revising it leaves the verdict describing text that is not applied, and resetting the verdict instead would turn revision into a way past the gate. A revision also requires a `decision_reason`.

**PROMOTED KNOWLEDGE RECORDS ITS SESSION (techne#949, schema v26).** `knowledge.origin_session` was NULL on every promoted row (3,090 of 3,090 on the operator's store); the session was reachable only through `knowledge_candidates.promoted_to_id` or by parsing `source`. `promote_candidate` now stamps it for `_ROW_MINTING_ACTIONS` (add, supersede, merge) in the same transaction, and the `write_to: live` auto-path passes it in `store()`'s provenance. RETIRE IS EXCLUDED on purpose: its applier returns an existing survivor, which did not originate in the retiring session. SO IS THE SLEEP SENTINEL (Prudence, #961 r1): consolidate merges, dream adds and every conflict supersede are filed under `SYSTEM_SLEEP_SESSION` ('system:sleep'), a placeholder that satisfies the FK. Stamping it recorded a merged fact, or a team store's fact, as originating in a local session. `_is_real_session` skips it, so in practice only reflect `add`s are stamped; the others stay NULL, unattributed rather than guessed. The v26 migration backfills existing rows by the same rule, sentinel included, where v25 refused to backfill its columns: a federated row's local source had been discarded, but a promoted row's session is recorded on its candidate. The thread is still reached through `knowledge_candidates.source_thread_id`; `knowledge` has no thread column.

**THE `prompt_hash` FALLBACK WAS NOT THE RARE CASE ITS DOCSTRING SAID (techne#954, 2026-09-17).** `_cursor_key` fell back to `prompt_hash` for a thread with no persisted row, described as "an unsaved/legacy thread". `techne import` persisted NO threads at all, so on an imported corpus the fallback was every thread. MEASURED on an external store: 35,096 imported observations, 0 `threads` rows, `thread_id` null on 18/18 emitted items. A backfill that promoted as it went changed live knowledge, every hash moved, and the next emit re-offered threads already ingested. The same missing rows are why those candidates carry a NULL `source_thread_id` (#949).
TWO CHANGES. (1) `techne import` now calls `lifecycle.ensure_threads` for each imported session, which goes through `redetect_threads` and so also enqueues reflection debt. A benign skip ("already has N observations") runs it with `replace=False`, so re-running `techne import` repairs a store imported before the fix and leaves hook-detected sessions alone. (2) A thread that still arrives unpersisted carries `obs_key`, a hash of its observation ids, and `_cursor_key` prefers it over `prompt_hash`. Observation ids move only when the thread's membership does; the knowledge block cannot touch them. `prompt_hash` remains the last resort, for in-memory observations with no ids.
AN `obs_key` IS A KEY WITHOUT A LEDGER, AND THE FIRST VERSION FORGOT THAT (Prudence, #955 r1). Emit claims on render; the #900 heal repairs a render-without-answer from `reflection_queue`, and an unpersisted thread has no queue row. So a stable key turned "re-offered by accident" (the drifting `prompt_hash`) into "dropped with every counter at zero". The ledger is now the marker's `answered` list: `ingest_one_and_drain(obs_key=...)` writes it via `_claim_answered`, emit carries it forward like `declined`, and the empty-batch heal re-offers `obs-` keys in the cursor that are neither answered nor declined. Declines record the `obs_key`, so `undecline` reaches them. Mutation-checked: removing either half fails its tests.
OVER MCP THE KEY IS THE CALLER'S TO PASS, so the tool description names `obs_key` beside `thread_id`, and `_techne_reflect_ingest` returns a `warning` when an item has neither — the agent reads the result, not the schema (Prudence, #955 r2). Without it the documented drain loop re-offered the same answered thread every pass, measured `[1, 1, 1, 1]`. The CLI path is unaffected: `ingest_reflection_batch` reads `obs_key` off the item.
UPGRADE COST, STATED: re-running `techne import` on a store backfilled before the fix re-offers each already-answered thread once. Their candidates carry a NULL `source_thread_id` (#949), so nothing links them to the threads the repair persists.
**EMIT PERSISTS WHAT ITS OWN DETECTION FOUND (techne#1091, 2026-09-29).** Import was not the last source of unpersisted threads. Emit re-detects from observations, and that detection runs ahead of the last persisted one whenever observations land after the final `session_end` detection (18200f28: detected at 323 observations, 446 now, threads 28-34 without rows) or the detector changed since the session was saved (2db12bfe: 11 saved thread numbers, 28 detected today). Those items went out `thread_id: null`; the overnight drain read the MCP schema's required `thread_id` as "cannot ingest", skipped them, and the #954 heal re-offered them every pass, so 13 of 95 sessions ended partial. `emit_reflection_pass` now calls `persist_unsaved_threads` before rendering: for each emittable thread `persisted_thread_id` cannot resolve, it upserts the row (`save_threads`) and enqueues its debt in one transaction. IT WRITES ONLY WHAT IS MISSING and prunes nothing; a thread resolved through the `(session_id, thread_num)` fallback keeps its old id, because writing its computed id too would make `persisted_thread_id` prefer the new row and re-offer a paid thread. It also moves the #954 ledger: each `obs-` key in the marker's `emitted`/`declined` is rewritten to the thread's id, and an `answered` one drains that thread's queue row, so a store drained by `obs_key` is not re-offered. That runs on EVERY emit for every emittable thread that resolves, not only the ones the call writes (techne#1106): an `obs_key` answer ingested after the emit that persisted its thread (a batch rendered on the fallback path, ingested later) otherwise left the row owed, and the #900 heal served it once more. Resolving the key at ingest instead would mean re-detecting the session per item; emit already holds the detection, so the cost is one hash per thread. A thread id that several detected threads resolve to (#733) drains only when all their keys are answered. A write failure logs a warning and leaves the `obs_key` fallback, which is why that path and its tests (now forcing the failure) stay.
**REPRODUCED AND FIXED AT IMPORT (techne#962, 2026-09-18).** This line previously read "Not reproduced here", and left that way it kept telling every recall consumer the bug was unconfirmed. It reproduces: a resumed session's transcript replays its parent's turns carrying their ORIGINAL message uuids under a NEW sessionId, and import idempotency is per session, so they import twice. Measured across 373 non-agent transcripts — 52 file pairs share message uuids, and of the 2 pairs with both halves imported, 44 observation rows were duplicated. Schema v27 records `observations.source_uuid` and import skips a record whose uuid is already stored. THE GUARD HAS A LIMIT WORTH KNOWING BEFORE YOU RELY ON IT: every pre-v27 row has `source_uuid` NULL and NULL never matches `= ?`, so a resume whose PARENT was imported before the upgrade still duplicates it. Closing that needs a backfill keyed on each session's own transcript (techne#978). THAT LIMIT IS EXACTLY "PRE-v27" ONLY BECAUSE BOTH WRITERS STAMP. `techne/sync/jsonl_transcript.py` is a SECOND writer into `observations` — same pairing, same filter, but its idempotency is a per-file BYTE-OFFSET cursor, and a resumed session is a new file — so until it stamped and consulted `source_uuid` it duplicated a resume on a FRESH store and left NULL rows that could not protect a later `techne import` either. Treat these two files as a pair: a third writer would reopen the hole the same way.
