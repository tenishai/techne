# archivist-query — guarded read-only SQL over the team store (techne#554)

SEAM: `query(config, sql, limit)` + `readable_schema(config)`. The ACCESS half of team memory; techne#553 (writer provenance) is the schema half — a query surface without provenance answers "what do we know" but never "who says so".
WHY SQL, NOT A FILTER DSL: #554's complaint is questions nobody wrote an endpoint for; a verb-per-question surface reproduces the gap it closes. The price is that it must be guarded, which is the whole module.

GUARD STACK — six layers, each enforced by SQLite, by query()'s fetch loop or by the OS, none load-bearing alone:
  1. ?mode=ro (via federation._open_remote_readonly — NOT a second opener; that one carries the measured WAL-sidecar caveat)
  2. set_authorizer — the load-bearing one. Denies ATTACH, all-but-one PRAGMA, every read outside ALLOWED_TABLES. Default branch is DENY, so a future SQLite action code is refused rather than waved through.
  3. set_progress_handler (OP_BUDGET) — read-only does NOT bound cost.
  4. size: setlimit SQLITE_LIMIT_LENGTH = MAX_VALUE_BYTES (1 MB), SQLITE_LIMIT_COLUMN = MAX_COLUMNS (64; a 400-wide row took ~1.2 GB before) and SQLITE_LIMIT_SQL_LENGTH = MAX_SQL_BYTES (100 KB), because the op budget counts VM steps and a C function runs as ONE step: length(replace(hex(zeroblob(5e7)),'0','00')) took ~590 MB (techne#1256); and query() iterates the cursor with a running total of value bytes (UTF-8 for text), refusing past MAX_RESULT_BYTES (16 MB), because up to MAX_LIMIT under-limit rows were materialised at once (~600 MB at 200 rows). None of these bounds SQLite's sorter (an ORDER BY over 1000 x 1 MB generated rows took ~550 MB); layer 6 does. A size refusal is a QueryDenied naming the limit.
  5. one statement only.
  6. worker process (techne#1313) — query() runs `_execute` in `python -I -c <_WORKER_BOOT> <root>`, request on stdin, one JSON reply on stdout. `-I` keeps cwd, PYTHONPATH and the user site out; `<root>` puts back the directory the caller's own `techne` came from, and the reply names the file the child imported techne from, which must equal the caller's or the result is refused (Prudence, PR 1315: without the pin, a worktree on a shared venv ran main's guards in the child under the PR's tests). The child sets `PRAGMA temp_store=MEMORY` and `PRAGMA hard_heap_limit` (config `archivist_query_heap_bytes`, 64 MiB) before the authorizer, so every sort, GROUP BY, DISTINCT and window counts against the cap and fails as MemoryError → QueryDenied. The parent kills it at `archivist_query_timeout_s` (10 s). WHY A PROCESS: the sorter spills to temp files but its merge holds about one record per spilled run, so spilling bounds neither memory nor disk (500 x 1 MB rows: 280 MB; temp_store=FILE no help, a smaller cache worse); the op budget lets ~2.4M generated rows through; and hard_heap_limit is process-wide, lower-only from Python, so set in the MCP server it would cap recall for life. Costs ~110 ms per query on dev04 (124 ms vs 12 ms in-process, a copy of the real store). Worker errors cross as JSON and are re-raised as the same sqlite3 class, so the QueryDenied / sqlite3.Error split below survives; a worker that cannot start, dies without a reply or ran another techne is `WorkerFailed` (a RuntimeError: a server fault, neither of the two).
NOT BY PARSING THE SQL. A parse-and-inspect allow-list is a regex that loses to the first sub-select nobody thought of; the authorizer denies `SELECT id FROM knowledge WHERE id IN (SELECT id FROM observations)` on the inner read with no parsing at all.

ATTACH IS THE ONE TO UNDERSTAND: a ?mode=ro connection can still ATTACH the operator's PERSONAL techne.db and read it out through this "team" surface. mode=ro does not stop that; only the authorizer does.

FOUR MEASURED FACTS a naive version gets wrong — all fail SILENTLY or read as bad SQL rather than as a broken guard (probed against a copy of the real 25MB archivist.db, py3.14.7/sqlite3.53.4):
  1. FTS5 needs `PRAGMA data_version` + SQLITE_READ on the knowledge_fts shadow tables (_config/_data/_docsize/_idx), issued inside the vtab constructor. Blanket PRAGMA deny ⇒ every MATCH dies "vtable constructor failed".
  2. A CTE's transient table is itself a SQLITE_READ; discriminator is arg3 dbname ('main' = real table, None = transient). Recursive CTEs also need SQLITE_RECURSIVE. A plain non-recursive CTE needs NO exemption — its reads are attributed to the real table.
  3. A runaway recursive CTE / 3-way cross join runs unbounded on a connection that cannot write a byte. Interrupted at 0.64s / 0.31s by the progress handler.
  4. THE DEFAULT BRANCH MUST RECORD WHAT IT DENIED, not merely deny it — else ATTACH escapes as a bare `DatabaseError: not authorized` traceback instead of a QueryDenied naming the surface. Counted in the set because it is the one the SUITE could not find: the tests accepted `raises((QueryDenied, DatabaseError))` and so could not tell a correct refusal from an unhandled one. Found by running the CLI once.

DISTILLED ONLY (Richard, 2026-08-21): knowledge, knowledge_deps, knowledge_fts (+ its shadow tables). `observations` — the raw thread-summary tier, 17,756 rows on the operator's box — is NOT readable, verified denied directly AND via observations_fts. This path landed BEFORE the distilled-only egress decision, not after it; opening the raw tier is a deliberate decision, not one inherited from whichever surface shipped first.

INVARIANTS:
- NO WRITE VERBS EVER, any caller. Enforced twice: the connection cannot write, and the authorizer denies it before the connection is asked. The write path is `sink:archivist` with its own gates (core/archivist.py). A query surface that can mutate is a second, ungoverned write path.
- THREE OUTCOMES, not two: `rows` / `no-rows` / `store-absent` (+ `schema` for the no-sql discovery call). An empty result MUST be distinguishable from an unasked question AND from "no team store is bound" — collapsing the third makes a standalone install report that the team knows nothing. Same failure the recall ladder's `loose-match-only` exists to prevent (#550/#552).
- Truncation is OBSERVED, not inferred: fetch cap+1. `len(rows)==limit` is ambiguous between "exactly that many" and "more, withheld".
- `_archivist_path` resolves WITHOUT creating the db — `archivist_db()` would init an empty store, collapsing store-absent into no-rows and erasing the cause of the misconfiguration.
- **A BLOB IS REACHABLE ON THE PERMITTED SURFACE, SO ROWS MUST BE COERCED BEFORE THEY LEAVE (Prudence, #707).** `knowledge_fts_data.block` is a BLOB and that table is in ALLOWED_TABLES, so `SELECT * FROM knowledge_fts_data` is an ALLOWED query that ran and then had its rows DISCARDED: the MCP dispatcher serialises with `json.dumps(..., indent=2)` and no `default=`, `bytes` raised TypeError, its blanket `except Exception` caught it, and the caller got `Error: Object of type bytes is not JSON serializable`. A THIRD failure category in a surface whose contract has exactly two, reading to a caller as a server bug. Coerced in `_jsonable` — in the seam that owns the rows, NOT in the dispatcher, whose response path is shared by 34 other tools (techne#695 spent three rounds establishing how expensive changing it is); fixing it at the source covers the CLI and every future consumer at once. A `<blob, N bytes>` marker, not a decoded string: an index block is not text and mojibake is less useful than its size.
- **EVERY NON-QueryDenied ESCAPE IS A CONTRACT VIOLATION, INCLUDING ValueError.** The card promises two failure modes; three separate ways to produce a third were found in one review. `_resolve_archivist_path` raises ValueError on the techne#346 misconfiguration and click let it out — the command printed NOTHING to stdout and dumped a traceback to stderr. `CliRunner` intercepts exceptions, which is exactly why the suite could not see it and a terminal could: A TEST HARNESS THAT SWALLOWS THE FAILURE MODE CANNOT OBSERVE IT. Both subcommands now catch it, and a non-numeric `limit` is a denial rather than `int()`'s message about our internals.
- **`SQLITE_FUNCTION` IS THE ONE INVERSION OF DEFAULT-DENY, AND IT RESTS ON A STATED ASSUMPTION**: there are no application-defined functions on this connection. True today (nothing registers `create_function`/`create_aggregate` on the `_open_remote_readonly` path, and SQLite refuses `load_extension`), but that opener belongs to FEDERATION, not to this module — if federation ever registers a helper, this surface inherits it silently. Adding one means this branch needs an allow-list.
- **NON-FINITE FLOATS ARE THE QUIETER HALF OF THE SERIALISATION PROBLEM.** `json.dumps` emits bare `Infinity`/`NaN` WITHOUT raising, so no exception fires and `isError` is never set — but those tokens are not valid JSON (RFC 8259) and a conformant client rejects the whole response. Strictly worse reporting than the BLOB case, which at least announced itself. Python's own `json.loads` is lenient, which is why a naive Python-side assertion misses it; the test parses with `parse_constant` set to raise so it sees what a strict client sees. Handled in `_cell` alongside bytes.
- **THIS MODULE INHERITS TWO ASSUMPTIONS FROM FEDERATION'S OPENER, AND BOTH ARE SILENT IF BROKEN.** (1) No application-defined functions on the connection — else the blanket `SQLITE_FUNCTION` allow admits them. (2) `_open_remote_readonly` sets neither `detect_types` nor `text_factory`, so sqlite3 can only return NoneType/int/float/str/bytes — which is WHY `_cell` has exactly two cases. Add `detect_types=PARSE_DECLTYPES` there and columns declared TIMESTAMP arrive as `datetime` and pass through uncoerced. Neither is this module's code to protect; both are its code to break.
- **THE SURFACE EXISTS ONLY FOR A SEPARATE STORE (techne#552).** `_archivist_path` now asks `archivist_binding(config)` instead of `config.standalone`, and returns None for BOTH `absent` and `local`. Under `local` the "team" knowledge IS this instance's own `knowledge` table, which `techne_search` and `techne_recall` already answer — offering a second surface onto the same rows, labelled as the team store, would report ONE SOURCE AS TWO. That is the same reason `archivist_connection` returns None for `local`, and the same reason #695 stopped fanning out to the local mirror.
- **A DENIAL MAY NAME A SHADOW TABLE.** Denying `observations_fts` reports `Not readable here: observations_fts_config`, because FTS5's vtab constructor reads `_config` first and prepare aborts there. Correct, but it points at an internal artefact rather than the table the caller named — noted so the next reader is not confused, deliberately not contorted around.

INDEPENDENTLY ADVERSARIALLY TESTED (Prudence, #707): 45 bypass shapes against canaries planted in `observations` AND in a personal `techne.db` — `main.`-qualified and quoted/bracketed identifiers, every `observations_fts` shadow table, `sqlite_master`/`sqlite_schema`/`sqlite_temp_master`, `dbstat`, `sqlite_dbpage`, `pragma_*` table-valued functions, bare `PRAGMA table_list`/`database_list`, `ATTACH` plain AND URI-form, `VACUUM INTO`, `ANALYZE`, `BEGIN`, temp-table creation, `fts5vocab`, `load_extension`, correlated scalar sub-queries, `UNION ALL`, joins, **a CTE NAMED `knowledge` wrapping `observations`**, and recursive-CTE laundering. All denied, no canary ever surfaced. `EXPLAIN` / `EXPLAIN QUERY PLAN` denied too. TWO PROPERTIES WORTH KNOWING ARE MEASURED, NOT ASSUMED: (a) a VIEW wearing an allow-listed name cannot launder the raw tier — `knowledge_deps` recreated as `CREATE VIEW knowledge_deps AS SELECT content FROM observations` was denied on the underlying `observations` read, with the view name never consulted, because THE ALLOW-LIST IS ATTRIBUTED TO REAL TABLES, NOT TO NAMES IN THE `FROM` CLAUSE; (b) across nine query shapes every real-table read arrived with `db='main'` — `dbname is None` appeared only for SELECT/FUNCTION, never for a READ of real data. OP_BUDGET headroom against a 2,100-row store: full-tier scan 48 units, GROUP BY 14, FTS MATCH + bm25 38, LIKE scan 12, self-join 6,626 — against 50,000, so honest work sits three orders of magnitude clear while the runaway still trips.
CONSUMERS: mcp_server._techne_archivist_query (returns a denial as a RESULT, so the agent learns the surface instead of getting a bare "Error: not authorized"); cli.py `techne archivist query|schema`.
FAIL-MODES: QueryDenied = a statement about the interface (learn it, re-ask); sqlite3.Error = the caller's SQL is wrong. Flattening both into one string teaches neither. CLI exit codes are the enforceable form of that distinction: 0 ran, 2 refused, 1 bad SQL, 3 the query worker broke (`WorkerFailed`) — and neither error path prints a traceback, which would describe OUR call stack for THEIR mistake.
THE AUTHORIZER'S DEFAULT BRANCH MUST RECORD WHAT IT DENIED (`ops`), not just deny. It did not in the first cut, so ATTACH — the most important thing here — escaped as a bare `DatabaseError: not authorized` traceback rather than a QueryDenied naming the surface. The guard worked; the REPORTING of it did not. The tests accepted `(QueryDenied, sqlite3.DatabaseError)` and so could not tell the difference; running the CLI found it in one command. Tests now assert QueryDenied specifically.
MEASURED SQLITE ORDERING: `DROP TABLE x` is refused as DELETE, not DROP TABLE — SQLite issues SQLITE_DELETE first (a drop deletes rows) and prepare aborts on the first denial. Assert that a write verb appears, never which one; the ordering is SQLite's, not our invariant.
TESTING: tests/test_archivist_query.py. Every guard is pinned by a test that FAILS WHEN THE GUARD IS REMOVED — verified by mutating all twelve guards, not by review. Two mutants survived the first pass: the SQLITE_PRAGMA branch was untested (the pragma_* table-valued functions take a different branch), and `test_limit_is_capped` asserted against a 3-row fixture, so it passed with or without the cap (the do-nothing shape of #701). Both fixed. If you widen this surface, mutate it again.
